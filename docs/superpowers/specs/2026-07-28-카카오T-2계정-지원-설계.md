# 카카오T 비즈니스 2계정 지원 — 설계

작성일: 2026-07-28

## 배경

UGD는 카카오T 비즈니스(법인택시) 계정을 **2개** 운영한다. 지금 ERP는 계정 하나만 전제하고 만들어져
있어 두 번째 계정의 이용내역·직원이 화면에 전혀 잡히지 않는다.

### 실측 현황 (2026-07-28, 읽기 전용 API 호출로 확인)

| | 계정 #1 | 계정 #2 |
|---|---|---|
| 기업ID | `26390514` | `25648071` |
| 그룹 | 12개 — 이름이 지점명과 일치(남산광어·대물섬 한남/종로점·8번대물집·사카바단단·강남대골뼈국·본사 등) | **`기본그룹` 1개뿐** |
| 인증완료 직원 | 32명 (30명 부서 기입됨) | 10명 → **7명** (퇴사자 3명 삭제, 부서 기입 완료 — 아래 "선행 데이터 작업" 참조) |
| 2026-06 이용 | 221건 | 98건 |
| 2026-07 이용(28일까지) | 224건 | 106건 |

두 계정 모두 자격증명이 유효함을 실호출로 확인했다. 계정 #2 이용량이 계정 #1의 약 45%로 무시할 수 없다.

### 확인된 제약과 사실

1. **계정 #2에는 지점 판별 근거가 없다.** 이용내역의 `group_name`은 전부 `기본그룹`, `member_department`는
   빈값/null이다. 그대로 통합하면 200여 건이 전부 "미매핑"으로 쌓인다.
2. **부서는 소급 반영된다(실측).** 카카오는 이용내역 응답에 *조회 시점*의 회원 부서를 조인해 준다.
   근거: 계정 #1은 2026-07-24 이후 부서를 채웠는데, 그 이전인 6월 주문 221건 중 부서 빈값이 10건뿐이고
   그 10건도 현재 회원 목록에 없는 인원(탈퇴·미연결)이다. 회원 목록에 있는 인원의 과거 주문은
   **전부 현재 부서 값과 일치**했다.
   → 계정 #2 직원 부서를 지금 채우면 과거 이용내역도 자동으로 지점별 집계에 잡힌다.
3. **지점 판정은 부서 우선.** `resolveBranchName`(src/pages/admin/helpers/kakaoTaxi.ts)이
   `member_department` → `group_name` 순으로 본다. 따라서 계정 #2에 지점명 그룹을 새로 만들 필요가 없다.
   (그룹 CRUD는 카카오 API 미제공이라 어차피 관리 웹에서만 가능하다.)
4. **매핑 성공 조건**: 부서 문자열이 ERP 지점 목록(`public_branches`)에 실제로 존재해야 한다.
   별칭표(`KAKAO_BRANCH_ALIASES`)에 있어도 지점이 없으면 미매핑으로 떨어진다.
5. **동명이인이 양쪽 계정에 있다.** 정윤기 씨가 계정 #1(대물섬 한남점)과 계정 #2(8번대물집) 양쪽에
   있으며 **서로 다른 사람**이다(사용자 확인).
6. 계정 #2 직원 4명(김지혜·최우석·이태현·승윤=백승윤)은 `name`이 비어 있고 `identifier`만 있다.
   이용내역 표에 "(이름 없음)"으로 뜬다. 카카오 PUT은 미전송 필드를 공백으로 지우므로 수정 시 주의가 필요하다.
7. **삭제된 회원의 과거 이용내역은 부서를 잃는다(실증).** 주문에 `member_id`·`member_name`·
   `member_identifier`는 스냅샷으로 남지만 **`member_department`가 `null`이 된다.** 회원이 사라져
   조인할 대상이 없기 때문이다. 재등록해도 새 ID가 발급돼 과거 건과 연결되지 않는다.
   → 퇴사자를 카카오에서 지우면 그 사람의 과거 이용액이 지점 비용에서 빠지고 "미매핑"으로 뜬다.

## 목표

- 관리자·지점 화면이 **두 계정의 이용내역·직원을 하나로** 보여준다.
- 어느 계정 것인지 화면에서 **구분 가능**하다.
- 계정 #2 직원도 ERP에서 **관리(부서 수정 등)** 할 수 있다.
- 계정 하나가 실패해도 **금액이 조용히 줄어들지 않는다.**

## 비목표

- 계정 #2에 지점별 카카오 그룹 생성 (API 미제공, 부서만으로 충분)
- 두 계정의 통합·이관
- 계정 3개 이상으로의 일반화 — 다만 레지스트리 구조라 추가는 상수 한 줄이면 된다

## 설계

### 1. 계정 레지스트리 (백엔드 — `gas/Code.gs` + `server.ts` 미러)

카카오 호출 계층 최하단에 계정 개념을 도입한다.

```
KAKAO_TAXI_ACCOUNTS = [
  { key: "acct1", label: "1계정", corpIdProp: "KAKAO_T_CORP_ID",   secretProp: "KAKAO_T_SECRET" },
  { key: "acct2", label: "2계정", corpIdProp: "KAKAO_T_CORP_ID_2", secretProp: "KAKAO_T_SECRET_2" },
]
```

- **자격증명은 저장소에 두지 않는다.** GAS는 스크립트 속성, 로컬은 `.env`. 계정 #2 값은 별도 전달 경로로만.
- **속성이 등록되지 않은 계정은 목록에서 제외**한다. 코드만 먼저 배포되고 속성 등록이 늦어도
  기존과 동일하게 동작한다(배포 순서 사고 방지). 단 **계정이 하나도 없으면** 기존과 같은 오류를 던진다.
- `kakaoTaxiBuildRequest / kakaoTaxiFetch / kakaoTaxiFetchAllPages` 전부 첫 인자로 `accountKey`를 받는다.

### 2. 조회 통합

`getKakaoTaxiOrders` / `getKakaoTaxiGroups` / `getKakaoTaxiMembers`는 등록된 계정을 순회하며 수집하고,
각 레코드에 **`account_key`를 주입**한 뒤 합쳐서 돌려준다.

- **캐시는 계정별로 분리**한다. 키에 계정을 포함(`kakao_taxi_orders_v1_<ver>_<account>_<month>`).
  한쪽 계정이 느리거나 실패해도 다른 쪽 캐시는 유효하고, ScriptCache 100KB 제한도 분산된다.
- 스냅샷 완전성 검사(`kakaoTaxiSnapshotComplete`)는 **계정별로** 수행한다. 계정별로 통과한 것만 캐시한다.
- 캐시 무효화: 직원 쓰기는 **해당 계정의 members 캐시**를 지우고, 이용내역은 기존대로 세대 번호를 올려
  전 계정·전 월을 함께 무효화한다(부서 변경이 집계를 바꾸므로).

### 3. 부분 실패 처리

응답을 `{ items, accountErrors: [{ key, label, message }] }` 형태로 바꾼다.

- 성공한 계정 데이터는 그대로 보여준다.
- 실패한 계정이 있으면 화면 상단에 **빨간 배너**로 "○○ 계정 조회 실패 — 아래 집계에 해당 계정 내역이
  빠져 있습니다"를 띄운다.
- 근거: 기존 fail-closed 원칙("일부 누락본을 정상 자료처럼 돌려주지 않는다")의 취지는 *합계가 조용히
  줄어드는 것*을 막는 데 있다. 명시적 경고는 그 취지를 지키면서, 계정 #2 장애로 기존 기능까지
  마비되는 것을 피한다.
- **모든 계정이 실패하면 기존처럼 오류를 던진다.**

### 4. 지점 → 계정 매핑

```
KAKAO_ACCOUNT_BY_BRANCH = { "<지점명>": "acct2", ... }   // 미기재 지점은 기본값 acct1
```

- 지점 이용신청(자동등록)이 이 표를 보고 등록할 계정을 정한다.
- **계정 #2로 등록할 때**: 지점명 그룹이 없으므로 그 계정의 `기본그룹`(활성 그룹이 하나뿐일 때)을 쓰고,
  `department`에 지점명을 넣는다. 지점 판정이 부서 우선이라 집계는 정상 동작한다.
  활성 그룹이 여럿인데 지점명과 일치하는 게 없으면 **거부**한다(오등록 방지, 기존 정책 유지).
- 이 표는 `gas/Code.gs`·`server.ts`·프론트 세 곳 동기화 대상이다(별칭표와 동일한 관리 방식).

### 5. 중복·동명이인

- **전화번호 중복 검사를 전 계정으로 확대**한다. 지금은 계정 #1만 봐서, 같은 사람이 양쪽에 등록되면
  이중 청구가 발생한다(정윤기 씨 실제 사례). 중복 안내 문구에 어느 계정·어느 지점인지 함께 표시한다.
- **`memberKey`에 계정을 포함**한다: `계정|이름|사번`. 안 하면 두 계정의 동명이인이 한 사람으로 합산되고,
  이상 점검의 "전월 대비 급증" 판정도 함께 틀어진다.
- 이상 점검 면제 목록(`TAXI_ANOMALY_EXEMPT_MEMBER_IDS`)을 **계정+member_id 쌍**으로 바꾼다.
  카카오 member_id는 8자리 단문자열이라 계정 간 충돌 가능성을 배제할 수 없다.

### 5-1. 퇴사자 과거 내역 귀속 보정

퇴사자를 카카오에서 삭제하면 그 사람의 과거 이용내역이 부서를 잃고 미매핑으로 떨어진다(위 "확인된 제약" 7번).
계정 #2는 그룹까지 `기본그룹` 하나뿐이라 그룹명 보조 판정도 통하지 않는다.

`resolveBranchName`이 부서·그룹으로 지점을 못 찾았을 때 마지막으로 보는 **member_id 보정표**를 둔다.

```
KAKAO_RETIRED_MEMBER_BRANCH = { "acct2|ZB2L167I": "사카바단단", ... }   // 김태호, 2026-05 10건 90,700원
```

- 키는 **계정+member_id**다. 이름으로 매칭하면 동명이인을 가를 수 없다(정윤기 사례).
- 보정된 건은 `unmapped: false`로 정상 집계하되, 원본에 부서가 없었다는 사실은 유지한다.
- 퇴사자가 생길 때마다 한 줄씩 추가하는 수동 표다. **삭제 전에 부서를 채워두면 애초에 필요 없으므로**,
  운영 지침은 "퇴사자는 삭제 대신 존치(또는 삭제 전 부서 확인)"를 권한다.

### 6. 쓰기 경로 라우팅

수정·삭제·휴직·알림톡은 `memberId`만 받는데 어느 계정인지 알 수 없다.

- 프론트가 `accountKey`를 함께 전송하고, 백엔드는 허용 목록 대조 후 라우팅한다.
- **쓰기는 `accountKey` 미지정 시 거부**한다. 기본값으로 계정 #1을 쓰면 엉뚱한 계정에 삭제가 나갈 수 있다.
  프론트와 백엔드를 함께 배포하므로 하위호환이 필요 없다.
- 조회는 계정 미지정 시 전 계정 통합(기본 동작).

### 7. 화면

**관리자 > 법인택시**
- 이용내역·직원 관리 표에 **계정 컬럼** 추가, 엑셀 내려받기에도 포함
- 계정 필터(전체 / 1계정 / 2계정)
- 계정 조회 실패 배너
- 직원 수정·삭제 시 해당 행의 계정으로 라우팅

**지점 > 비즈니스택시**
- 자기 지점 직원 조회는 부서 기준이라 두 계정이 자동 통합된다(`getKakaoTaxiBranchMembers`가
  전 계정 목록을 필터하도록 변경)
- 이용신청은 매핑표가 정한 계정으로 등록

UI 변경은 `DESIGN.md` §6-0-1 폰트 기준표를 따른다(제목/헤더/입력칸/버튼 11px, 데이터셀 12px, `text-sm` 금지).

## 선행 데이터 작업 — **완료 (2026-07-28)**

계정 #2 직원 부서를 채우지 않으면 200여 건이 전부 미매핑으로 뜨므로, 1단계 배포 전에 먼저 처리했다.

- **퇴사자 3명 정리**: 서승현·박경택(둘 다 이용 0건)은 이름·전화 대조 후 삭제. 김태호는 이용 이력이 있어
  존치를 권고했으나 별도로 삭제됨 → 5월 10건(90,700원)이 미매핑으로 남았고, §5-1 보정표 대상이 되었다.
- **부서 기입 7명 완료**(전원 HTTP 200):
  사카바단단 = 정승화·이윤지·김지혜·이태현·백승윤(카카오엔 `승윤`)·최우석 / 8번대물집 = 정윤기
- **소급 반영 실증**: 기입 직후 과거 내역이 즉시 지점별로 잡혔다.
  5월 사카바단단 64건 977,980원 / 8번대물집 25건 263,900원, 6월 71건 1,160,300원 / 27건 250,700원,
  7월 86건 1,392,700원 / 20건 225,300원. 잔여 미매핑은 김태호 10건뿐이다.
- **적용한 규칙**(향후 동일하게 유지):
  - PUT은 `name`·`mobile_phone`·`department`·`group_ids` 4필드를 항상 함께 전송(미전송 필드는 공백으로 지워짐)
  - 기존 `group_ids` 그대로 유지 — 그룹 제거 PUT은 카카오가 500으로 거부한다
  - ERP 지점명과 정확히 일치하는 문자열만 사용 — 확인 결과 `사카바단단`·`8번대물집`이 정확한 표기다
    (`src/api/firebaseAuth.ts`·`src/pages/BranchConfirmPage.tsx`·`gas/Code.gs` 세 곳 일치, 별칭 불필요)

**남은 데이터 작업**: 이름이 빈 4명(김지혜·최우석·이태현·백승윤)은 이용내역에 "(이름 없음)"으로 뜬다.
`name`을 채우면 해소되나 이번 작업 범위 밖으로 두었다.

## 배포 단계

**1단계 — 조회 통합**
계정 레지스트리, 조회 3종 통합, 계정별 캐시, 부분 실패 배너, 계정 컬럼·필터,
`memberKey`·면제목록 계정 반영, 퇴사자 귀속 보정표(§5-1).
쓰기는 계정 #1 고정 유지.

**2단계 — 쓰기·등록 통합**
쓰기 계정 라우팅, 지점→계정 매핑표, 자동등록 계정 선택, 중복 전화 검사 전 계정 확대.

선행 데이터 작업(부서 채우기)은 **완료**했다.

## 테스트

- **자격증명 부재**: 계정 #2 속성 미등록 상태에서 기존 화면이 그대로 동작하는가
- **부분 실패**: 계정 #2 시크릿을 일부러 틀리게 두고, 계정 #1 데이터가 보이면서 배너가 뜨는가
- **집계 대사**: `verifyBranchTotals`가 두 계정 합산에서도 통과하는가(지점별 합계 총합 == 건별 총합)
- **실측 기준값 대조**: 계정 #2가 5월 사카바단단 64건 977,980원 / 8번대물집 25건 263,900원,
  6월 71건 1,160,300원 / 27건 250,700원, 7월(28일까지) 86건 1,392,700원 / 20건 225,300원으로 나오는가
- **퇴사자 보정**: 김태호 5월 10건 90,700원이 보정표로 사카바단단에 귀속되는가
- **동명이인**: 정윤기 씨가 계정별로 분리 집계되는가, 이상 점검 급증 판정이 계정별로 이뤄지는가
- **캐시 무효화**: 계정 #2 직원 부서를 고친 뒤 이용내역 집계가 즉시 바뀌는가
- **쓰기 라우팅**: `accountKey` 없이 삭제 요청 시 거부되는가
- **중복 등록**: 계정 #1에 있는 번호를 계정 #2 지점에서 등록 시도하면 차단되는가
- 로컬(`npm run dev`, localhost:3000)에서 화면 확인 후 사용자에게 보여주고, "배포해" 지시 전에는 커밋·푸시하지 않는다
- 배포 직전 Codex 지독한 리뷰 필수(상시 지침)
