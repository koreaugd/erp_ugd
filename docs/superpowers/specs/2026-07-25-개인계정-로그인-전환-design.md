## 1. 배경과 목적

현재 로그인은 **지점 공통 PIN 1개 + 관리자 PIN 1개** 방식이다.

- 계정 단위가 사람이 아니라 "지점"이며, 전 지점이 PIN 하나를 공유한다 (`src/api/firebaseAuth.ts`의 `ugd-{PIN}` 패턴, 지점당 가짜 계정 `branch-NN@ugd-erp.example`).
- 어느 지점인지는 로그인 화면 드롭다운에서 스스로 고른 값일 뿐, 인증 토큰과 무관하다.
- 작성자 기록(`submittedBy`/`modifiedBy`)은 존재하지만 **손으로 타이핑하는 자기신고**라 신뢰할 수 없다 (`firebaseDirect.ts:146` — 비면 `"branch"`, `"관리자"`, `"미상"`이 들어감).

**목적 (사용자 확인 완료):**
1. **추적** — ERP의 어떤 내용을 어느 계정이 등록·수정했는지 남긴다.
2. **PIN 단독 로그인 제거** — PIN 하나만 알면 익명으로 들어오는 구조를 없앤다. v3부터 PIN은 존속하되 역할이 바뀐다: "그것만 있으면 되는 열쇠" → "개인 계정에 더해 요구되는 회사 게이트". 진입에는 항상 계정+PIN 둘 다 필요하므로 기록은 계정 단위로 남는다.

**목적이 아닌 것 (Non-goals — 전부 사용자 명시 확인):**
- **지점 간 데이터 격리는 하지 않는다.** 규칙 수준에서 지점별 쓰기를 막지는 않는다 — 급여대장(§15)만 예외로 규칙까지 격리한다. 단 **v7부터 지점 접근 기본값은 "전체"가 아니라 "가입 시 고른 지점 한 곳"이다**(사용자 지시, 2026-07-28). 넓혀야 할 계정은 총괄이 계정 관리에서 개별로 열어 준다.
- **계정 공유를 막지 않는다.** 한 아이디를 여러 사람이 써도 무방하다(사용자 확정). 추적 단위는 "사람"이 아니라 "계정"이다 — 기록에는 계정 이름·uid가 남는다.
- Firestore 업무 컬렉션(`daily_settles` 등)의 쓰기 규칙 강화는 하지 않는다. 단 `users` 컬렉션 잠금은 예외로 반드시 한다(§6).
- 휴대폰(SMS) 가입 제외 (Blaze 유료 + SMS 과금).
- GAS 백엔드의 인증 방식 개편(ID token 검증 전환)은 이번 범위가 아니다 — §9의 임시 호환책으로 대응하고 장기 과제로 남긴다.

**수용한 잔여 위험 (사용자 고지·수용 완료):**
- 가입 자체는 열려 있으나 **로그인 후 PIN 게이트(§4)** 를 통과해야 앱에 진입할 수 있다. PIN을 모르는 외부인은 계정을 만들어도 화면에 못 들어온다. 단 이 게이트는 클라이언트 검증이므로, 가입만 한 외부인이 개발자도구로 Firestore에 직접 쓰는 경로는 이론상 남는다(업무 컬렉션 규칙이 `signedIn()`이기 때문). 대응은 "모든 기록에 계정 표시 + 신규 가입 관리자 알림 + 정지 기능"이며, 규칙 수준 차단은 하지 않는다.
- 탭 권한은 UI 차단이다. 개발자도구 우회 가능. 내부 도구 성격상 수용.
- suspended 계정이 이미 열어둔 화면의 쓰기는 즉시 막히지 않는다. 30분 유휴 로그아웃(§10)과 브라우저 종료 시 로그아웃으로 자연 차단되는 수준을 수용.

## 3. 데이터 모델

### 3.1 `users` 컬렉션 (신설)

문서 ID = Firebase Auth `uid`.

```
users/{uid}
  name: string          // 표시 이름. 구글=displayName, 이메일가입=가입 시 입력
  email: string
  phone: string         // 가입 시 필수 입력
  workBranch: string    // 가입 시 고른 근무지점. 계정 관리 '선택지점' 컬럼의 원본이며 이후 바뀌지 않는다
  role: "admin" | "branchAdmin" | "branch"   // 기본 "branch" — 표시는 총괄 / 지점관리자 / 지점
  allowedTabs: string[] | "all"     // 기본 ["daily.settle"] — 키 체계는 §5 레지스트리 참조
  allowedBranches: string[] | "all" // 기본 [workBranch] — 고른 지점 한 곳 (v7)
  salaryBranches: string[] | "all"      // 급여대장 허용 지점. 기본 [] (불가). §15
  salaryBranchesEncoded: string[] | "all"  // 위의 encodeURIComponent 본 — 규칙이 그대로 비교
  allowedBranchesEncoded: string[] | "all" // allowedBranches의 인코딩본 — 규칙이 급여 범위 상한을 확인하는 데 쓴다
  status: "active" | "suspended"    // 기본 "active"
  createdAt: string                 // ISO
  reviewedByAdmin: boolean          // 기본 false — 신규가입 알림 배지용
```

- `workBranch`와 `allowedBranches`는 목적이 다르다. **`workBranch`는 "가입할 때 스스로 밝힌 소속"이라 바뀌지 않는 기록**이고, `allowedBranches`는 총괄이 넓히고 좁히는 살아 있는 권한이다. 계정 관리 목록의 '선택지점' 컬럼은 앞의 것을, '허용 지점' 요약은 뒤의 것을 보여준다.

- **생성**: 첫 로그인 성공 직후 클라이언트가 자기 문서를 생성. 규칙이 **기본값 그대로일 때만** 허용(§6).
- **생성 실패 시** (Codex 지적 반영): 즉시 `signOut()` + "가입 처리에 실패했습니다. 다시 로그인해 주세요" 안내. users 문서 없이 앱 진입은 불가 — 로그인 판정(§4)이 users 문서 로드를 통과 조건으로 삼는다. 다음 로그인에서 생성 재시도.
- **수정**: 관리자(개인 계정 admin)만. 본인 수정 불가 — 규칙으로 잠금. **타협 불가 항목** (없으면 셀프 권한 상향 가능).
- **삭제**: 관리자만. Auth 계정 자체 삭제는 Spark에 Admin SDK가 없어 불가 → `suspended`로 차단, Auth 정리는 콘솔 수동.

### 3.2 `UserSession` 스키마 개정 (Codex 지적 반영)

현행 `UserSession`은 `pinHash`가 필수라 개인 계정에서 깨진다. 다음으로 개정:

```ts
interface UserSession {
  loginType: "personal" | "pin";
  uid?: string;            // personal만
  name: string;            // personal=users.name, pin=지점명/관리자
  email?: string;
  role: "admin" | "branchAdmin" | "branch";   // v7 — pin 로그인은 항상 "branch"/"admin"
  branchName: string;      // 선택된 지점 (현행 유지)
  brand: string;
  allowedTabs: string[] | "all";     // pin 로그인은 "all" (현행 동작 보존)
  allowedBranches: string[] | "all"; // pin 로그인은 "all"
  pinHash: string;         // pin 로그인=로그인 PIN 해시(현행), personal=로그인 직후 PIN 게이트(§4)에서 채움
}
```

- v3부터 개인 로그인도 PIN 게이트를 통과해야 세션이 만들어지므로 `pinHash`는 **항상 채워진다.** `user.pinHash`를 참조하는 기존 코드(AdminPage 일일목록, KakaoTaxiSection, BusinessTaxiTab, gasClient)는 **수정 없이 그대로 동작**한다.
- **PIN 로그인 세션은 `users` 문서를 만들지 않는다** — `users`는 개인 계정 전용. `loginType`으로 두 경로를 구분한다.

## 4. 로그인 화면 개편 (`LoginPage.tsx`)

### 새 첫 화면
1. **[구글로 시작하기]** (주 동선, `signInWithPopup`)
2. 이메일/비밀번호 로그인 + [가입하기] 전환 — 가입 폼: 이름(필수)+이메일+비밀번호, `createUserWithEmailAndPassword` 후 `updateProfile(displayName)`. [비밀번호 찾기] = `sendPasswordResetEmail`
3. 하단 작게: **[기존 PIN으로 로그인]** — 펼치면 현행 PIN 플로우 그대로 (전환 기간용)

### 로그인 후 판정 순서 (users 문서 로드 + PIN 게이트가 통과 조건)

**게이트 순서는 "지점 선택 → PIN"이다** (v4 확정). (지점, PIN) 쌍을 함께 검증해야 현행 로그인·GAS 소비처와 일치하기 때문 (Codex 2차 P0-1·2).

```
Auth 성공 (개인 계정)
 → users/{uid} 읽기
   → 없으면: 기본값으로 create 시도
       → 실패: signOut + 오류 안내 (앱 진입 불가)
   → status == "suspended": "관리자에게 문의" 화면 + 즉시 signOut
 → role == "branch":
     [지점 선택] allowedBranches 목록(1개면 자동 선택)
     [PIN 게이트] 지점 공통 PIN 입력
       → 검증: 게이트 전용 보조 Auth(아래 "gateAuth 규격")로
          signInWithEmailAndPassword(gateAuth, 선택 지점의 loginEmail, `ugd-{PIN}`)
          — 현행 지점 로그인과 정확히 동일한 (지점, PIN) 쌍 검증.
       → Firestore settings 폴백은 두지 않는다
          — 게이트 통과 전 계정이 pin_hash를 읽는 구멍이 되므로 (Codex 2차 P0-3).
 → role == "admin":
     [PIN 게이트] 관리자 PIN 입력
       → 검증: gateAuth로 admin@ugd-erp.example + `ugd-{PIN}` 로그인 시도 (위와 동일 패턴)
 → 실패: 재입력 (failedAttempts 카운트 현행 유지). 통과 전 앱 진입 불가
 → 통과: UserSession.pinHash = hashPin(입력 PIN)  → §9의 GAS·카카오 기능이 그대로 동작
 → 세션 구성 (loginType: "personal") → admin은 /admin, branch는 선택 지점으로 진입
```

### gateAuth 규격 (Codex 3차 P0·P1 반영 — 구현 강제 사항)
- **전용 헬퍼 `verifyGatePin()`을 신설한다. 기존 `loginWithBranchPin`/`loginWithAdminPin` 재사용 금지** — 그 헬퍼들은 주(主) Auth 인스턴스에 로그인하므로 재사용하면 개인 세션이 지점/관리자 가짜 계정으로 바뀐다(주 세션 오염, Codex 3차 P0).
- 보조 앱 생성: `getApps().find(a => a.name === "gate") ?? initializeApp(firebaseConfig, "gate")` — config 객체와 이름을 함께 전달(이름만 주는 `initializeApp("gate")`는 성립하지 않음), 재초기화 방지 가드 포함.
- 보조 Auth: `initializeAuth(gateApp, { persistence: inMemoryPersistence })` — 게이트 검증 결과가 디스크에 남지 않게 한다. **`initializeAuth`는 같은 앱에 두 번 호출하면 오류이므로 모듈 스코프 싱글턴 getter(`getGateAuth()`)로 감싼다** (Codex 4차 P1 잔여 반영). 검증 성공/실패와 무관하게 `try/finally`로 `signOut(gateAuth)` 보장.

### 게이트 오류 분류·폴백 정책 (Codex 3차 P0 — 브루트포스 우회 차단)
- **자격증명 오류는 절대 GAS로 폴백하지 않는다**: `auth/wrong-password`, `auth/invalid-credential`, `auth/user-not-found`, `auth/too-many-requests` → 즉시 실패 처리. 특히 `too-many-requests`(Firebase 남용 방지 차단)를 폴백하면 4자리 PIN 브루트포스가 GAS `verifyPin`으로 우회되므로 금지. 이때 안내: "시도가 너무 많습니다. 잠시 후 다시 시도해 주세요."
- **네트워크류 오류만 폴백**: `auth/network-request-failed` 등 연결 실패 → `gasClient.verifyPin(pinHash)` 호출 후, 지점은 반환 `branchName` 일치·관리자는 반환 `role == "admin"`을 반드시 비교(현행 `useAuth.ts:67-72` 패턴).
- 공유 지점 계정이 `too-many-requests`로 잠기면 정상 사용자도 잠시 막힌다 — 수용(수 분 내 자동 해제, 내부 도구 특성상 빈도 낮음).

- **역할·지점 강제**: 지점 계정은 "선택한 지점의 계정 비밀번호"로만, 관리자 계정은 "관리자 계정 비밀번호"로만 통과할 수 있다. 지점 계정이 관리자 PIN을 넣거나 그 반대는 구조적으로 불가능 (Codex 2차 P0-1 해소). BusinessTaxiTab 등 지점별 GAS 검증도 현행 세션과 동일한 (지점, pinHash) 쌍이 유지되므로 무수정 동작 (P0-2 해소).
- PIN 게이트는 브라우저 세션마다 1회 (세션 지속성이 browserSession — 현행 PIN 로그인 빈도와 동일).
- 이 게이트는 클라이언트 검증이다 — 회사 외부인 차단이 목적이며, 개발자도구 우회 가능성은 §1 잔여 위험으로 수용.
- 공통 PIN은 존속하되 역할이 "로그인 비밀번호"에서 "회사 게이트"로 축소된다. 유출 시 교체 절차는 현행(관리자 화면 PIN 변경) 유지.

### Legacy 세션 마이그레이션 (Codex 2차 P1-2)
- 세션 저장 키를 `erp_ugd_session` → `erp_ugd_session_v2`로 올린다. 새 복구 로직은 `loginType` 필드가 있는 v2 세션만 인정하고, 구 키는 읽지 않고 삭제한다. 배포 직후 기존 접속자는 1회 재로그인 — split-brain 원천 차단.

### 세션 관리 일원화 (Codex split-brain 지적 반영)
- 개인 로그인의 세션 원본은 **Firebase Auth (`onAuthStateChanged`)** 하나다. sessionStorage에는 파생 캐시(선택 지점 등)만 두고, Auth 상태와 어긋나면 Auth를 따른다. 새로고침 복구는 `onAuthStateChanged` → users 재로드로 처리.
- PIN 로그인은 현행 sessionStorage 방식 그대로 (전환 기간 동안 두 경로가 코드상 분리되어 공존, `loginType`으로 구분).
- `setPersistence(auth, browserSessionPersistence)` — 브라우저 닫으면 로그아웃(현행 체감 동일).

### 이메일 인증
인증 메일은 보내되 **로그인 차단 조건으로 삼지 않는다.** Firebase 기본 발신 주소는 네이버/다음에서 스팸 처리가 잦아 인증 강제 시 "메일이 안 온다" 문의가 반복된다. 구글 로그인이 주 동선이고 기본 권한이 최소라 실용적 타협.

## 6. Firestore 규칙 변경 (users 컬렉션만 추가)

기존 업무 컬렉션 규칙은 **변경하지 않는다.** 아래만 신설.

```
// 개인 계정 관리자 판정 — users 문서 기반, status 확인 포함 (Codex 지적 반영)
function isPersonalAdmin() {
  return signedIn()
    && exists(/databases/$(database)/documents/users/$(request.auth.uid))
    && get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'admin'
    && get(/databases/$(database)/documents/users/$(request.auth.uid)).data.status == 'active';
}

match /users/{uid} {
  // 본인 문서 읽기 + 개인 관리자 전체 읽기
  allow read: if signedIn() && (request.auth.uid == uid || isPersonalAdmin());
  // 본인 생성은 "기본값 그대로"일 때만
  allow create: if signedIn() && request.auth.uid == uid
    && request.resource.data.role == "branch"
    && request.resource.data.allowedTabs is list
    && request.resource.data.allowedTabs.size() == 1
    && request.resource.data.allowedTabs[0] == "daily.settle"   // §5 레지스트리의 일일마감 권한 키 — 문서 전체 단일 표기
    // v7: 허용 지점은 "전체"가 아니라 본인이 고른 근무지점 한 곳이어야 한다.
    // 스스로 전 지점 권한을 달고 가입하는 경로를 규칙에서 막는다.
    && request.resource.data.allowedBranches is list
    && request.resource.data.allowedBranches.size() == 1
    && request.resource.data.allowedBranches[0] == request.resource.data.workBranch
    && request.resource.data.status == "active"
    && request.resource.data.reviewedByAdmin == false;
  // 수정·삭제는 "개인 계정 관리자"만, 그리고 본인 문서는 관리자라도 불가
  // (Codex 2차 P1-1: isPersonalAdmin()만으로는 관리자의 셀프 수정이 뚫려 문구와 규칙이 어긋났음)
  allow update, delete: if isPersonalAdmin() && request.auth.uid != uid;
}
```

- 부작용 명시: 관리자도 자기 문서(이름 등)를 화면에서 못 고친다. 관리자가 2명 이상이면 서로 고쳐 주고, 1명뿐이면 Firebase 콘솔에서 수정한다. 셀프 권한 상향·셀프 정지해제를 막는 대가로 수용.

### 전환기 PIN 관리자의 권한 경계 (Codex P0 반영)
- **`users` 컬렉션에는 기존 `isAdmin()`(= `admin@ugd-erp.example` 이메일 판정)을 쓰지 않는다.** 계정·권한 관리는 개인 관리자 계정 전용. 유출된 관리자 PIN으로는 계정 체계를 건드릴 수 없다.
- 기존 업무 컬렉션(`public_branches`, `settings`, `edit_logs`)의 `isAdmin()`은 전환 기간 동안 `isAdmin() || isPersonalAdmin()`으로 확장 — 개인 관리자도 기존 관리자 기능을 쓸 수 있게. PIN 로그인 제거 시점에 `isAdmin()` 분기 삭제.
- 클라이언트 쪽 관리자 가드 중 `admin@ugd-erp.example` 이메일을 직접 비교하는 곳은 전수 조사해 교체한다. **교체 기준** (Codex 2차 P2-2 — API 레이어는 React 세션을 모르므로 "세션 판정으로 교체"만으로는 불충분): `firebaseDirect.ts:716-718`처럼 세션에 접근 못 하는 함수는 **호출부가 `isAdminSession: boolean` 인자를 명시적으로 전달**하도록 시그니처를 바꾼다. 이메일 비교는 `이메일 일치 || isAdminSession`으로 확장 후, PIN 제거 시점에 이메일 분기 삭제.

### 규칙 `get()` 비용
- `isPersonalAdmin()`의 `get()`은 규칙 평가당 읽기 1회 추가. 호출 지점은 관리자 쓰기 경로 + users 읽기라 빈도가 낮고, Firestore는 동일 요청 내 동일 문서 `get()`을 1회로 계산한다. Spark 일일 무료 읽기 쿼터(5만) 내에서 충분하나, **"비용 0원 보장"이 아니라 "무료 쿼터 내 운영 목표"로 표현을 정정**한다(Codex 지적). 초과 시에도 과금이 아니라 일시 거부이며, 관리자 화면 사용 패턴상 도달 가능성 낮음.

### 부트스트랩
첫 관리자 1명(사용자 본인 구글 계정)의 `users/{uid}` 문서는 구현자가 콘솔/스크립트로 직접 생성 (`role: "admin"`). 이후 관리자 지정은 계정 관리 탭에서.

## 7. 작성자 자동 기록

### 원칙
- 기존 `submittedBy`/`modifiedBy` 문자열 필드와 `edit_logs` 파이프라인을 **그대로 유지**한다 (기존 export·리포트·관리자 화면 호환). 
- 여기에 **`submittedByUid` / `modifiedByUid` 필드를 병행 추가**한다 (Codex 지적: uid 저장 경로가 실제 코드에 없음 → `firebaseDirect.ts`의 저장·수정 함수와 `edit_logs` 기록부에 uid 인자를 추가하는 코드 변경 필요). 기존 레코드는 소급하지 않는다.
- 개인 로그인 세션: 작성자 입력칸을 `users.name`으로 자동 확정 + 읽기 전용.
- PIN 로그인 세션: 현행 수기 입력 유지 (전환 기간 하위호환, uid는 빈 값).
- **거짓 작성자 기본값 제거** (Codex 지적): `dailyOps.ts` 등에서 actor가 비었을 때 `"관리자"`·`"branch"`로 채우는 기본값을 없애고 actor를 필수 인자로 만든다. 값이 정말 없으면 `"미상"`이 아니라 호출부 컴파일 오류가 나야 한다.

### 공용기기 오염 방지
- 확정 버튼 근처 **"작성자: ○○○" 고정 노출** (숨기지 않는 크기). 남의 계정이면 현장에서 알아챈다.
- 헤더에 현재 로그인 이름 + 로그아웃 버튼 상시 표시.

### 기록 범위와 실패 처리
- 기록 시점은 현행 `edit_logs` 그대로 (확정, 확정 후 수정 — 자동저장 제외).
- `edit_logs` 기록 실패 시 현행은 `console.warn`으로 삼킨다 → **화면 토스트로 표면화**한다 ("수정이력 기록에 실패했습니다"). 본문 저장 자체는 막지 않는다 — 이력은 보조 수단이고 본문에도 modifiedBy/Uid가 남기 때문. (Codex 지적 반영, 트랜잭션 결합은 과설계로 판단해 채택 안 함)

## 8. 관리자 — 계정 관리 탭 (신설)

1. **계정 목록**: 이름/이메일/역할/**선택지점**/허용 탭 요약/허용 지점 요약/상태/가입일. `reviewedByAdmin == false`는 신규 배지.
   - **'선택지점' 컬럼은 역할 바로 오른쪽**에 둔다(v7, 사용자 지시). 값은 `workBranch` — 가입할 때 본인이 고른 지점명을 그대로 보여주며, 총괄이 허용 지점을 넓혀도 이 칸은 바뀌지 않는다. 값이 없는 옛 계정은 `-`.
2. **계정 편집**: 탭 체크박스(전체 토글), 지점 다중 선택(전체 토글), 역할(지점/지점관리자/총괄), 급여대장 허용 지점(§15), 상태(사용중/정지).
2-1. **목록에서 바로 고치기**(2026-07-28 사용자 지시): 자주 손대는 **역할·허용지점·상태**는 상세 패널을 열지 않고 행 안에서 바꾸고 즉시 저장한다.
   - 역할·상태는 드롭다운. 허용지점은 지점 칩 + `×` 제거 + `+ 추가` 드롭다운(여러 지점을 맡는 계정을 여기서 늘린다). `전체 지점` 배지를 누르면 목록형으로 바뀌어 하나씩 고를 수 있다.
   - 이 칸들은 클릭이 행 클릭(상세 열기)과 겹치지 않게 이벤트를 멈춘다. 저장 중인 행은 흐리게, 실패하면 행 아래에 사유를 남긴다(조용히 삼키지 않는다).
   - **본인 계정은 규칙상 수정 불가**이므로 드롭다운도 잠근다.
   - 역할을 바꾸면 급여대장 허용 지점이 §15.3 규칙대로 함께 정리된다.
2-2. **지점 필터**: 지점을 고르면 그 지점 소속(가입 시 선택)이거나 허용지점에 그 지점이 든 계정만 보인다. 허용지점이 '전체'인 계정은 어느 지점에서도 보인다 — 실제로 그 지점에 들어갈 수 있기 때문이다.
2-3. **접근을 실수로 끊지 않게**: `전체 지점` 배지를 누르면 빈 목록이 아니라 **전 지점이 칩으로 펼쳐진다**(접근 범위 그대로). 빈 목록으로 떨어뜨리면 지점을 다시 고르기 전까지 그 계정이 모든 지점을 잃는다. 마지막 지점 칩을 뺄 때는 "어느 지점에도 들어갈 수 없게 된다"고 한 번 묻는다.
2-4. **권한 인덱스 복구**: 지점관리자인데 인코딩본(`salaryBranchesEncoded`/`allowedBranchesEncoded`)이 없는 계정을 배너로 띄우고, 값은 그대로 둔 채 다시 저장해 인덱스만 채우는 버튼을 둔다. 이 인덱스가 없으면 **화면은 권한이 있어 보이는데 급여 문서만 조용히 막히는** 고장이 되어 원인을 찾기 어렵다.
3. **신규 가입 알림**: 대시보드 알림 영역(현행 "정산 변경 N건" 자리)에 "신규 가입 N건" → 클릭 시 계정 관리 탭. 확인 시 `reviewedByAdmin: true`.
4. 저장은 개인 관리자 세션의 `users/{uid}` 직접 update (§6 규칙 허용 범위).
5. 디자인: DESIGN.md 관리자 화면 규칙 준수 (`--branch-*` 토큰 사용 불가 주의, 인사 탭 스타일 준용).

## 9. GAS·카카오 연동 호환 (Codex P0 → v3에서 구조적으로 해소)

GAS 웹앱 URL이 공개라 모든 카카오 액션과 일부 관리자 API는 `pinHash`를 자격증명으로 요구한다 (`gasClient.ts:767`, `AdminPage.tsx:149`의 `getDailyList`, `KakaoTaxiSection`, `BusinessTaxiTab`).

- v3의 **로그인 PIN 게이트(§4)에서 받은 PIN 해시가 세션에 항상 존재**하므로, pinHash 의존 경로는 **코드 수정 없이 그대로 동작**한다. (v2의 "기능 진입 시 지연 입력 모달"은 폐기 — 불필요)
- 관리자 계정은 관리자 PIN을, 지점 계정은 지점 공통 PIN을 게이트에서 입력하므로 역할별 자격증명도 현행과 일치한다.
- 주의 (Codex 2차 P2-1): GAS의 `getDailyList`는 `adminPinHash`로 `verifyPin`만 호출하고 **반환 role을 검사하지 않는다** (`gas/Code.gs:1003-1008`). v4 게이트가 관리자 계정에 관리자 PIN을 강제하므로 실질 위험은 없지만, 구현자가 "GAS가 role을 검증한다"고 오해하지 않도록 명시해 둔다. GAS 쪽 role 검사 추가는 장기 과제에 포함.
- 장기 과제(범위 외): GAS가 Firebase ID token을 검증하도록 개편해 PIN을 완전히 제거. `ERP_ACCESS.md`의 평문 PIN 삭제(§12)와 함께 PIN 값 자체를 교체해 두는 것을 권장.

## 10. 자동 로그아웃 정책 (설계서 v1 모순 정정)

- **기존 30분 유휴 로그아웃(`AppSessionGuard`, `IDLE_LOGOUT_MS = 30분)은 그대로 유지**한다. v1의 "자동 로그아웃 없음" 표현은 오기 — 급여대장 주민번호 보호 목적의 현행 장치를 제거할 이유가 없고, 개인 로그아웃 시 Firebase `signOut()`도 함께 타도록 `logout()` 경로만 확인한다.

## 15. 역할 3단계와 급여대장 접근 권한 (v7 — 2026-07-28 사용자 지시)

### 15.1 역할

| 내부 값 | 화면 표시 | 무엇을 하는 사람인가 |
|---|---|---|
| `branch` | **지점** | 기본값. 일일마감 등 지점 업무. **급여대장은 열람도 작성도 불가** |
| `branchAdmin` | **지점관리자** | 지점 계정이 하는 일 전부 + **허용된 지점의 급여대장 열람·작성** |
| `admin` | **총괄** | 관리자 화면 + 전 지점 급여대장 열람·작성 |

- **내부 값 `admin` 은 바꾸지 않는다.** 규칙(`isPersonalAdmin`)·세션·기존 문서가 전부 이 값을 쓰고 있어, 이름을 바꾸면 배포 순간 관리자가 전원 잠긴다. 바뀌는 것은 화면에 보이는 이름뿐이다(`ROLE_LABEL`).
- **지점관리자는 관리자 화면에 들어가지 못한다**(사용자 확정). `branchAdmin` 은 지점 화면 전용 역할이며, 관리자 라우팅 판정은 지금처럼 `role === "admin"` 하나만 본다. 권한이 조용히 넘어가는 경로를 만들지 않기 위함이다.
- 역할을 바꿀 수 있는 사람은 총괄뿐이다(§6 규칙 그대로 — 본인 문서는 총괄이라도 수정 불가).

### 15.2 급여대장 접근 판정

정직원·파트타이머 급여대장 **둘 다** 같은 규칙을 쓴다.

```
총괄(admin)            → 전 지점 열람 + 작성
지점관리자(branchAdmin) → salaryBranches 에 있는 지점만 열람 + 작성
지점(branch)           → 불가
PIN 로그인             → 불가   ← v7에서 전환기 예외를 삭제
```

- **PIN 로그인 예외 삭제가 이번 개편의 핵심이다.** 지금은 `salaryAccess.ts` 와 `firestore.rules` 양쪽에 "PIN 로그인이면 무조건 통과"가 있어, 지점 공용 PIN을 아는 사람은 누구나 급여대장을 열 수 있다. 요청("비밀번호를 알고 있더라도 지점관리자 계정으로만")을 지키려면 이 예외가 없어져야 한다.
- 판정은 `src/utils/salaryAccess.ts` 한 곳에 두고 화면과 규칙이 같은 기준을 쓴다(현행 구조 유지). 함수는 `canReadSalaryBranch` 하나를 그대로 쓰되 내부 조건만 위 표대로 바꾼다 — 열람과 작성의 경계를 나누지 않는다(볼 수 있으면 쓸 수 있다).
- `firestore.rules` 의 `canReadSalary(dataKey)` 에서 `isPinAccount()` 를 빼고, 개인 계정 조건에 **역할 검사**(`role in ['admin','branchAdmin']`)를 더한다. 화면만 막고 규칙이 열려 있으면 개발자도구로 뚫리므로 둘을 함께 고쳐야 한다.
- `salaryBranches` 는 `allowedBranches` 와 **별개로** 유지한다(현행 구조 그대로). 일반 업무 지점을 넓히는 일이 급여 열람 권한을 자동으로 넓히면 안 되기 때문이다.

### 15.3 지점관리자의 급여 허용 지점

- **권한 재확인은 fail-closed다.** 급여대장 탭에 들어오면 서버 프로필을 다시 읽어 판정하고, **확인이 끝날 때까지 표를 띄우지 않는다.** 확인에 실패하면 열어 주지 않고 '다시 시도'를 제공한다 — 세션 판정으로 열어 주면 강등된 사람이 통신이 끊긴 상태에서 기기에 남은 급여 자료를 그대로 볼 수 있다(Codex 정지게이트 지적). 오프라인이어도 캐시된 프로필이 있으면 조회는 성공하므로 실제로 막히는 경우는 드물다.
- **지점관리자에게 '전체 지점'은 없다.** `salaryBranches == "all"` 은 총괄 전용이며, 지점관리자 계정에서는 화면·규칙·판정 모두 이를 통과시키지 않는다. "전체매장의 급여대장을 볼 수 있는 게 아니라 허용된 지점만"이 사용자 지시이기 때문이다(Codex P0 지적 2026-07-28).
- **급여 허용 지점은 일반 허용 지점(`allowedBranches`)을 넘지 못한다.** 화면에 들어가지도 못하는 지점의 급여를 볼 수는 없다. 계정 관리에서 저장할 때 교집합으로 정리하고, 화면 판정과 **`firestore.rules` 양쪽에서** 다시 확인한다 — 화면에만 두면 개발자도구로 뚫린다(Codex 정지게이트 지적). 규칙이 비교할 수 있도록 `allowedBranchesEncoded`(인코딩본)를 함께 저장하며, 계정 관리의 저장 경로는 역할만 바꿀 때도 `allowedBranches`를 함께 보내 이 인코딩본을 항상 갱신한다(안 보내면 방금 올린 지점관리자가 규칙에서 막힌다).
- 총괄이 계정 역할을 `branchAdmin` 으로 바꾸면 **`salaryBranches` 에 그 계정의 `workBranch` 를 자동으로 넣어 준다**(사용자 확정, 그 지점이 허용지점 안에 있을 때). 매번 따로 체크하지 않아도 자기 지점은 바로 열린다.
- 여러 지점을 맡는 사람은 총괄이 계정 편집에서 지점을 추가로 체크한다.
- 역할을 `branch` 로 되돌리면 **`salaryBranches` 를 비운다.** 권한 데이터가 남아 있다가 나중에 역할이 다시 올라갈 때 의도치 않게 되살아나는 것을 막는다(fail-closed).
- `salaryBranchesEncoded` 는 지금처럼 항상 같이 갱신한다(규칙이 인코딩된 문서 ID와 비교하므로).

### 15.4 비밀번호 게이트

- **순서는 역할 → 비밀번호다.** 역할 게이트를 통과하지 못하면 비밀번호 입력칸 자체가 뜨지 않는다. 비밀번호를 아는 지점 직원이 우회하는 경로를 없앤다.
- **파트타이머 급여대장에도 정직원과 같은 비밀번호를 건다**(사용자 확정). 관리자 설정에 이미 있는 급여대장 열람 비밀번호 **하나를 두 탭이 공유**한다 — 새 비밀번호를 만들지 않는다. 바꿀 곳이 한 곳이어야 관리가 어긋나지 않는다.
- 정직원 탭의 재잠금 장치(탭 이탈 시 잠금, 1분 이상 숨김 후 복귀 시 잠금)를 파트타이머 탭에도 그대로 적용한다.
- **급여 마감 컨트롤도 같은 잠금을 따른다.** 마감 버튼은 급여대장 표가 아니라 월말마감 헤더에 있어 게이트로 감싸이지 않는다. 그대로 두면 비밀번호를 넣지 않은 채 마감을 눌러 급여대장을 읽고 쓰는 우회가 남는다(Codex 정지게이트 지적 2026-07-28). 버튼 노출과 각 핸들러(확정·수정·취소·수정취소) 양쪽에서 역할 권한과 해제 상태를 함께 확인한다.
- 해제 상태는 두 탭이 공유한다 — 같은 비밀번호를 쓰므로 한 번 풀면 탭을 오갈 때 다시 묻지 않는다. 월말 업무를 떠나면 다시 잠긴다.

### 15.5 지점 계정이 보는 화면

- 급여대장 탭은 **목록에서 숨기지 않고, 눌렀을 때 잠김 안내를 보여준다**(사용자 확정). 기능이 사라진 것인지 권한 문제인지 지점이 바로 알 수 있어야 하기 때문이다.
- 안내 문구는 현행 "열람 권한이 없습니다" 화면을 재사용하되, **왜 막혔고 무엇을 하면 되는지**를 담는다: "급여대장은 지점관리자 계정으로만 이용할 수 있습니다. 필요하면 본사에 지점관리자 지정을 요청해 주세요."

## 16. 테스트 계획

- 신규 구글 가입 → users 기본값 생성 → 지점 선택 → **지점 공통 PIN 게이트 통과(보조 Auth 검증)** → 일일마감만 보임 → 작성 → 확정 시 작성자(name+uid) 자동 기입.
- PIN 게이트 부정 경로: 틀린 PIN 반복 → 진입 불가 + failedAttempts 증가. **지점 계정에 관리자 PIN 입력 → 거부, 관리자 계정에 지점 PIN 입력 → 거부** (역할 교차 차단). 게이트 통과 후 주 세션(개인 Auth)이 유지되는지(gateAuth signOut이 주 세션에 영향 없는지) 확인.
- 게이트 오류 정책: 틀린 PIN(`wrong-password`/`invalid-credential`) 시 GAS 폴백이 호출되지 않는지, `too-many-requests` 시 안내 문구+폴백 없음, 네트워크 차단 상태에서만 GAS 폴백 경로 진입 확인. 게이트 검증 후 브라우저 저장소에 gate 인스턴스 인증 흔적이 없는지(inMemoryPersistence) 확인.
- Legacy 세션: 구 `erp_ugd_session` 키가 남은 브라우저에서 새 버전 접속 → 재로그인 유도, split-brain 없음.
- 탭 가드: `daily.settle`만 허용된 계정에서 대시보드·근로계약서·비즈니스택시·연차관리(mainCategory 직접 진입 경로 포함)와 월말 서브탭이 사이드바에 없고 어떤 경로로도 진입 불가, 첫 화면이 일일마감정산으로 라우팅되는지 확인.
- 이메일 가입(이름 입력) + 비밀번호 재설정.
- 규칙 부정 경로: 본인 users update 거부, 기본값 아닌 create(role=admin 등) 거부, **PIN 관리자 세션의 users update 거부**.
- users 생성 실패 시나리오(오프라인) → signOut + 안내 확인.
- suspended → 다음 진입 차단. 허용 지점 1개 → 자동 진입.
- 관리자: 개인 로그인 + 관리자 PIN 게이트 → 계정 편집 반영, 신규 가입 배지, getDailyList·카카오 기능이 게이트에서 받은 pinHash로 바로 동작.
- 지점 법인택시 탭: 개인 로그인 세션의 pinHash로 바로 동작(추가 입력 없음).
- PIN 로그인 병행 회귀: 기존 지점/관리자 PIN 플로우, 작성자 수기 입력, allowedTabs "all" 동작.
- 30분 유휴 로그아웃이 개인 로그인에서 Firebase signOut까지 타는지.

### v7 권한 개편 검증

- 신규 가입: 근무지점 A를 골라 가입 → 허용 지점이 A 한 곳뿐 → 지점 선택 화면 생략 → B 지점으로 진입 시도 시 목록에 없음.
- 규칙 부정 경로: `allowedBranches: "all"` 로 users create 시도 → 거부. `workBranch` 와 다른 지점을 넣은 create → 거부. 지점 계정이 자기 `role` 을 `branchAdmin` 으로 update 시도 → 거부.
- 급여대장 역할 게이트 — **화면**: 지점 계정으로 정직원·파트타이머 탭 진입 → 잠김 안내가 뜨고 비밀번호 입력칸이 아예 없음. 지점관리자로 바꾼 뒤 재로그인 → 자기 지점만 열리고 다른 지점은 잠김. 총괄 → 전 지점 열림.
- 급여대장 역할 게이트 — **규칙**(화면 우회 차단): 지점 계정 토큰으로 `shared_data/monthly_fulltime_salary%3A...` 직접 읽기·쓰기 시도 → 거부. 지점관리자 토큰으로 허용 지점 외 문서 접근 → 거부. 같은 검증을 `monthly_parttime_salary` 키에도 수행.
- **PIN 로그인 차단 확인**: PIN 로그인 세션에서 급여대장 두 탭 모두 잠김, 규칙에서도 거부(`isPinAccount` 예외 삭제 확인).
- 파트타이머 비밀번호: 정직원과 같은 비밀번호로 열리는지, 관리자 설정에서 비밀번호를 바꾸면 두 탭에 동시 반영되는지, 탭 이탈·1분 이상 화면 숨김 후 재잠금되는지, 한 탭에서 풀면 다른 탭도 열리는지.
- 급여 마감 컨트롤: 비밀번호를 넣기 전에는 정직원 급여 탭 헤더에 마감 버튼이 보이지 않는지, 해제 후 나타나는지, 1분 이상 숨김으로 재잠금되면 다시 사라지는지. 잠긴 상태에서 마감 핸들러가 직접 호출돼도 안내 후 중단되는지(급여 데이터 요청이 나가지 않는지).
- 역할 전환 부수효과: `branch → branchAdmin` 시 `salaryBranches` 에 `workBranch` 자동 포함, `branchAdmin → branch` 시 `salaryBranches` 비워짐, `salaryBranchesEncoded` 동시 갱신.
- 계정 관리 화면: 역할 라벨이 총괄/지점관리자/지점으로 보이고, 역할 오른쪽 '선택지점' 컬럼에 가입 시 고른 지점명이 뜨는지. `workBranch` 없는 옛 계정은 `-`.
- 목록 인라인 편집: 행의 역할·상태 드롭다운과 허용지점 칩(`×`)·`+ 추가`가 즉시 저장되는지, 그 칸을 눌러도 상세 패널이 열리지 않는지, 본인 계정 행은 전부 잠기는지, 저장 실패 시 행 아래 사유가 뜨는지, `전체 지점` 배지를 누르면 목록형으로 바뀌는지.
- 지점 필터: 지점을 고르면 그 지점 소속·허용 계정만 남고 '전체' 계정도 포함되는지, 건수 표시가 맞는지, 결과가 없을 때 안내 문구가 뜨는지.
- 지점관리자 '전체' 차단: 계정 편집에서 지점관리자에게 '전체 지점' 체크가 잠기는지, 옛 문서에 `salaryBranches: "all"` 이 남은 지점관리자가 급여대장에서 막히는지(화면·규칙 모두).
- 급여 범위 상한: 허용지점 밖 지점을 급여 목록에 넣어도 저장 시 빠지는지, 남아 있더라도 판정에서 막히는지.
- 권한 강등 반영: 급여대장을 연 상태에서 총괄이 역할을 지점으로 내리면, 다른 기기의 그 화면이 (탭 재진입 시) 서버 프로필 재확인으로 잠기는지. 네트워크를 끊은 상태에서는 기존 판정이 유지되는지(정당한 작업이 끊기지 않는지). **차단 판정이 계정·지점을 바꾼 뒤에도 남지 않는지** — A 계정이 차단된 뒤 B 계정으로 바꾸고 오프라인이 되어도 B가 잠기지 않아야 한다.
- 접근 끊김 방지: `전체 지점` 배지를 누르면 전 지점이 칩으로 펼쳐지고 접근 범위가 그대로인지, 마지막 칩을 뺄 때 확인 창이 뜨는지.
- 권한 인덱스: 인코딩본이 없는 지점관리자 문서를 만들면 배너가 뜨고, 복구 버튼을 누른 뒤 급여대장이 열리는지.
- 승인 처리: 편집(지점 축소)과 함께 승인할 때 급여 허용 지점이 역할 규칙대로 정리되어 저장되는지.
- 백업 문서 권한: `part_time_profiles:{지점}` 저장 시 만들어지는 백업(`...--slot{요일}`)을 그 지점 권한을 가진 지점관리자가 읽고 쓸 수 있는지, 권한 없는 계정은 거부되는지.
- 허용지점 일괄 축소: 버튼 건수가 실제 대상과 맞는지, 미리보기의 "전체 → 지점명"이 맞는지, `workBranch` 가 비었거나 없는 지점명인 계정이 건너뛰기 목록에 뜨는지, 반영 후 목록의 허용 지점이 1개로 바뀌고 버튼이 사라지는지, 일부 실패 시 실패한 이름이 그대로 표시되는지.
- `npm run dev` 로컬 확인 후 배포 승인 대기 (AGENTS.md 규칙).
