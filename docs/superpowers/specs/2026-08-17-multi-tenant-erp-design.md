# 멀티테넌트 ERP 제품화 설계서

- 작성일: 2026-08-17
- 개정: 2026-08-17 (Codex 1~7차 리뷰 46건 반영 — §11. 6차 이후 **P0 없음**)
- 대상: 현재 사내 전용 `erp_ugd`를 **여러 회사에 판매 가능한 제품**으로 재구성
- 원본: `koreaugd/erp_ugd` (React 42,559줄 / 101파일)

## 1. 배경과 목표

UGD 본사 14개 지점이 매일 사용 중인 ERP를, 다른 회사도 가입해서 쓸 수 있는 제품으로 만든다.
기능은 현재와 동일하게 유지하되, **회사 단위로 데이터가 완전히 분리**되어야 한다.

### 확정된 결정 (사용자 선택, 2026-08-17)

| 항목 | 결정 |
|---|---|
| 확장 범위 | 여러 회사에 파는 제품 (멀티테넌트) |
| 일정 | 여유 있음 — 임시방편 없이 제대로 구성 |
| UGD 외부 파이프라인 의존 기능 | 삭제하지 않고 **회사별 on/off 스위치** |
| 회사 추가 방식 | **자유 가입** (회사 생성은 개방, 회사 합류는 초대제) |
| 접근 전략 | **A안** — 새 저장소로 복사 후 개조 |
| **UGD 이주** | **하지 않는다** (2026-08-17 결정). UGD는 기존 `erp_ugd` 를 계속 쓰고, 새 제품은 신규 가입 회사만 사용 → §6 |
| 로그인 수단 | 카카오 · 네이버 · 구글 · 이메일 |
| 휴대폰 인증 | **가입 시 1회 본인확인** (로그인 수단 아님) |

### 이 설계의 불변식

> **불변식 1.** A사 계정으로 B사 데이터를 읽거나 쓸 수 없다.
> **불변식 2.** 소속·권한·본인확인 상태는 **클라이언트가 쓸 수 없다.** 서버만 쓴다.
> **불변식 3.** 정지된 회사는 어떤 데이터도 읽거나 쓸 수 없다.

불변식 2가 핵심이다. 화면에서 자기 소속을 적어 넣을 수 있으면 나머지 방어는 전부 무의미하다.

## 2. 현재 시스템 실측 (2026-08-17 직접 확인)

설계 판단의 근거가 된 수치. 추정이 아니라 코드에서 센 값이다.

### 2.1 데이터는 이미 대부분 Firestore로 간다

| 경로 | 건수 |
|---|---|
| `gasClient.ts` → Firestore 직행 (`loadFirebaseDirect()`) | **43곳** |
| `gasClient.ts` → Apps Script (`callApi()`) | 21곳 / **19개 action** |

Apps Script 19개 action의 내역:

- **카카오T 비즈니스 택시: 13개** — `getKakaoTaxiOrders`, `registerKakaoTaxiMember`, `sendKakaoTaxiMemberTms` 등
- **지점 관리 / PIN: 6개** — `addBranch`, `deleteBranch`, `getBranchListAll`, `toggleBranchActive`, `updateBranchPin`, `verifyPin`

**결론: 회사마다 구글시트를 만들고 Apps Script를 배포하는 수동 절차는 필요 없다.**
이것이 **자유 가입이 실제로 구현 가능한 이유**다.

### 2.2 Firestore 경로 생성 위치 — 3개 파일 + 별도 경로 4곳

| 파일 | 경로 생성 호출 |
|---|---|
| `src/api/firebaseDirect.ts` | 52 |
| `src/api/userProfile.ts` | 6 |
| `src/api/firebaseAuth.ts` | 1 |
| **소계** | **59** |

> **정정(Codex 지적 1-3, 4-4).** 초판은 "이 3개 파일 59곳이면 끝난다"고 썼으나 **틀렸다.**
> 아래 경로들은 같은 파일 안에 있지만 성격이 달라 **별도로 다뤄야 한다.**

| 별도 취급 대상 | 위치 | 왜 위험한가 |
|---|---|---|
| 전체 컬렉션 스캔 폴백 | `firebaseDirect.ts:111-115` (`findDailyDocs`의 `fullColl`) | 지점 미지정 시 컬렉션 전체를 읽는다 |
| 인덱스 실패 시 전체 스캔 폴백 | `firebaseDirect.ts:231-234` | 타깃 쿼리 실패 시 조용히 전체 스캔으로 떨어진다 |
| 복원(restore) 경로 | `firebaseDirect.ts:1264-1305` (`restoreDirectFromFirebase`) | `settings`·`daily_settles` 전체를 읽고 GAS로 되쓴다 |
| 구 이관 스크립트 | `scripts/migrate-to-firebase.ts:75-105` | 최상위 경로에 직접 쓴다 (§6.5 참조) |
| 키 접두사 범위 조회 | `firebaseDirect.ts:801-821` (`getSharedDocsByKeyPrefix`) | `enc(dataKey)` 형식을 전제한 범위 조회. §3.4의 새 문서ID 형식에서는 **아무것도 못 찾는다** (조용한 빈 결과 → 관리자 집계 누락). 새 형식에 맞춰 재작성 필요 (4차 리뷰 P1) |

**전체 스캔 폴백은 지점 격리를 켜는 순간 규칙에 막혀 화면이 깨진다.** 삭제하지 않고 두면
"격리를 켰더니 지점 화면이 빈다"는 사고가 난다. 1단계에서 제거한다.
인덱스 실패 폴백은 전체 스캔 대신 **명시적 오류**로 바꾼다(조용한 광역 읽기 금지).

**★ 정정 (2026-08-17, 규칙 구현 후 실측) — "지점별 쿼리로 대체"는 불가능하다**

> 초판은 전체 스캔을 "지점별 쿼리로 대체한다"고 썼다. **그럴 수 없다.**

범위키가 **문서ID 안에** 있어서(§3.4 규약), Firestore 보안규칙은 어떤 쿼리가 안전한지
증명할 방법이 없다. `list` 는 **결과로 나올 모든 문서가 조건을 만족함이 증명 가능할 때만**
허용되는데, 문서ID를 조건으로 삼는 쿼리는 그 증명이 성립하지 않는다.
그래서 구현된 규칙은 업무 컬렉션 전부에 `allow list: if false` 를 건다.

**결과: 모든 조회가 문서ID를 아는 상태에서 문서 단위로 읽는 방식이어야 한다.**

이것은 3단계(앱 경로 이관)의 성격을 바꾼다. "경로 앞에 회사ID를 붙인다"로 끝나지 않는다.
현행 `erp_ugd` 에서 아래 호출부는 새 규칙 아래서 **전부 거부된다** — 3단계 범위에 명시적으로 넣는다.

| 위치 | 현재 방식 |
|---|---|
| `firebaseDirect.ts:73-80` | `where("master.branchName","==",…)` 복합 `or` 쿼리 |
| `firebaseDirect.ts:109-116` | `findDailyDocs` 가 위 쿼리를 주 경로로 사용 |
| `firebaseDirect.ts:805-812` | `getSharedDocsByKeyPrefix` 의 `documentId()` 범위 쿼리 |
| `firebaseDirect.ts:980` | `getCountFromServer(collection(...))` |
| `firebaseDirect.ts:1284` | `getDocs(collection(...))` |

대체 방법은 두 가지뿐이다: **①호출부가 문서ID를 열거해 개별 조회** 하거나,
**②서버가 만들어 두는 목록 문서(색인 문서)를 하나 읽는다.**
월 단위 화면은 ①로 가면 쿼리 1회가 get 31회가 되므로, 그런 화면은 ②가 맞다.
어느 쪽을 쓸지는 3단계 착수 전에 화면별로 정한다.

### 2.5 읽기 전략 확정 (2026-08-18) — §2.2 가 미뤄둔 "화면별로 정한다"의 답

§2.2 는 대체 방법을 두 가지로 제시하고 "어느 쪽을 쓸지는 착수 전에 화면별로 정한다"고
미뤘다. `erp_ugd` 의 읽기 지점 **49곳을 전수 조사**해서 확정한다.

**먼저 정정 — §2.2 의 "전부 거부된다" 표가 과대평가였다.** 구현된 규칙(계획 1·4)을
실제로 대조하니 두 항목은 애초에 막히지 않는다:

| §2.2 표 항목 | 실제 |
|---|---|
| `public_branches` 전체 조회 (`firebaseDirect.ts:580`) | **허용됨** — 규칙이 `allow get, list: if inTenant(t)` (지점명은 회사 안에서 민감정보가 아니고 범위키가 문서ID에 없다) |
| `users` 전체 조회 (`userProfile.ts:102`) | 대체물인 `members` 목록 조회가 **관리자에게 허용됨** (`allow list: if isTenantAdmin(t)`) |

**그리고 조사에서 나온 결정적 사실:** 화면 파일(`pages/**`)은 Firestore를 **직접 만지지
않는다.** SDK import 가 `firebaseDirect.ts`·`userProfile.ts`·`firebaseAuth.ts` 3개뿐이고
모든 화면은 `gasClient` 래퍼를 지난다. 실시간 리스너·페이지네이션·`orderBy`·`limit` 도
저장소 전체에 **하나도 없다**. 즉 읽기 재작성은 **화면을 건드리지 않고** 이 3개 파일
안에서 끝난다 — 화면 이관과 분리해 먼저 할 수 있다.

#### 2.5.1 실제로 막히는 것 (그리고 그것만)

| 읽기 | 현재 | 처리 |
|---|---|---|
| 지점 전체 이력 `or(where("master.branchName"))` (`:73-80, 215, 227`) | 그 지점이 지금까지 낸 **모든** 정산 | **①월 열거 + ②롤업** |
| 날짜별 전 지점 (`dailyDateQuery`, `getDailyList`) | `or(where("master.settleDate"))` | **①** — 문서ID가 정확히 `{각 지점}--{그 날짜}` |
| `shared_data` 접두사 범위 조회 (`:805-811`) | `manual_overtime:` / `labor_contracts:` | **①** — 지점당 1문서, 지점 목록은 이미 있음 |
| `edit_logs` 전체 스캔 (`:244`) | 무조건 전체 스캔, 문서ID가 타임스탬프 | **②색인 문서** (열거 불가) |
| 로그인 화면 지점 목록 (`firebaseAuth.ts:25`) | **인증 전** 읽기 | 제품에는 **로그인 지점 선택이 없다** — 개인계정 로그인 후 본인 `allowedBranches` 로 대체(계획 7) |
| 전체 스캔 폴백 3곳 · 죽은 코드 5곳 | — | **삭제**(§2.2 기존 지시) |

#### 2.5.2 ①문서ID 열거가 기본값 — 그리고 읽기 수를 **줄인다**

막히는 이력 조회는 거의 전부 **월 단위 의도**다. `MonthlySettleTab`·`OfficeWorkLogTab`·
관리자 루프가 `month` 인자를 넘기지만 **서버 필터가 아니라 클라이언트 필터**라서
(현행 코드 주석이 명시) 실제로는 전체 이력을 읽고 나서 버린다.
`daily_settles` 문서ID는 `enc(지점)--YYYY-MM-DD` 가 **보장되므로**(`normalize-daily-doc-ids.mjs`
가 성립시킨 규약), **한 달 = 열거 가능한 31개 문서ID**다.

그래서 ①은 **이력이 쌓인 지점에서 이득**이다. 2년치 이력이 있는 지점은 쿼리 1회가
730문서를 읽었는데, 열거는 31회다. §2.2 가 "쿼리 1회가 get 31회가 되므로 ②가 맞다"고
쓴 것은 **분모를 잘못 봤다** — 비교 대상은 1이 아니라 730이다. 이 전환은 코드 주석에
기록된 **무료 등급 하루 5만 읽기 소진 사고**(전 지점 빈 화면)가 났던 그 경우를
우회가 아니라 근본 해소한다.

**단, 모든 경우에 싸지는 것은 아니다** (2026-08-18 리뷰 지적, 타당). Firestore 는
**없는 문서를 읽어도 읽기 1회로 과금**한다. 그 달에 3일만 제출한 지점은 3회가 아니라
31회가 된다. 신규 지점·이력이 얇은 지점에서는 열거가 더 비싸다.
**열거를 택한 이유는 평균 비용이 아니라 규칙이 목록 조회를 닫았기 때문**이고,
비용 절감은 이력이 쌓인 지점에서 따라오는 부수 효과로만 주장한다.

이미 이 형태인 `firebaseGetDailyMastersByDates`(`:202`, 날짜 배열 → `Promise.all` get)가
모범 사례이며, 재작성은 전부 이 함수의 모양으로 수렴한다.

#### 2.5.3 ②롤업 문서는 `shared_data` 안에 `sys` 등급으로 둔다

여러 달·여러 지점을 한꺼번에 보는 읽기는 ①로도 과하다(전 지점 전 기간 매출 차트).
그것만 서버가 미리 만들어 둔다.

**결정: 새 컬렉션을 만들지 않고 `shared_data` 에 세 번째 등급 `sys` 를 추가한다.**

| 항목 | 값 |
|---|---|
| 문서ID | `{enc(지점명)}--sys--{종류}_{YYYY-MM}` |
| 읽기 | 기존 `scopeAllowed` 그대로 — **지점 격리가 자동으로 걸린다** |
| 쓰기 | **클라이언트 전면 금지** (등급이 `sys` 면 무조건 거부) |
| 규칙 변경량 | `sharedIdValid` 에 `sys` 허용 1줄 + 쓰기 거부 1줄 |

이 선택의 이유: 새 컬렉션은 새 `match` 블록·새 판정 함수·새 테스트 축을 부른다.
`sys` 등급은 **이미 검증된 범위/등급 기계장치를 그대로 재사용**하고, 지점별 롤업이
공짜로 격리된다.

**모든 롤업을 지점 범위로 둔다** — `_all`·`_admin` 롤업은 만들지 않는다.
회사 전체 집계 문서 하나에 전 지점이 쓰면 **한 문서 쓰기 경쟁**(Firestore 문서당
지속 쓰기 ~1회/초)이 생기고, 관리자 화면은 어차피 지점 목록을 루프하므로
지점당 1문서 읽기로 같은 결과가 나온다.

**★ 정정 (같은 날, 위 문단을 쓴 직후 재검산) — 롤업이 필요한 읽기는 4개가 아니라 2개다.**

위 표에 4개를 적었는데, **화면별로 실제 기간을 따져보니 대부분 ①로 충분하다.**
"전체 이력을 읽는다"는 사실에 놀라서 ②로 보냈지만, **그 화면이 보여주는 기간**은 한 달이다.

| 읽기 | 실제 필요 기간 | 판정 |
|---|---|---|
| 캘린더 `completedDates` | 캘린더가 표시하는 **한 달** | **①** 31 get |
| 미제출일 카운트 · 지점 대시보드 | 당월 | **①** ≤31 get (이미 `getDailyMastersByDates` 가 이 형태) |
| `getDailyList(날짜)` | 하루 × 전 지점 | **①** 지점수만큼 get |
| `getAttendanceLog` (근태) | 호출자 3곳 전부 **월 단위 화면** | **①** 31 마스터 + 31 상세 = 62 (현행 ~1,460 → **23배 감소**) |
| 전일 현금 잔액 (`getDailyFormBootstrap`) | 직전 1~2일 | **①** 1~2 get |
| **`AdminSalesOverviewSection`** | **전 지점 × 전 기간** 차트 | **②** — ①이면 14×12개월×31=5,208 get, 롤업이면 14×12=168 |
| **`edit_logs`** | 문서ID가 타임스탬프라 **열거 자체가 불가** | **②** |

| 롤업 | 죽는 읽기 |
|---|---|
| `{B}--sys--sales_{YYYY-MM}` (일별 매출·현금 요약) | `AdminSalesOverviewSection` 전 지점 전 기간 이력 |
| `{B}--sys--editlog_{YYYY-MM}` (변경이력 색인) | `edit_logs` 전체 스캔 2곳. 상세는 `edit_logs/{id}` 로 필요할 때만 |

색인 문서 + 필요시 상세 문서는 **저장소에 이미 있는 검증된 패턴**이다
(`AdminReportPackTab` 의 `pnl_report_pack_index` → 월별 문서).

**이 둘은 모두 관리자 분석 화면이고, 제품이 처음 동작하는 데 필요하지 않다.**
그래서 롤업은 읽기 계층과 **분리된 뒤 계획**으로 미룬다 — 아래 §2.5.5 참조.

#### 2.5.4 롤업은 **트리거**로 유지해야 한다 (호출형 함수로는 불가) — 뒤 계획

구현된 규칙에서 `daily_settles` 는 **클라이언트 쓰기가 허용**된다(정산 제출 경로).
그러므로 "저장 후 롤업 갱신 함수를 호출한다"는 방식은 **우회 가능**하다 — 클라이언트가
문서만 쓰고 호출을 생략하면 롤업이 조용히 어긋난다.
**Firestore 트리거(`onDocumentWritten`)만이 우회 불가능한 유지 수단이다.**
이 저장소의 기존 함수는 전부 `onCall` 이므로 트리거는 신규 역량이다(에뮬레이터 배선 포함).

**그리고 트리거는 실패할 수 있다.** 한 번 놓친 호출은 영구히 어긋난 숫자로 남고
고칠 방법이 없다 — 이 조직이 실제로 겪은 사고 유형이다(03↔04↔05 3원천 금액 불일치).
그래서 롤업 계획에는 **`rebuildRollups` 복구용 호출형 함수를 반드시 포함**한다.
롤업 갱신은 **멱등(idempotent)** 이어야 하고, 재작성이 원본 문서에서 전량 재계산으로
성립해야 한다(누적 가산 금지).

**★ 왜 지금 하지 않는가 (2026-08-18 실측).** `erp_saas` 에는 **`src/` 가 없다** — 앱 코드가
한 줄도 없다. 롤업 트리거는 `daily_settles` 문서의 **필드 구조**(매출·현금 항목명)에서
값을 꺼내야 하는데, 그 구조를 만드는 코드가 저장소에 없으므로 지금 쓰면 **필드명을
추측**하게 된다. 추측한 스키마 위에 트리거와 테스트를 쌓으면, 앱을 이관할 때 둘 다 다시
쓴다. 읽기 계층 이관이 그 구조를 저장소 안으로 들여온 **뒤에** 롤업을 만든다.

#### 2.5.5 이 결정이 계획 순서를 바꾼다

읽기 계층은 화면의 **선행 조건**이다. 그리고 §2.5 의 조사 결과 덕분에 **화면 없이 이관할
수 있다** — Firestore 접근이 `src/api/` 3개 파일에 모여 있고 화면은 `gasClient` 계약만
보므로, 그 계약을 유지한 채 데이터 계층만 먼저 옮기고 에뮬레이터로 검증할 수 있다.

| | 종전 | 확정 |
|---|---|---|
| 계획 5 | 화면·앱 경로 이관 | **데이터 접근 계층(`src/api/`) 이관** — 회사ID 경로 + 문서ID 규약 + ①열거 재작성 + 폴백·죽은코드 제거 |
| 계획 6 | 인증 3종 | 화면 이관 (계획 5의 계약 위에) |
| 계획 7 | — | **`sys` 롤업 + 트리거 + `rebuildRollups`** (읽기 2개 대상, 실제 문서 구조 확보 후) |
| 계획 8 | — | 인증 3종(카카오·네이버·문자) + 로그인 지점 선택 폐지 |

**계획 5 에서 ②가 필요한 읽기 2개는 fail-closed 로 막는다** — 조용히 틀린 값을 주지 않고
명시적 오류를 던지고, 계획 7 이 닫는다. 이 프로젝트 원칙(조용한 광역 읽기·조용한 빈 결과
금지)의 직접 적용이다.

### 3.2 데이터 구조


**`users/{uid}`를 "안내판"으로 축소한 이유 (Codex 지적 1-1).**
초판은 이 문서에 이름·전화번호·권한·담당지점을 전부 담았다. 그런데 이 컬렉션은
**회사 밖에 있다.** 지금 코드(`userProfile.ts:100`)는 관리자가 `users` 전체를 읽는다.
그대로 두면 **A사 관리자가 B사 직원의 이름·이메일·전화번호를 열람**하게 된다.

그래서 최상위에는 **소속만** 남긴다. 사람의 실제 정보는 `tenants/{t}/members/{uid}`에 두어
회사 경계 안으로 넣는다. 관리자의 직원 목록 조회도 `members`를 읽으므로 자기 회사만 보인다.

**`signup_verifications`가 필요한 이유 (2차 리뷰 B-1).**
`users`를 축소하면서 구멍이 하나 생겼다. **회사를 만들기 전에는 소속이 없으므로 `members` 문서도 없다.**
그런데 `createTenant`는 "전화 본인확인이 끝났는지"를 확인해야 한다 — 확인할 데이터를 둘 곳이 없었다.
그래서 가입 진행 중인 사람의 본인확인 결과만 담는 별도 보관소를 둔다.
**클라이언트는 읽지도 쓰지도 못하며**, 서버만 기록하고 서버만 확인한다.
회사 소속이 확정되면 서버가 전화번호를 `members`로 옮기고 이 문서는 정리한다.

**`public_branches`는 더 이상 공개가 아니다.** 현재 규칙은 `allow read: if true`(로그인 전
지점 선택 화면 때문)이다. 새 제품은 개인 계정으로 먼저 로그인한 뒤 소속이 정해지므로 공개일 이유가 없다.
회사 아래로 옮기면서 `if true`를 제거한다. **이걸 놓치면 로그인 화면이 조용히 빈 목록을 받는다.**

### 3.3 보안 규칙 — 클라이언트 쓰기 금지 구역

**불변식 2를 규칙으로 못 박는다.** 아래 네 컬렉션은 클라이언트가 **읽기만** 하거나 아예 못 본다.

| 컬렉션 | 클라이언트 읽기 | 클라이언트 쓰기 |
|---|---|---|
| `users/{uid}` | **본인 문서만** (`request.auth.uid == uid`). 목록 조회 불가 | **금지** |
| `signup_verifications/{uid}` | **금지** | **금지** |
| `tenants/{t}` (메타) | **활성 회사의** 소속 구성원, 또는 최고관리자 | **금지** |
| `tenants/{t}/members/{uid}` | 본인 + 같은 회사 관리자 | **금지** — 권한 변경·표시명 수정은 `updateMember` 경유 |
| `tenants/{t}/invites/{id}` | **금지** — 관리자 목록 조회는 `listInvites` 경유 | **금지** |
| `platform_admins/{uid}` | **금지** | **금지** |

전부 서버 함수(Admin SDK)만 쓴다. 이 한 줄이 Codex 지적 **2-1, 2-3, 3-1, 3-2, 3-3, 3-4**를 동시에 닫는다.

> **읽기 금지 컬렉션에는 반드시 대응하는 서버 함수가 있어야 한다 (2차 리뷰 B-5).**
> `invites`를 클라이언트가 못 읽게 막아놓고 관리자 화면에 초대 목록을 띄우려면 통로가 필요하다.
> `members`도 마찬가지로 쓰기를 막았으니 권한 변경 통로가 필요하다. §3.5에 둘 다 넣었다.
> **막은 것과 뚫어준 것이 짝이 맞는지**가 이 표를 볼 때의 점검 기준이다.

**회사 메타 읽기에도 "활성" 조건이 붙는 이유 (3차 리뷰 P0)**

> 개정 2판은 메타 읽기를 "소속 구성원 또는 최고관리자"로만 썼다. 그런데 §1 불변식 3은
> **"정지된 회사는 어떤 데이터도 읽거나 쓸 수 없다"**이다. 정지된 회사의 구성원이 회사 문서를
> 계속 읽을 수 있으면 **설계서가 자기 불변식을 스스로 어긴다.**

- 메타 읽기 = `tenantActive(t)`를 통과한 소속 구성원
- **최고관리자는 예외** — 정지시킨 회사를 봐야 하므로 활성 조건을 적용하지 않는다
- 정지된 회사의 구성원에게는 **`getAccountState` 서버 함수**가 "왜 막혔는지"만 알려준다
  (회사 데이터는 한 글자도 주지 않고 상태와 안내 문구만 반환)

정지 안내 통로를 안 만들면 그 회사 직원들은 **이유 없이 빈 화면**을 보게 된다.

> **왜 이게 결정적인가 (Codex 지적 2-1).** 초판은 "`tenantId`를 수정 못 하게 잠근다"고만 썼다.
> 그런데 **문서를 처음 만들 때** 남의 회사ID를 적어 넣으면 잠금은 아무 역할도 못 한다.
> 공격자가 가입 직후 `users/{자기uid}`를 `{tenantId: "피해회사", status: "active"}`로 생성하면
> `inTenant(피해회사)`가 그걸 그대로 믿는다. **생성 자체를 클라이언트에게서 뺏는 것이 유일한 해법이다.**

### 3.4 접근 판정

```
myTenant()      = get(/users/{uid}).data.tenantId
tenantActive(t) = get(/tenants/{t}).data.status == 'active'
member(t)       = get(/tenants/{t}/members/{uid})
inTenant(t)     = signedIn()
                  && myTenant() == t
                  && tenantActive(t)              ★ Codex 지적 2-2
                  && member(t).status == 'active'
```

> **`tenantActive(t)`가 빠지면 회사 정지가 아무것도 막지 않는다**(Codex 지적 2-2).
> 정지된 회사의 직원이 여전히 `myTenant() == t`를 만족하므로 급여·마감을 계속 쓸 수 있다.

**지점 격리 (`branchIsolation == true`일 때)**

컬렉션마다 지점을 꺼내는 방법이 다르므로(§2.3) **규칙도 컬렉션마다 따로 쓴다**(Codex 지적 1-2).

**문서ID 규약 (신규) — 모든 데이터에 하나의 형식만 쓴다**

> **문서ID는 `<범위키>` 로 시작한다. 뒤에 더 붙일 것이 있을 때만 `--` 로 잇는다.**
> (`enc(지점명)` 하나로 끝나는 문서도 규약을 지키는 것이다 — 3차 리뷰 지적 2)
>
> **단, `shared_data`와 그 백업은 두 번째 칸에 `<등급>`이 반드시 온다** — 이 컬렉션에만
> 급여·개인정보가 섞여 들어오기 때문이다. 예외는 이 하나뿐이며 아래 급여 항에서 정의한다.
> (5차 리뷰 P0: 개정 4판은 같은 절 안에 2칸 표와 3칸 규약이 함께 있어, 위 표만 보고
> 구현하면 등급 칸이 통째로 빠질 수 있었다)

| 범위키 | 뜻 | 읽기 | 쓰기 |
|---|---|---|---|
| `enc(지점명)` | 그 지점의 데이터 | 담당 지점 구성원 + 회사 관리자 | 동일 |
| `_all` | 회사 전 구성원 공용 | 소속 구성원 전원 | **회사 관리자만** |
| `_admin` | 회사 관리자 전용 | 회사 관리자만 | 회사 관리자만 |

`_all`과 `_admin`은 지점명으로 쓸 수 없게 예약한다.

```
branchKeyOf(id) = id.split('--')[0]
```

`split()`은 Firestore 규칙에 실제로 존재한다(`rules.String.split`). 다만 **이 한 줄로 끝나지 않는다.**
실제 허용 판정은 여기에 `branchIsolation` 여부 · 회사 활성 · 구성원 상태 · 범위키 종류를
조합해야 한다. (개정 2판이 "규칙 한 줄로 끝난다"고 쓴 것은 과장이었다 — 3차 리뷰 지적 1)

| 컬렉션 | 문서ID | 범위 판정 |
|---|---|---|
| `daily_settles` | `enc(지점명)--YYYY-MM-DD` | `branchKeyOf(id)` |
| `staff_rosters` / `branch_own_rosters` / `settings` | `enc(지점명)` (접미사 없음) | `branchKeyOf(id)` |
| `shared_data` | **`<범위키>--<등급>--<키>`** — 등급 칸 **필수** (아래 급여 항) | `scopeOf(id)` + `gradeOf(id)` |
| `shared_data_backups` | 위와 동일 + `--slotN` | 동일 |
| `edit_logs` | `enc(지점명)--<자동ID>` | `branchKeyOf(id)` |
| `public_branches` | `enc(지점명)` | 회사 공용 — 소속 구성원이면 읽기 허용 |

**`_all`은 권한 목록에 넣지 않는다 (3차 리뷰 지적 3).**
`_all`을 `allowedBranchesEncoded`에 넣어 처리하려 하면 두 가지가 다 잘못된다 — 안 넣으면
공용 데이터가 전부 막히고, 넣으면 그 사람이 `_all` 키의 **모든** 문서를 쓸 수 있게 된다.
`_all`·`_admin`은 **범위키 종류로 분기**해 판정하고, `allowedBranchesEncoded`는
지점 범위키에만 쓴다.

**급여·주민등록번호처럼 민감한 데이터는 `_all`에 두지 않는다.** 지점 범위키로 쪼개거나
`_admin`을 쓴다. `_all`은 "그 회사 직원 누가 봐도 되는 것"만 담는다.

**★ 급여는 지점 권한과 별개의 축이다 (4차 리뷰 P0-1)**

> 지금 규칙에는 급여 전용 판정(`isSalaryKey` / `salaryBranchOf` / `canReadSalary`,
> `firestore.rules:120-199`)이 따로 있다. **담당 지점이라고 해서 급여를 볼 수 있는 게 아니다.**
> 개정 3판은 범위키만 정의하고 이 두 번째 축을 어떻게 물려받을지 안 적었다. 그대로 구현하면
> **지점 담당자 전원이 그 지점 급여·주민등록번호·계좌를 보게 된다.**

`shared_data`(및 그 백업)는 문서ID에 **등급**을 한 칸 더 넣는다.

```
shared_data 문서ID = <범위키>--<등급>--<나머지>
등급: gen (일반)  |  salary (급여·개인정보)

scopeOf(id) = id.split('--')[0]
gradeOf(id) = id.split('--')[1]
```

**`shared_data` 접근 판정 — 범위와 등급을 한 식으로 (6차 리뷰 P1-1·2·3)**

> 개정 5판은 범위키 표와 등급 표를 **따로** 적었다. 그러면 규칙대로 읽었을 때
> `_all--gen--<키>`는 **아무도 못 읽는다**(`_all`은 권한 목록에 없으므로).
> 관리자가 지점 문서를 볼 근거도, `_admin--salary--`의 판정도 빠져 있었다.
> 두 축을 **하나의 판정식**으로 합친다.

```
scopeOf(id) = id.split('--')[0]      gradeOf(id) = id.split('--')[1]
관리자      = member.role == 'admin'

① 범위 통과 (읽기/쓰기 구분)
   scope == '_admin'  →  관리자
   scope == '_all'    →  읽기: 소속 구성원 전원 / 쓰기: 관리자
   그 외(지점 범위키) →  관리자 이거나,
                         branchIsolation 이 켜져 있으면 scope ∈ allowedBranchesEncoded
                         (꺼져 있으면 소속 구성원 전원)

② 등급 통과
   grade == 'gen'     →  통과
   grade == 'salary'  →  scope == '_all'  →  ★ 무조건 거부 (읽기·쓰기·수정·삭제 전부)
                         그 외            →  scope ∈ salaryBranchesEncoded

접근 허용 = ① 그리고 ②
```

**여기서 반드시 지킬 네 가지**

1. **관리자는 ①만 통과한다. ②는 통과시키지 않는다.**
   회사 관리자라고 자동으로 급여를 보는 게 아니다. `_admin--salary--<키>`를 보려면
   관리자이면서 `salaryBranchesEncoded`에 `_admin`이 **명시적으로** 들어 있어야 한다.
2. **급여 등급은 `branchIsolation`과 무관하게 항상 적용된다** (6차 리뷰 P1-6).
   격리 스위치는 ①에만 영향을 준다. UGD처럼 `branchIsolation=false`인 회사에서도
   급여 권한 없는 사람은 급여를 못 본다 — 지금 UGD 동작과 같다.
3. **`_all`과 `_admin`은 `allowedBranchesEncoded`에 넣지 않는다.** ①의 분기로 판정한다.
4. **`_all--salary--` 는 존재 자체를 인정하지 않는다** (7차 리뷰 P1).
   개정 6판은 "생성 금지"라고만 썼는데, 그러면 **이미 만들어진 문서를 읽는 것은 안 막힌다.**
   `_all` 범위 읽기는 ①에서 전원 통과이므로, 이주 실수나 서버 버그로 그런 문서가 한 번
   생기면 **회사 전 직원이 급여를 보게 된다.** 그래서 ②에서 **동작 종류와 무관하게** 거부한다.
   `_all`을 `salaryBranchesEncoded`에 넣어도 이 분기가 먼저 걸린다.

**그 밖에**

- 기존 급여 키(`monthly_fulltime_salary:지점명:YYYY-MM` 형식)는 **이주 시 새 형식으로 변환**하고,
  변환 전후 대조표를 §6.3 게이트에 포함한다 (§6.3 "급여 키 변환 대조" 행)
- `salaryBranchesEncoded` 역시 **인코딩본**이다 (메모리 `erp_salary_branch_isolation` 관례 계승)

`edit_logs`는 현재 자동 생성 ID라 지점이 필드에만 있다. 필드 기반 규칙은 목록 조회 시
클라이언트가 지점 필터를 반드시 붙여야만 통과하는데, 한 곳이라도 빠뜨리면 조용히 실패하거나
광역 노출된다. **새 제품에서는 `edit_logs`도 접두사 ID를 쓴다.**

**★ 규칙은 디코딩하지 않는다 — 인코딩된 채로 비교한다 (2차 리뷰 P0-4)**

> 초판 개정본은 "`--` 앞부분을 **디코드**해서 비교한다"고 썼는데 **실행 불가능하다.**
> **Firestore 보안 규칙에는 URL 디코딩 기능이 없다.** 같은 사실이 메모리
> `erp_salary_branch_isolation`에도 이미 기록돼 있었다(급여 권한을 인코딩본으로 별도 저장한 이유).

그래서 **비교를 인코딩된 쪽에서 한다.**

- `members` 문서에 `allowedBranchesEncoded[]`(= `enc(지점명)` 목록)를 **함께** 저장한다
- 규칙은 `branchKeyOf(id) in member.allowedBranchesEncoded` 만 확인한다 — 디코딩 없음
- `allowedBranches[]`(원문)와 `allowedBranchesEncoded[]`는 **서버가 항상 함께 기록**한다.
  둘 중 하나만 바뀌면 권한이 어긋나므로, 클라이언트 쓰기를 막은 것(§3.3)이 여기서도 안전장치가 된다

**지점명 제약**: 지점명에 `--`가 들어가면 접두사 분리가 깨진다.
회사 생성·지점 추가 시 **`--` · `_all` · `_admin` 세 가지를 모두** 지점명으로 쓸 수 없게 검증한다.
(개정 3판은 본문엔 `_admin`도 예약이라 써놓고 검증 문장과 테스트에는 `_all`만 넣어
**절반만 반영**된 상태였다 — 4차 리뷰 P0-2)

**Collection group 쿼리 금지 (Codex 지적 2-4)**

`collectionGroup("shared_data")` 같은 조회는 **회사 경계를 넘어 전 테넌트를 훑는다.**
규칙에 collection group 허용을 넣지 않으며, §8.1에 **거부 테스트를 명시적으로 포함**한다.
향후 전체 통계가 필요하면 별도 집계 문서를 서버가 만들어 제공한다.

**포괄 규칙 금지**

`match /tenants/{t}/{document=**}` 같은 규칙을 쓰지 않는다. 현재 규칙에는 급여 키 판정
(`isSalaryKey`, `salaryBranchOf`, `canReadSalary`)처럼 세밀한 로직이 있는데, 포괄 규칙을 얹으면
그 제한이 무력화된다. **컬렉션별 명시 규칙만 쓴다.**

**최고관리자 (Codex 지적 2-3)**

`platform_admins/{uid}`는 **클라이언트가 만들 수 없다.** Firebase 콘솔 또는 서버로만 생성한다.
`exists(/platform_admins/{uid})`만 확인하는 규칙을 쓰면서 생성을 열어두면 **아무나 최고관리자가 된다.**

권한 범위는 다음 둘뿐이며, **하위 컬렉션은 전부 차단**한다.

- `tenants/{t}` 메타 문서 **읽기** — 규칙에 이 예외를 명시한다(§3.3 표. 2차 리뷰 B-4:
  "메타는 소속 구성원만"으로만 쓰면 최고관리자 화면이 자기 권한으로 아무것도 못 읽는다)
- 회사 **정지·해제** — 직접 쓰지 않고 `setTenantStatus` 서버 함수를 통한다

지원이 필요한 경우는 향후 "회사 관리자가 기간을 정해 허용하는" 방식으로 별도 설계한다.

### 3.5 서버 함수 목록

| 함수 | 하는 일 |
|---|---|
| `authExchange` | 카카오·네이버 토큰 검증 → Firebase 커스텀 토큰 발급 |
| `sendPhoneCode` / `verifyPhoneCode` | 문자 발송·확인. 성공 시 서버가 `signup_verifications/{uid}.phoneVerifiedAt` 기록 |
| `createTenant` | 회사 생성. **트랜잭션**: `users/{uid}` 부재 + 전화인증 완료 확인 |
| `createInvite` | 초대 생성. 원문 토큰은 1회 반환, **저장은 해시만**. `allowedBranches`·`allowedBranchesEncoded` **둘 다 기록** |
| `redeemInvite` | 초대 소비. **트랜잭션**: 단일 사용 + 이메일 검증·대조 + 만료 + **`users/{uid}` 부재**. 초대의 두 목록을 `members`로 **그대로 복사** |
| `listInvites` | 회사 관리자용 초대 목록 (`tokenHash` 제외) |
| `updateMember` | 구성원 권한·표시명 변경. `allowedBranches`와 `allowedBranchesEncoded`를 **함께** 기록 |
| `setTenantStatus` | 최고관리자의 회사 정지·해제 |
| `getAccountState` | 로그인했는데 화면을 못 쓰는 사람에게 **이유만** 알려줌 (회사 정지·구성원 정지·소속 없음). 회사 데이터는 반환하지 않음 |

**초대장에도 인코딩본을 넣는 이유 (3차 리뷰 지적 4).**
`allowedBranchesEncoded`를 `members`에만 두면, 초대를 소비하는 순간 **누가 인코딩본을 만드는지가
불명확**해진다. 초대 생성 시점에 이미 담당 지점이 정해지므로 **그때 둘 다 만들어 두고**,
소비 시에는 복사만 한다. 변환 지점이 한 곳(`createInvite`)으로 고정되어 어긋날 여지가 없다.

카카오T 프록시는 기존 Apps Script를 그대로 쓴다(회사 1벌).

### 3.5.1 계획 4 반영 개정 (2026-08-17)

위 표는 v1 설계 시점의 것이다. 계획 2~4를 구현하면서 **"막은 것에는 뚫어준 통로가 있어야 한다"**(§3.3)
원칙에 따라 서버 함수 4개가 추가로 필요해졌다. 실제 구현된 전체 목록:

| 함수 | 관문 | 비고 |
|---|---|---|
| `getAccountState` | 로그인 | 막힌 이유만 반환 |
| `createTenant` | 로그인 + 전화인증 | |
| `createInvite` / `listInvites` / `redeemInvite` | 회사 관리자 / 관리자 / 초대받은 본인 | |
| **`revokeInvite`** | 회사 관리자 | **신설.** 7일짜리 관리자 초대를 취소할 수단이 없었다 |
| `updateMember` | 회사 관리자 | 마지막 관리자 강등 불가 |
| **`removeMember`** | 회사 관리자 | **신설.** `users`+`members`+해당 이메일 미소비 초대를 원자 제거 |
| **`createBranch`** / **`setBranchActive`** | 회사 관리자 | **신설.** `public_branches` 클라이언트 쓰기를 폐쇄하고 서버로 이전 |
| `setTenantStatus` | **최고관리자**(`platform_admins`) | 회사 정지·해제 |

**개정 사항 4가지 — 위 §3.2~§3.4의 서술과 다른 부분:**

1. **`_admin` 급여 권한은 부여할 수 없다.** §3.4 "지킬 것 1번"은 `_admin` 을
   `salaryBranchesEncoded` 에 명시 부여하면 통과한다고 썼는데, 구현된 `assertValidBranchNames` 가
   `_admin` 을 예약어로 거부한다. 따라서 **`_admin--salary--*` 문서는 현재 아무도 읽을 수 없다**
   (fail-closed). 의도적 범위 제한이며, 필요해지면 별도 부여 경로를 만든다.
2. **지점 비활성(`isActive:false`)은 데이터 접근을 끊지 않는다.** 이미 그 지점을 담당하는 사람은
   기존·신규 데이터를 계속 읽고 쓴다. 비활성은 **새 부여(초대·권한변경)만** 막는다.
   보안규칙은 `isActive` 를 보지 않는다 — 규칙 판정은 `allowedBranchesEncoded` 멤버십만 본다.
   **운영자에게 이 차이를 화면에서 반드시 알려야 한다**("새 부여만 막힙니다, 기존 담당자 접근은 유지").
3. **지점 삭제 수단은 없다.** 삭제하면 `members`·`invites`·기존 데이터 문서에 굳어 있는 범위키를
   원자적으로 스윕해야 하고, 같은 이름의 지점을 다시 만들면 옛 보유자가 접근을 되찾는다.
   v1은 비활성만 지원한다 — **지점명은 사실상 영구적이므로 생성 화면에서 경고할 것.**
4. **구성원 정지(`members.status`) 변경 수단이 없다.** 규칙(`inTenant`)과 `getAccountState` 는
   `status !== 'active'` 를 판정하는데 그 값을 바꿀 서버 함수가 없어, `member_suspended` 상태는
   현재 도달 불가다. §3.3 의 짝 맞추기 원칙이 이 항목에서만 미완이다.
   **추가할 때 반드시 `assertNotLastAdmin` 을 경유할 것** — 유일한 관리자를 정지시키면 강등과
   똑같이 회사가 영구 잠긴다(클라이언트는 소속·권한 문서를 쓸 수 없으므로). 현재 그 가드는
   강등·제거 경로에만 배선돼 있다.

**`redeemInvite`도 `users/{uid}` 부재를 확인해야 한다 (2차 리뷰 P0-3).**
초판 개정본은 이 확인을 `createTenant`에만 넣었다. 그러면 **이미 A사에 속한 사람이 B사 초대를
받아 삼킬 수 있고**, 그 순간 그 사람의 소속이 어디인지가 모호해진다. 두 경로 모두 같은 확인을 한다.

> **알려진 제약**: 한 계정은 한 회사에만 속한다. 회계사처럼 여러 회사를 보는 사람은 **계정을 나눠야** 한다.
> 소속을 하나로 고정하는 것이 §3.4의 모든 판정을 단순하게 만들기 때문이며, 다중 소속은
> `users/{uid}`를 목록형으로 바꾸는 별도 설계가 필요하다. v1 범위에서 제외한다.

## 4. 인증과 가입

### 4.1 로그인 수단

| 수단 | 구현 |
|---|---|
| 구글 | Firebase 기본 제공 |
| 이메일+비밀번호 | Firebase 기본 제공 |
| **카카오** | Firebase 미지원 → `authExchange`로 커스텀 토큰 발급 |
| **네이버** | Firebase 미지원 → `authExchange`로 커스텀 토큰 발급 |

구글·이메일을 남기는 이유: **UGD 기존 사용자가 구글로 로그인 중이다.** 빼면 이주 시 전원 재가입해야 한다.

**필요한 외부 절차 (일정에 반영):**
카카오 개발자 앱 등록 + 이메일·전화번호 수집 시 **비즈니스 앱 전환·검수** /
네이버 개발자 앱 등록 + **검수 승인(수일)** / 개인정보처리방침·이용약관·수집동의 화면

### 4.2 휴대폰 본인확인

가입 시 1회. 로그인 수단이 아니다.

- 문자 발송은 **국내 업체(솔라피 / NHN Cloud 등)** 우선 검토 (단가는 구축 시점 비교)
- 인증된 번호는 직원 연락처로 재사용
- **`phoneVerifiedAt`은 서버만 기록한다**(Codex 지적 3-3). 클라이언트가 쓸 수 있으면
  스크립트가 스스로 인증 표시를 켜고 회사를 대량 생성한다 — 남용 방어가 통째로 무의미해진다
- 발송 요청에 속도 제한 (문자 폭탄·비용 폭주 방지)

**저장 위치 (2차 리뷰 P0-2)**

```
가입 직후 (소속 없음)   →  signup_verifications/{uid}.phoneVerifiedAt   ← 서버 전용
회사 소속 확정 후        →  tenants/{t}/members/{uid}.phoneVerifiedAt
```

회사를 만들기 전에는 `members` 문서가 아직 없으므로, `createTenant`가 확인할 값을 둘 곳이 없었다.
가입 중인 사람용 보관소(§3.2)를 따로 둔다. 소속이 확정되면 서버가 번호를 `members`로 옮긴다.
**두 위치 모두 클라이언트는 쓸 수 없다.**

### 4.3 가입 경로는 두 개뿐

```
① 회사를 새로 만든다 (대표·관리자)
   가입 → 휴대폰 본인확인 → 회사명·지점목록 입력
   → createTenant 호출 → 회사 생성 + 본인이 관리자 → 즉시 사용

② 기존 회사에 합류한다 (지점 직원)
   회사 관리자가 초대 생성 (이메일 + 담당지점 + 권한) → 초대 링크 전달
   → 받은 사람이 로그인 후 redeemInvite → 그 회사 소속으로 확정
```

**초대 없이는 어떤 회사에도 들어갈 수 없다.**
가입 화면에서 회사를 목록으로 고르게 하면 "자유 가입"과 "회사 격리"가 정면충돌한다.
**여는 것은 회사를 만드는 문이고, 회사에 들어가는 문은 그 회사 관리자만 연다.**

### 4.4 초대장 설계 (Codex 지적 3-1, 3-2)

| 요건 | 내용 |
|---|---|
| 추측 불가 | 무작위 토큰. **저장은 해시만**(`tokenHash`), 원문은 생성 시 1회만 반환 |
| 이메일 소유 확인 | 소비 시 **로그인 계정의 이메일이 검증된 상태**이고 초대 대상과 일치해야 함 |
| 만료 | `expiresAt` 필수 (기본 7일) |
| 단일 사용 | `redeemInvite`가 **트랜잭션**으로 `consumedAt` 미설정을 확인하고 즉시 설정 |
| 열거 방지 | 초대 문서는 클라이언트가 읽지 못함 |

> **왜 이메일 검증이 필요한가 (Codex 지적 3-1).** 이메일+비밀번호 가입은 아무 주소나 적을 수 있다.
> 공격자가 `cfo@피해회사.com`으로 계정을 만들고 그 회사 재무담당자에게 간 초대를 대신 삼킬 수 있다.
> **검증된 이메일**이어야 초대를 소비할 수 있게 한다. 카카오·네이버·구글 계정은 제공자가 확인한
> 이메일을 쓰되, 제공자가 이메일을 주지 않는 경우는 초대 소비 전에 이메일 인증을 요구한다.

### 4.5 자유 가입 남용 방어

| 방어 | 내용 |
|---|---|
| 휴대폰 본인확인 전 회사 생성 불가 | 서버가 `phoneVerifiedAt` 확인 (§4.2) |
| 한 계정은 회사 하나만 | `createTenant`**와** `redeemInvite` **둘 다** 트랜잭션으로 `users/{uid}` 부재 확인 (Codex 지적 3-4 두 탭 동시 제출 + 2차 P0-3 초대 경로 우회 방지) |
| 회사ID는 **예측 불가능한 무작위 값** | 회사명 기반이면 남의 회사 주소를 추측당함 |
| 최고관리자 화면에서 회사 정지 | 정지가 실제로 차단되는지는 §3.4 `tenantActive()` 가 보장 |
| 문자 발송 속도 제한 | 비용 폭주 방지 |

## 6. (보류) UGD 이주 계획

> **★ 2026-08-17 사용자 결정: UGD 이주는 하지 않는다.**
>
> UGD는 지금의 `erp_ugd` 시스템을 계속 쓰고, 새 제품은 **새로 가입하는 회사만** 사용한다.
> 따라서 이 장(§6)과 §7의 7단계는 **v1 범위에서 제외한다.**
>
> **이 결정으로 없어지는 위험** — 전부 이 프로젝트에서 가장 까다로운 항목들이었다:
> 이주 중 쓰기 유실(§6.1), 매니페스트·체크섬 증명 게이트(§6.3), 권한 이주 감사(§6.4),
> 구 이관 스크립트 오용(§6.5), 복원 경로 갈라짐(§6.6), 옛 지점명·급여키 형식 변환.
>
> **이 결정이 남기는 것**: `erp_ugd`의 보안 감사 P0 항목(저장소 public, 지점 격리 부재,
> 평문 PIN)이 UGD에서 **계속 유효한 상태로 남는다.** 새 제품의 강화된 규칙은 UGD에 적용되지 않는다.
> 사내용으로 감수해 온 위험이므로 새로운 문제는 아니지만, "나중에 이주하면서 해결된다"는
> 경로가 사라졌다는 점은 분명히 해둔다.
>
> **내용을 지우지 않고 남겨두는 이유**: 나중에 마음이 바뀌어 UGD를 옮기기로 하면 그때 필요하다.
> 특히 §6.1(얼리기 우선)·§6.3(증명 게이트)은 어떤 데이터 이사에도 적용되는 절차다.

아래는 보류된 원안이다.

새 제품이 실사용으로 검증된 **후에** 진행한다.

### 6.1 순서 — 얼리기가 먼저다 (Codex 지적 4-1)

> 초판은 "복사 시점 고정, 원본은 읽기전용 전환"이라고 썼는데 **순서가 모호했다.**
> 복사를 시작한 뒤에 읽기전용으로 바꾸면, 그 사이에 지점이 자동저장한 내용은
> **복사본에 없고 원본은 곧 버려져 조용히 사라진다.**

```
1. 원본을 읽기전용으로 전환한다            ← 반드시 먼저
2. 쓰기가 완전히 멎은 것을 확인한다 (최종 쓰기 시각 확인)
3. 그 다음에 복사를 시작한다
4. 매니페스트를 만들고 대조한다 (§6.3)
5. 통과하면 전환, 실패하면 중단하고 원본 읽기전용을 해제한다
```

### 6.2 이주 절차

1. 새 시스템에 UGD 회사 생성 — 기능 전부 켬, `branchIsolation = false`
2. §6.1 순서로 데이터를 `tenants/UGD/` 아래로 복사
3. 기존 구글 로그인 사용자에게 UGD 소속·권한 부여 → **재가입 불필요**
4. 남은 PIN 계정은 개인 계정으로 전환
5. **마감이 없는 월 중순 새벽**에 전환. 옛 주소는 새 주소 안내 화면으로 교체
6. 옛 시스템을 **한 달간 읽기전용으로 보존** (되돌릴 여지 확보)

> 마감 시간대 배포 금지 원칙(메모리 `erp_stale_chunk_and_translate_fix`)이 이주에도 적용된다.

### 6.3 전환 전 증명 게이트 (Codex 지적 4-3)

> 초판은 "급여·마감 금액 0원 차이"만 확인했다. **금액이 맞아도 컬렉션 하나가 통째로
> 빠질 수 있다.** `shared_data_backups`나 `edit_logs`가 누락돼도 금액 대조는 통과한다.

전환 전에 **전부** 통과해야 한다. 하나라도 실패하면 전환하지 않는다.

| 게이트 | 확인 내용 |
|---|---|
| 컬렉션 목록 | 원본에 있는 컬렉션이 **하나도 빠짐없이** 복사본에 있다 |
| 문서 수 | 컬렉션별 문서 개수가 원본과 정확히 일치 |
| **내용 체크섬** | **문서마다 내용 해시**를 구해 대조 (아래) |
| 금액 대조 | 급여·마감 합계 0원 차이 |
| 권한 대조 | §6.4 |
| **급여 키 변환 대조** | 옛 급여 키(`monthly_fulltime_salary:지점:월`)가 **빠짐없이** 새 3칸 형식(`<범위키>--salary--<키>`)으로 변환됐다. 변환 전후 1:1 대조표를 출력하고, **등급 칸이 `salary`가 아닌 급여 문서가 0건**임을 확인 (§3.4) |
| **형식 검사** | 이주 후 모든 문서ID가 §3.4 규약을 만족한다 (`shared_data`는 3칸, 나머지는 범위키로 시작). **`_all--salary--` 로 시작하는 문서가 0건**임을 별도로 확인한다 — 형식만 보면 통과해 버리는 조합이라 따로 세지 않으면 놓친다 (7차 리뷰 P1) |
| **지점명 검사** | **`public_branches` 문서ID 중 `--` 를 포함하거나 `_all`·`_admin` 인 것이 0건**임을 확인한다. 규칙은 **새로 만드는** 지점만 검증하므로, 이주해 온 옛 지점명은 검사를 거치지 않는다. `--` 가 든 지점명이 하나라도 넘어오면 `scopeOf` 가 앞부분만 떼어내어 **다른 지점 담당자가 그 지점 데이터를 읽게 된다**(구현 리뷰 I-2). 지점명에 `-` 자체가 없으면 안전하다 |
| 되돌리기 | 되돌리는 명령이 **문서화되어 있고 실제로 시연됐다** |

**내용 체크섬 (2차 리뷰 P0-1)**

> 초판 개정본은 체크섬을 "문서ID 정렬 목록의 해시"로 정의했다. **그건 내용을 전혀 안 본다.**
> 문서가 다 있는데 **안에 든 값이 깨졌거나 잘린 경우를 잡지 못한다.**

```
문서 해시   = SHA-256( 키 이름 오름차순으로 정렬한 JSON 직렬화 )
컬렉션 해시 = SHA-256( 문서ID 순으로 이어 붙인 "문서ID:문서해시" 목록 )
매니페스트  = 컬렉션별 { 문서 수, 컬렉션 해시 } 전체 목록
```

- 원본과 복사본에서 각각 매니페스트를 만들어 **컬렉션 해시까지 일치**해야 통과
- 이주 과정에서 값이 바뀌는 필드(예: 이주 시각, 문서 경로)는 **해시 대상에서 제외**하고,
  제외 목록을 매니페스트에 함께 기록한다 (제외 목록이 조용히 늘어나는 것을 막기 위함)
- 불일치 시 **어느 컬렉션의 어느 문서인지**를 출력한다

이주 스크립트는 **몇 번 실행해도 같은 결과**(멱등)여야 한다. 중단 후 재실행이 가능해야 한다.

### 6.4 계정·권한 이주 감사 (Codex 지적 4-5)

기존 프로필에는 `allowedBranches`, `salaryBranchesEncoded`, 승인 상태가 들어 있다.
**일괄로 `allowedBranches = all`을 넣으면 지점 직원이 전 지점 급여를 보게 된다.**

- 이주 스크립트는 사람별 **이주 전/후 권한 대조표**를 파일로 출력한다
- 그 표를 **사람이 눈으로 확인한 뒤에** 전환한다
- 급여 접근 권한(`salaryBranchesEncoded`)은 **URL 인코딩 관례**가 있으므로 그대로 옮긴다
  (메모리 `erp_salary_branch_isolation`)
- 이주 스크립트는 `allowedBranches`(원문)와 함께 **`allowedBranchesEncoded`를 반드시 생성**한다.
  §3.4가 규칙 판정에 인코딩본만 쓰므로, 이게 비면 그 사람은 **아무 지점도 못 보게 된다**
  (UGD는 `branchIsolation=false`라 당장은 드러나지 않지만, 나중에 켜는 순간 터진다)

> §3.4와 여기가 같은 규약을 쓴다: **규칙은 디코딩하지 않고 인코딩된 값끼리 비교한다.**

### 6.5 구 이관 스크립트 재사용 금지 (Codex 지적 4-2)

`scripts/migrate-to-firebase.ts`를 **이주 기반으로 쓰지 않는다.**

실제 확인한 내용: 이 스크립트는 계정·지점설정·빈 직원명부만 만들고,
주석에 "기존 이력은 앱 전환 후 별도 일괄 이관한다"고 적어둔 채
`shared_data/migration_status`에 **`completed: true`를 기록한다**(`settlementCount`는 0인 채로).

즉 **아무것도 안 옮기고 "완료"라고 표시**한다. 그대로 쓰면 마감·급여·공유데이터·백업·수정이력이
전부 사라진 상태로 이주가 끝났다고 판단하게 된다. 새 이주 도구를 별도로 만든다.

### 6.6 복원 경로 동시 수정 (Codex 지적 4-4)

`restoreDirectFromFirebase`(`firebaseDirect.ts:1264-1305`)는 최상위 `settings`·`daily_settles`를
읽어 되쓴다. 이주 후에도 이게 남아 있으면 **화면은 회사 경로를 읽는데 복원은 최상위에 쓰는**
갈라진 상태가 된다. 1단계에서 회사 경로로 함께 옮긴다.

| P0 | `tenants/{t}` 메타 읽기에 활성 조건이 없어 **§1 불변식 3을 스스로 위반** | §3.3 — 활성 회사 구성원으로 제한 + `getAccountState` 안내 통로 |
| 1 | "규칙 한 줄로 끝난다"는 과장 (`split`은 실존하나 판정은 조합 필요) | §3.4 — 표현 정정, 조합 요소 명시 |
| 2 | "반드시 `enc(지점명)--<나머지>`"라면서 표에는 접미사 없는 예시 | §3.4 — "뒤에 더 붙일 것이 있을 때만 `--`" 로 규약 정정 |
| 3 | `_all` 공용 데이터의 접근 규칙 자체가 없음 | §3.4 — `_all`/`_admin` 범위키 도입, 권한 목록과 분리 |
| 4 | 초대→구성원 전환 시 인코딩본 생성 주체가 불명확 | §3.2 초대 스키마 + §3.5 — `createInvite`가 둘 다 생성, 소비는 복사만 |
| 5 | §7이 "서버 함수 5종"으로 낡음 (실제 9종) | §7 — 9종으로 정정 |

**이번 개정에서 얻은 교훈**

- **불변식은 써놓는 것으로 지켜지지 않는다.** §1에 "정지된 회사는 어떤 데이터도 못 읽는다"고
  적어두고, §3.3에서 정지 여부를 안 보는 규칙을 썼다. 불변식을 세웠으면 **그걸 건드리는 모든
  규칙을 하나씩 대조**해야 한다. §8.1 #25가 그 대조를 자동화한다.
- **예외를 한 개 만들면 그 예외의 규칙도 써야 한다.** `_all`을 "공용"이라고만 적고 누가 읽고
  누가 쓰는지를 안 적어서, 구현자가 권한 목록에 밀어 넣는 잘못된 해석이 가능해졌다.
- **문서 안의 숫자는 낡는다.** 함수 5종 → 9종처럼, 한 곳을 늘리면 그걸 세는 다른 곳도 같이 낡는다.

### 11.4 4차 리뷰 (2026-08-17, P0 2건 + P1 1건 / 3차 지적 6건은 전부 종료 확인)

| # | 지적 | 반영 위치 |
|---|---|---|
| P0-1 | 새 범위키가 **기존 급여 전용 규칙을 어떻게 물려받을지 미규정** → 지점 담당자 전원이 급여 열람 | §3.2 `salaryBranchesEncoded`, §3.4 급여 등급 항 (`<범위키>--<등급>--<키>`) |
| P0-2 | `_admin` 예약이 본문에만 있고 검증·테스트에는 누락 (절반만 반영) | §3.4 지점명 제약, §8.1 #21 |
| P1 | 키 접두사 범위 조회가 새 문서ID 형식에서 아무것도 못 찾음 | §2.2 별도 취급 표에 추가 |

**이번 개정에서 얻은 교훈**

- **기존 시스템의 "예외 규칙"이 가장 잘 잊힌다.** 급여는 지점 권한과 별개 축이라는 사실이
  현행 규칙에 80줄이나 들어 있는데, 새 체계를 설계하면서 통째로 빠뜨렸다.
  **기존 규칙 파일에 있는 판정 함수를 하나씩 세어 새 설계에 대응물이 있는지 확인**해야 한다.
- **"본문에 썼다"와 "검증·테스트에 넣었다"는 다른 일이다.** `_admin` 예약이 정확히 그 사이에서
  샜다. 규약을 하나 만들면 **선언 · 검증 · 테스트 세 곳**에 같이 들어가야 한다.
- **형식을 바꾸면 그 형식을 읽던 조회도 같이 깨진다.** 접두사 범위 조회는 오류를 내지 않고
  **빈 결과**를 준다 — 가장 발견하기 어려운 종류의 고장이다.

### 11.5 5차 리뷰 (2026-08-17, P0 2건 / `_admin` 예약은 종료 확인)

| # | 지적 | 반영 위치 |
|---|---|---|
| P0-1 | §3.4 한 절 안에 `shared_data` 문서ID가 **2칸 표와 3칸 규약으로 이중 규정** — 위 표만 보고 구현하면 급여 등급 칸이 통째로 빠짐 | §3.4 — 표를 3칸으로 통일 + 규약 문단에 예외 명시 |
| P0-2 | §3.4가 약속한 **급여 키 변환 대조 게이트가 §6.3 표에 실제로 없음** (실효 없는 참조) | §6.3 — 급여 키 변환 대조 + 형식 검사 2행 추가 |

**검증된 사항**: `split('--')`의 인덱스 0(범위키)·1(등급)은 뒤에 `--slotN`이 붙거나 키 내부에
`--`가 들어가도 밀리지 않는다. 유일한 반례인 "지점명 자체에 `--`"는 §3.4 지점명 제약이 이미 차단한다.

**이번 개정에서 얻은 교훈**

- **같은 절 안의 요약표와 상세 규약이 어긋나면, 구현자는 표를 본다.** 표가 더 눈에 띄기 때문이다.
  규약을 바꿨으면 **그 규약을 요약한 표를 먼저 고쳐야** 한다.
- **"~에 포함한다"고 쓴 참조는 실제로 그쪽에 가서 넣어야 완성이다.** §3.4에서 §6.3을 가리켰지만
  §6.3에는 그 항목이 없었다. 참조를 쓸 때마다 **가리킨 곳을 열어 확인**한다.

  형식이 맞는데도 있어선 안 되는 조합은 **따로 세어야** 잡힌다.
