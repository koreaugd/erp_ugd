03 AGENT가 만드는 `02.보고용 통합보고서/{YYMM}_손익계산서_통합*.xlsx` 를 관리자 화면에서 **엑셀 그대로** 열람하는 탭.

## 2. 원본 파일의 구조 — 왜 "격자 그대로"인가

2607 파일 실측: **17개 시트** (14지점 + 험프리스 + 본사 + 상각), 총 48,615개 비어있지 않은 셀.

시트 한 장 안에 여러 블록이 **가로로 나란히** 들어 있다(마음죽 시트 기준):

| F3:K… | 매출 상세 (총매출 / 단순현금 / 현금영수증 / 신용카드 / 영수건수 / 영수단가) |
| M3:AA… | 1. 실무자 기준 급여 (분류·성명·직급·**주민등록번호**·입사일·근로계약·**입금계좌**·전월급여·이달 급여·…) |

**그리고 시트마다 양식이 다르다.**

- 지점 시트: 위 구조
- `본사`: 손익계산서에 `계산식` 열이 추가되고, 배당인센 행이 여러 줄, 급여 블록의 열 배치가 한 칸씩 다르다(U열이 `이달급여`, 지점은 `이달 급여`)
- `험프리스`: `통장7월거래내역원본` + `본사평택계좌7월거래내역원본` 두 블록이 P·X열에 따로 붙고, 환율 환산 블록(거래외화금액·거래환율·원화)이 있다
- `상각`: 아예 다른 표(상호·상각개시월·상각기간·투자총액·보증금·월상각금액·…)를 세로로 세운 형태

→ **항목별로 파싱해 예쁜 표로 재구성하면 어느 시트에선 반드시 깨진다.** 셀 위치를 그대로 보존하는 격자 뷰어로 만든다. 이것이 "파일 양식으로 볼 수 있게"에 대한 정확한 답이기도 하다.

## 3. 저장 — 형식과 크기

### 3-1. 왜 원본 xlsx를 그대로 저장하지 않는가

원본을 base64로 저장하면(선례: `firebaseDirect.ts:878` 근로계약서 양식) 편하지만, **파일 안의 주민번호·계좌가 원본 그대로 서버에 남는다.** 마스킹이 불가능해진다. 그래서 **브라우저에서 파싱 → 마스킹 → 저장**한다.

### 3-2. 크기 실측 (2607 파일)

| 방식 | 크기 |
| --- | --- |
| 원본 xlsx | 447 KB |
| 원본 base64 | 596 KB |
| 파싱 JSON (꼬리 빈칸 정리) | 661 KB |
| **JSON → gzip** | **140 KB** |
| **JSON → gzip → base64** | **187 KB** |

Firestore 문서 한도는 1,048,576 바이트. **187KB = 한도의 19%** 이므로 **월 1문서**로 충분하다. 시트별로 17개 문서로 쪼갤 필요가 없다.

> Firestore는 **배열 안의 배열**을 저장하지 못한다. `rows: [[...],[...]]` 는 그대로 못 넣는다. 압축 base64 **문자열 한 필드**로 저장하면 이 제약도 함께 사라진다.

### 3-3. 저장 스키마

```
shared_data/pnl_report_pack%3A2607
  {
    month: "2607",
    fileName: "2607_손익계산서_통합2_본사적용 (2).xlsx",
    sheetNames: ["강남대골뼈국", …, "상각"],   // 목차용(압축 풀지 않고 읽기)
    gzipBase64: "H4sIAAAA…",                  // gzip(JSON({name, rows}[]))
    maskedFields: 138,                         // 마스킹한 칸 수(검증용)
    uploadedAt: "2026-08-11T…",
    uploadedBy: "서광엽"
  }

shared_data/pnl_report_pack_index
  { months: [{ month, fileName, uploadedAt, uploadedBy }] }   // 최신순 아님, 화면에서 정렬
```

- 월 인식: 각 시트 A1의 `마음죽_2607` / `험프리스_26.07월` 패턴에서 6자리 추출 → 실패 시 파일명(`2607_…`) → 그래도 실패하면 업로드 거부하고 사유를 알린다(엉뚱한 달에 덮어쓰는 사고 방지).
- 인덱스는 **`mutateSharedData`(트랜잭션)** 로 갱신한다. `saveSharedData`로 쓰면 두 관리자가 다른 달을 동시에 올릴 때 한쪽 목록이 통째로 사라진다. updater는 순수 함수여야 한다(재시도 시 여러 번 호출됨).
- 같은 달을 다시 올리면 덮어쓴다. 덮어쓰기 전에 기존 업로드 시각을 보여주고 `window.confirm` 으로 한 번 되묻는다.
- 인코딩 후 **900KB 초과면 업로드를 거부**한다. 조용히 실패해 "저장했다"고 표시되는 것이 가장 나쁘다.

### 3-4. gzip

`CompressionStream("gzip")` / `DecompressionStream("gzip")` 사용. 미지원 브라우저면 업로드 시 명확히 거부한다(무압축 저장은 1MB를 넘어 실패하므로 폴백을 두지 않는다). 대상 사용자는 Windows Chrome/Edge라 실사용 문제 없음.

## 4. 개인정보 — 3중 방어

현재 `firestore.rules:190-196` 의 `shared_data` 기본 권한은 `canAccessWork()` 다. **로그인한 모든 지점 계정이 읽을 수 있다.** 예외로 막힌 것은 급여대장 키(`isSalaryKey`)뿐이다. 통합보고서를 평범한 키로 저장하면 지점 계정 하나로 전 지점 손익·주민번호·계좌·통장 전체 거래내역이 열린다.

### ① 저장 전에 지운다 (가장 중요)

화면에서만 가리면 원본은 서버에 남아, 문서를 직접 읽는 순간 무의미해진다. **업로드 파싱 단계에서 마스킹**해 서버에 뒷자리가 아예 존재하지 않게 한다.

| 대상 | 저장 형태 |
| --- | --- |
| 주민등록번호 | `740130-2******` (뒤 6자리 제거, 성별자리 1자리는 남김) |
| 입금계좌 | `국민 004-21-****-250` (은행명·앞·뒤 일부만) |

판정은 **열 이름 + 값 패턴 이중**으로 한다. 시트마다 열 위치가 다르므로(본사 시트는 한 칸씩 밀려 있다) 열 위치를 못 박으면 새어 나간다.

- 열 이름: 같은 행에 `주민등록번호` / `입금계좌` 머리글이 있으면 그 열 아래를 마스킹
- 값 패턴: `\d{6}-\d{7}` (주민번호), 계좌 형태 문자열 — 머리글을 못 찾아도 값 자체로 잡는다

마스킹한 칸 수를 `maskedFields`로 남겨 "0건"이면 화면에 경고를 띄운다(패턴이 안 맞아 통째로 새는 것을 알아채기 위해).

### ② 권한을 잠근다

`firestore.rules`에 급여대장과 같은 방식으로 전용 판별을 추가한다.

```
function isReportPackKey(dataKey) {
  return dataKey.matches('^pnl_report_pack(:|%3A|_index).*');
}
```

`shared_data` / `shared_data_backups` **두 match 모두**에서 `isAdmin() || isPersonalAdmin()` 만 허용한다.

- `isAdmin()` = PIN 관리자(`admin@ugd-erp.example`), `isPersonalAdmin()` = 개인 총괄관리자
- 지점·지점관리자 계정은 문서 자체에 닿지 못한다

### ③ 백업 복사본도 같이 잠근다

`firebaseSaveSharedData`는 저장할 때마다 `shared_data_backups/{키}--slot{요일}` 에 사본을 만든다(`firebaseDirect.ts:619-625`). 여기를 막지 않으면 본문을 막아도 백업으로 샌다 — 급여대장에서 실제로 났던 사고로 `firestore.rules:205` 주석에 남아 있다.

### 화면 게이트

**별도 조건이 필요 없다.** `AdminPage.tsx:826` 이 `role !== "admin"` 이면 화면 전체를 `return null` 로 막으므로, 관리자 화면에 들어온 사람은 이미 총괄관리자다(지점관리자·지점은 관리자 화면 자체에 못 들어온다). PIN 관리자 세션도 `role: "admin"` 이라 규칙의 `isAdmin()` 과 판정이 일치한다. 하위탭은 다른 분석 하위탭과 같이 `analysis` 권한을 따른다.

## 4-2. [개정 2026-08-11] 2차 지시 — 가로 스크롤 · 서식 · 시트 탭 · 수정 가능

1차 구현을 보고 받은 지시 네 가지와 그 처리다.

### ① "가로 스크롤이 없어"

**원인은 스크롤 CSS가 아니라 열 너비였다.** 헤드리스 브라우저로 재현해 보니 격자 자체는 스크롤된다(4396px > 1454px). 문제는 실제 데이터에 **빈 칸이 많아 열이 내용만큼 쪼그라들면서** 표 폭이 화면보다 좁아진 것이다. 그러면 스크롤이 생길 이유가 없고, 대신 긴 값이 `…`으로 잘려 볼 방법이 사라진다.

→ `!cols[].wpx`(**엑셀의 실제 열 너비 px**)를 저장해 `<colgroup>` + `table-layout: fixed` 로 못 박는다. 실측 표 폭 1,757~2,107px 로 화면(1,454px)보다 넓어 가로 스크롤이 항상 생기고, 덤으로 **열 폭이 엑셀과 같아진다.**

### ② "엑셀의 서식이 걸린 곳들은 서식을 넣어줘"

서식은 두 곳에서 온다.

| 출처 | 얻는 것 |
| --- | --- |
| SheetJS(xlsx-js-style) | 값 · **숫자서식(z)** · 열너비 · 행높이 · 병합 |
| `helpers/xlsxStyles.ts` (신규) | **볼드 · 정렬 · 테두리 · 글자색/크기 · 배경색** |

> SheetJS 읽기 경로는 `cellStyles: true` 를 줘도 `.s` 에 **채우기(fill)만** 담아 준다. 이 파일들은 머리글·합계행이 전부 볼드라, 그것이 빠지면 "엑셀 서식 그대로"가 성립하지 않는다. 그래서 xlsx(zip)의 `xl/styles.xml` 과 시트 XML 의 `s` 속성을 직접 읽는다. 압축 해제는 `DecompressionStream("deflate-raw")`, XML 은 정규식으로 훑는다(Node 에는 DOMParser 가 없어, 한 구현으로 브라우저·검증 스크립트 양쪽에서 돌리려면 정규식이라야 한다).

숫자서식은 `XLSX.SSF.format` 으로 화면에서 다시 적용한다 — 그래야 **값을 고쳐도 서식이 다시 걸린다**(`1234567` → `1,234,567`, `0.25` → `25.0%`).

서식은 **사전(styles/numFmts)** 으로 모으고 셀에는 색인만 둔다. 2607 파일 실측 97종·13종뿐이라 통째로 담는 것보다 훨씬 작다.

**적용 규칙**: 배경·글자색·볼드·기울임·정렬·줄바꿈은 엑셀 값 그대로. 글자 크기는 `pt × 1.1 → px`(10pt→11px — ERP 기본 글자에 맞추면서 상대 크기는 지킨다). 테두리는 엑셀에 선이 있는 칸만 진하게, **오른쪽·아래만**(§9-1-A — 왼쪽·위까지 그으면 이웃 칸이 같은 경계를 두 번 그려 두 줄로 굵어진다).

### ③ "상단의 헤더 위에 지점 탭을 일렬로"

시트 드롭다운을 없애고, **제목 밴드와 열 문자 머리글 사이**에 시트 탭 17개를 가로 한 줄로 세운다(`.report-sheet-tabs`). 줄바꿈하지 않고 가로로 민다 — 줄이 접히면 표가 그만큼 아래로 밀린다. 고른 탭은 흰 바탕 + 검정 볼드 + 아래쪽 강조선.

### ④ "읽기전용이 아니고 수정할 수 있어야 해"

**엑셀과 같은 두 단계 모델**이다. 클릭 = 선택(굵은 테두리) / Enter·F2·더블클릭·글자 입력 = 편집 시작.

| 상태 | 키 |
| --- | --- |
| 선택 | 방향키·Tab·Home·End·PageUp/Down = 칸 이동 · Enter·F2 = 편집 · Delete/Backspace = 지우기 |
| 편집 | Enter = 확정 후 아래 · Tab = 확정 후 오른쪽 · Esc = 취소 · 방향키 = 글자 사이 이동 |

- **IME**: 입력칸에 `inputMode="numeric"` 을 절대 넣지 않는다(DESIGN.md §9 의 실제 사고 — 윈도우 IME 가 영문으로 바뀐 채 전역에 남아 다음 칸의 한글이 깨진다). 조합 중(`isComposing`) Enter 는 글자 확정이라 칸을 옮기지 않는다.
- **저장은 명시적이다.** 문서가 200KB대라 타자마다 저장할 수 없다. 고치면 밴드에 `저장 안 됨` 이 뜨고 `저장` 단추가 켜진다.
- **되묻는 자리는 고친 내용이 *실제로 버려지는* 곳뿐이다** — 다른 달로 옮기기 · 새로고침 · 새 파일 업로드. 이 셋은 서버에서 문서를 다시 읽어 통째로 갈아 끼우므로 확인을 누르면 수정이 진짜로 사라진다. 창을 닫을 때는 브라우저 기본 경고가 막는다.
  > **시트 전환에는 묻지 않는다.** 시트는 **같은 파일 안**이라 옮겨도 아무것도 버려지지 않는다 — 엑셀처럼 여러 시트를 고친 뒤 한 번에 저장한다. 예전엔 여기서도 "버리고 이동할까요?"를 물었는데 **정작 버리는 동작이 없어, 확인을 눌러도 수정이 그대로 남아 나중에 저장됐다**(Codex 정지게이트 2026-08-11). 말과 동작이 어긋난 확인창은 없느니만 못하다.
- **동시 수정**: 아래 4-3 참고 — 판올림 번호 기반 비교-후-쓰기(CAS).
- **[한계 — 화면에 명시]** 엑셀 수식은 **계산된 값으로만** 들어온다. 어떤 칸을 고쳐도 총매출·총지출·이익금 같은 합계는 따라 바뀌지 않는다. 숨기면 잘못된 보고서가 되므로 각주에 붉게 적었다.

## 4-3. [P0] 동시 수정 — 판올림 번호 CAS (Codex 정지게이트 지적으로 재작성)

첫 구현은 **"서버 값을 읽어 시각을 비교" → "따로 쓰기"** 두 단계였다. 구멍이 두 개였다.

| 구멍 | 어떻게 새는가 |
| --- | --- |
| 읽기와 쓰기 **사이**가 열려 있다 | 비교를 통과한 뒤 쓰기 전에 다른 노트북이 저장하면 그대로 덮어쓴다 |
| 시각이 둘 다 비면 `"" === ""` | 서로 다른 내용인데 "같다"로 판정해 **조용히** 덮어쓴다 |
| 업로드는 **월 목록(index)** 으로만 존재 확인 | 목록은 **셀을 고쳐 저장해도 갱신되지 않는다** → 다른 노트북의 수정이 안내조차 없이 사라진다. 목록 쓰기가 한 번 실패한 상태였다면 확인 자체가 건너뛰어진다 |

**해결 — 문서에 판올림 번호(`rev`)를 두고, 쓰기를 트랜잭션 안의 비교-후-쓰기로 바꿨다.**

```
mutateSharedData(pnl_report_pack:2607, (current) => {
  if (current && revOf(current) !== baseRev) return null;   // 한 글자도 쓰지 않는다
  return { ...doc, rev: baseRev + 1 };
})
```

- `mutateSharedData` 는 Firestore 트랜잭션이라 **읽고 쓰는 사이가 없다.**
- 판정 기준은 **숫자 하나**뿐이라 `""` 무승부가 없다. 번호가 없는 옛 문서는 `revOf` 가 0으로 보므로, 두 기기가 같은 0에서 출발해도 먼저 쓴 쪽만 통과한다.
- 갱신하지 않았을 때 돌려주는 `value` 는 **트랜잭션이 실제로 본 서버 문서**다(`firebaseDirect.ts:756` 규약) — 다시 읽을 필요가 없고, 다시 읽는 사이에 또 바뀌는 문제도 없다. 이 값으로 "누가 언제 저장했는지"를 안내한다.
- 사용자가 확인한 덮어쓰기도 **다시 CAS** 다 — 그새 또 바뀌었으면 또 막힌다.
- **업로드도 같은 경로**를 쓴다. 존재 확인은 월 목록이 아니라 **그 달의 보고서 문서 자체**로 하고, 이미 고쳐진 문서면 "화면에서 고친 내용이 모두 사라집니다"를 붙여 되묻는다.

갱신자(`reportPackCasUpdater`)는 **순수 함수**로 빼 두었다 — 트랜잭션 재시도로 여러 번 불리기 때문이고, 검증 스크립트가 **같은 함수로** 동시 저장 시나리오를 돌리기 때문이다(화면이 도는 코드와 검증한 코드가 갈라지지 않게).

## 4-4. 화면 배율 — "열 너비가 너무 크다"에 대한 답 (2026-08-11 3차 지시)

먼저 **왜 넓어 보이는지**를 측정했다.

- 우리 글자의 숫자 폭은 **6.1px**, 엑셀이 이 파일의 열 너비를 계산할 때 쓴 폭(MDW)은 **6px**. 배율로 치면 1.02 — **엑셀 열 너비를 그대로 쓰는 것이 맞다.**
- 그런데도 헐거워 보이는 이유: 엑셀 열 너비는 그 열의 **가장 긴 값**에 맞춰져 있다. 마음죽 B열이 128px인 것은 아래쪽 거래내역의 긴 거래처명 때문이고, 위쪽 손익계산서만 보면 **57px이 남는다**(D열 36px).
- 그렇다고 폭만 줄이면 아래쪽 값이 잘리고 글자만 상대적으로 커져 비율이 깨진다. A열은 남는 폭이 3px뿐이라 조금만 줄여도 `세금예비(10%)`가 잘린다.

→ **엑셀과 같은 방식, 즉 배율(확대/축소)로 푼다.** 글자·열너비·행높이에 같은 배율을 곱하므로 비율이 그대로 유지된다. `[배율 70/80/90/100%]` 드롭다운, **기본 80%**.

| 배율 | 표 폭 | 한눈에 보이는 열 | 값 있는 칸 중 잘림 |
| --- | --- | --- | --- |
| 100% | 1,938px | 18개 | 18% |
| 90% | 1,747px | 21개 | 18.3% |
| **80% (기본)** | **1,558px** | **24개** | 20.8% |
| 70% | 1,349px | **27개 전부** | 20.2% |

**배율을 줄여도 잘림이 거의 안 는다**(18% → 20.8%)는 것이 핵심이다. 잘림은 배율이 아니라 원본 열 너비 자체에서 오기 때문이다 — 그래서 배율을 낮추는 쪽이 손해가 거의 없다.

배율 선택은 **localStorage** 에 기억한다. 화면 보기 설정이지 업무 데이터가 아니고, 노트북마다 화면 크기가 다르므로 기기별로 따로 기억하는 편이 맞다(“모든 노트북에서 같아야 한다”는 규칙은 데이터에 대한 것이다).

> **[TDZ 함정]** 배율에서 나오는 `rowHeadPx`·`colPx` 선언은 `moveTo` 의 `useCallback` **위에** 두어야 한다. 의존성 배열은 즉시 평가되므로 선언이 아래에 있으면 초기화 전 접근으로 화면이 통째로 죽는다.

## 4-5. 성능 — 가상 스크롤 (시트 탭 전환 딜레이, 2026-08-11 4차 지시)

시트 탭을 누르면 눈에 띄게 기다려야 했다. 실측:

| 시트 | 행수 | DOM 칸 | 전환 시간 |
| --- | --- | --- | --- |
| 마음죽 | 132 | 3,696 | 233ms |
| 대물섬종로점 | 638 | 17,864 | 453ms |
| 사카바단단 | 640 | 17,920 | **496ms** |

원인은 단순하다 — 시트를 바꿀 때마다 **17,920개의 `<td>` 를 새로 만들고**, 그중 숫자 칸마다 엑셀 서식을 다시 계산한다.

**해결 — 화면에 보이는 행만 그린다(가상 스크롤).** 위아래로 안 그린 행들의 높이를 대신 차지하는 빈 행(스페이서)을 두어 스크롤 막대는 실제 크기대로 움직인다.

| 시트 | DOM 칸 | 전환 시간 |
| --- | --- | --- |
| 마음죽 · 사카바단단 · 대물섬종로점 · 상각 | **약 1,430개(고정)** | **48~79ms** |

**시트 크기와 무관하게 일정**해졌다 — 640행이든 66행이든 화면에 들어오는 만큼만 그리기 때문이다.

### 가상 스크롤이 성립하기 위한 조건

| 조건 | 왜 |
| --- | --- |
| 모든 행에 **높이를 못 박는다**(엑셀 hpx, 없으면 19px×배율) | 스크롤 위치를 미리 계산하려면 각 행이 몇 px인지 알아야 한다 |
| 엑셀의 **자동 줄바꿈은 따르지 않는다** | 줄이 늘면 행이 계산보다 높아져 스크롤이 어긋난다. 엑셀도 높이가 고정된 행에서는 넘치는 줄을 감추므로 무시하는 편이 원본에 가깝다 |
| `line-height` 를 CSS 로 고정 | 같은 이유 — 글자에 따라 행이 들쭉날쭉해지면 안 된다 |
| 커서 이동 스크롤을 **DOM 조회 대신 누적합**으로 계산 | 화면 밖 행은 DOM 에 없어서 `querySelector` 로 찾을 수 없다 |
| 편집 입력칸은 **언마운트에서도 값을 확정** | 편집 중인 행이 스크롤로 밀려나면 입력칸이 사라지는데, 그때는 blur 가 안 떠서 친 내용이 조용히 사라진다 |

> **[좌표계 함정 — 실제로 걸림]** `rowTop`/`colLeft` 는 **본문(tbody) 기준**이고 `scrollTop`/`scrollLeft` 는 **표 전체 기준**이다. 표 맨 위의 열 문자 머리글과 맨 왼쪽의 행 번호 열이 자리를 차지하는 데다, 둘 다 고정(sticky)이라 **화면 가장자리 그만큼을 늘 덮고 있다.** 이 둘을 빼먹으면 커서가 머리글 뒤에 숨거나 아예 화면 밖에 남는다(PageDown 을 12번 눌렀을 때 실제로 그랬다).

### 함께 유지되는 최적화

- 행(`GridRow`)을 `React.memo` 로 감싸고 커서가 없는 행엔 `activeCol=null` → 커서 이동 시 다시 그려지는 행은 둘뿐
- 편집 입력칸은 **비제어** — 한 글자마다 부모를 다시 그리지 않는다
- 값 수정은 순수 함수 `withEditedCell` 의 불변 갱신 — 바꾼 행만 새 배열
- 콜백은 전부 `useCallback` 으로 정체 고정 — 인라인 화살표 함수를 쓰면 memo 가 통째로 무력화된다

## 4-6. 열 너비·행 높이 끌어 조절 (2026-08-11 5차 지시)

엑셀처럼 **머리글 오른쪽 모서리**를 끌어 열 너비를, **행 번호 아래 모서리**를 끌어 행 높이를 바꾼다.

- **끄는 동안에는 React 상태를 건드리지 않는다.** 움직일 때마다 상태를 바꾸면 보이는 행(약 50행 × 27열)이 매 프레임 다시 그려져 끌리는 느낌이 끊긴다. 끄는 중에는 `<col>`/`<tr>` 의 `style` 만 직접 적고, **손을 뗄 때 한 번만** 부모에 알린다. 그 뒤 React 가 새 값으로 다시 그리며 누적합(스크롤 위치 계산)까지 맞춘다.
- 포인터를 손잡이에 가둬(`setPointerCapture`) 격자 밖으로 나가도 계속 따라온다.
- **저장값은 배율 100% 기준**으로 되돌려 담는다(화면에서 끈 폭 ÷ 배율). 그대로 담으면 배율을 바꿨을 때 크기가 어긋난다.
- 크기 조절은 **값 수정과 같은 취급**이다 — 엑셀에서도 열을 넓히면 문서가 바뀐 것이고, 저장해야 다른 사람 화면에도 그 폭으로 보인다. 그래서 `저장 안 됨` 이 함께 켜진다.
- 최소 크기(열 24px · 행 12px)를 둬서 칸을 0으로 만들어 잃어버리는 일이 없게 한다.
- 손잡이는 sticky 인 머리글·행번호 칸 **안쪽**에 깐다 — 본문 칸에는 `overflow:hidden` 이 걸려 있어 바깥으로 내밀면 보이지 않는다. 평소엔 투명하고 손을 올리면 파란 선이 뜬다.

### 5-2. 엑셀형 규칙 적용

| 항목 | 적용 |
| --- | --- |
| 헤더 색 | 관리자는 엘리스 `--admin-alice` (§9-1, DESIGN_ADMIN §4-0 — 밴드가 바닐라라 헤더까지 바닐라면 뭉친다) |

| 선 | **오른쪽·아래만 1px**(§9-1-A). 표의 맨 왼쪽·위·오른쪽·아래에는 긋지 않는다(카드 테두리와 겹침) |
| 테이블 | `border-separate; border-spacing: 0`. 고정 칸의 선은 `border`가 아니라 `inset box-shadow` |
| 숫자 | `font-mono` + **천 단위 쉼표**(§9-4), 우측 정렬. **칸 안에 단위(원) 안 붙임**(§9-5) |
| 커서 띠 | 클릭한 행에 §9-3 '막+선'. 읽기 전용이라 `focus-within`이 없어 손익 요약표와 같이 **클릭**으로 준다 |
| 입력칸 | 없음(읽기 전용). §9-0의 입력칸 투명화·키보드 이동은 해당 없음 |
| 글자 크기 | 밴드 제목 14px(`.admin-band-title`), 그 외 11px(`.admin-analysis-uniform`) |

### 5-3. 표시 규칙

- **빈 셀은 빈 칸.** `-`나 `0`으로 채우지 않는다 — 원본에 없는 값이 있는 것처럼 보인다.
- 숫자는 쉼표. 소수(비율 `0.17696…`)는 원본 그대로 두되 소수점 이하가 길면 잘라 `title`에 전체값을 넣는다.
- 날짜 셀은 `YYYY-MM-DD`로 통일(엑셀에서 datetime으로 들어오는 칸이 섞여 있다).
- 마스킹된 칸은 값 옆에 표시를 붙이지 않는다 — 값 자체가 `******` 라 이미 드러난다.
- 시트 선택은 **드롭다운**. 17개를 칩으로 늘어놓으면 두 줄로 접혀 상단 줄이 무너진다(같은 이유로 지점 선택을 칩→드롭다운으로 되돌린 선례가 `AdminAnalysisSection.tsx:171-174` 주석에 있다).

### 5-4. 성능

한 번에 한 시트만 그린다. 최대 시트는 사카바단단 640행 × 27열 = 17,280셀. 렌더가 느리면 행 가상화를 넣되, **먼저 실측하고 필요할 때만** 넣는다.

## 6-1. [P0] 원점은 반드시 A1 — 구현 중 실제로 걸린 함정

`XLSX.utils.sheet_to_json` 은 시트의 `!ref` 범위를 그대로 쓴다. **값이 A1 에서 시작하지 않는 시트가 있다** — 2607 파일의 `상각` 시트는 범위가 `B2:Y66` 이라, 그대로 두면 **B열이 A열로, 2행이 1행으로 통째로 밀린다.** 격자 뷰어의 존재 이유가 무너지는 결함이다(11행×6열이어야 할 시트가 10행×5열로 나왔다).

→ `range` 옵션에 시작점을 `{r:0, c:0}` 으로 못 박아 넘긴다. 다른 시트는 원래 A1 시작이라 영향이 없다.

## 8. 하지 않는 것

- 셀 편집. 읽기 전용이다.
- 항목별 재해석·차트. 그건 이미 같은 분석 탭의 손익 종합·손익 차트가 한다.
- 원본 xlsx 다시 내려받기. 저장본은 마스킹본이라 원본을 재생성할 수 없다. 원본이 필요하면 03 AGENT 폴더의 파일을 연다.
- 수식 복원. `data_only` 로 계산된 값만 읽는다(엑셀이 저장한 마지막 계산값).
