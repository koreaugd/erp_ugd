# 비즈니스택시·연차관리 월말 확인 마감 — 설계서

작성일: 2026-08-11

## 1. 배경과 목표

지점은 말일에 **매입매출·매출집계·파트타이머 급여대장** 세 가지를 월말마감으로 제출한다
(정직원 급여대장은 25일 작성이라 시점이 다르다).

그런데 **비즈니스택시 등록 인원**과 **연차 내역**은 상시 업무라 아무도 "이번 달 것이 맞는지"
멈춰서 보지 않는다. 퇴사자가 택시 계정에 남아 있거나 연차 사용이 등록되지 않은 채로 달이 넘어간다.

**목표**: 말일 마감을 제출하기 전에, 지점이 두 화면을 **눈으로 확인하고 버튼을 누르도록** 강제한다.

**비목표(명시적으로 하지 않는 것)**:
- 지점 명부와 택시 등록 인원의 **자동 대조를 하지 않는다.** 시스템이 "누가 빠졌다"를 판정하지 않는다
  (사용자 지시 2026-08-11). 판단은 사람이 하고, 시스템은 확인했다는 사실만 기록한다.
- 연차 부여일수·잔여일수 검산도 하지 않는다.
- 관리자 화면에 새 컬럼을 만들지 않는다 (§7 후속 과제).

## 3. 데이터 설계

### 3.1 저장소 — 기존 `monthly_closings` 재사용

새 저장소를 만들지 않는다. 기존 마감 레코드 배열에 섹션 값 두 개를 더한다.

섹션 값의 **단일 출처는 새 헬퍼**다. 문자열을 두 곳에 각자 적으면 한쪽만 고쳤을 때 게이트가
조용히 빠진다(에러도 안 난다).

```ts
// src/pages/branch/helpers/monthlyCheckSections.ts  ← 단일 출처
export const CHECK_SECTIONS = ["businessTaxi", "annualLeave"] as const;
export type CheckSection = typeof CHECK_SECTIONS[number];
export const CHECK_SECTION_LABEL: Record<CheckSection, string> = { ... };
export const GATED_CLOSE_SECTIONS = ["purchase", "salesSummary", "partTimeSalary"] as const;
```

**`MonthlySettleTab`의 `CloseSection` 타입은 넓히지 않는다.**
확인 섹션은 그 화면의 마감 기계(`saveSectionClose` · 상태 배지 · 사유 인라인칸)를 전혀 타지 않고,
게이트가 헬퍼를 통해서만 읽는다. 넓히면 `editReasonDrafts` · `reasonErrors` 같은
`Record<CloseSection, …>` 맵에 **쓰이지 않는 키 2개**를 채워 넣어야 하는데, 이는 확인 섹션에
수정 사유 개념이 없다는 §3.2와 정면으로 어긋난다.

레코드 모양:

```ts
{
  branchName: string,
  month: "YYYY-MM",
  section: "businessTaxi" | "annualLeave",
  status: "confirmed" | "pending",
  confirmedAt: string,   // ISO. 취소하면 ""
  updatedAt: string      // ISO. 최신 레코드 판정 기준
}
```

**하위호환**: 관리자 월말마감 현황은 `MONTHLY_CLOSE_SECTIONS` 상수를 순회해 컬럼을 만들고
(`AdminPage.tsx` rows/sectionStats), 그 목록에 없는 `section` 값은 그냥 읽히지 않는다.
새 값을 넣어도 기존 화면·엑셀은 영향받지 않는다.

### 3.2 확인 섹션에는 없는 것

일반 마감 섹션에 있는 `editing` 상태 · `editedAfterConfirm` 표식 · `editEvents`(수정 사유 이력)를
확인 섹션은 **쓰지 않는다.** 확인 섹션은 데이터를 잠그지 않으므로(§4.3) "확정본을 수정했다"는
개념 자체가 없다. 상태는 `confirmed` / `pending` 두 가지뿐이다.

### 3.3 손상된 문서는 만지지 않는다

`monthly_closings`를 읽는 모든 경로는 같은 검사를 통과시킨다(`assertCloseRecordList`).

| `current` | 뜻 | 처리 |
|---|---|---|
| `null` | 문서 없음 — 아직 아무 마감도 없다 | 정상. 빈 배열로 시작 |
| 배열 | 정상 | 그대로 사용 |
| 그 밖(객체·문자열 등) | **손상** | `throw` — 읽지도 쓰지도 않는다 |

세 번째 줄이 핵심이다. `Array.isArray(current) ? current : []`로 관대하게 넘기면,
손상된 문서에 확인 저장 한 번으로 **전 지점·전 월의 마감 기록이 레코드 하나로 덮인다.**
이 문서는 지점별로 나뉘어 있지 않아서 손상 시 피해가 저장소 전체에 미친다.

읽기 경로도 같이 막는다. 손상됐는데 '미제출'로 보여주면 지점이 버튼을 다시 누르고,
그 저장이 곧 위의 파괴다. 화면에는 오류 배너를 띄우고 원인 문구를 그대로 보여준다 —
일반 안내로 덮으면 지점은 새로고침만 반복하고 본사에 알리지 않는다.

### 3.4 쓰기 방식 — 트랜잭션

```ts
await gasClient.mutateSharedData<any[]>("monthly_closings", (current) => {
  const list = assertCloseRecordList(current);   // §3.3 — 손상이면 throw
  return [nextRecord, ...list.filter((r) => !matches(r))];
});
```

`saveSharedData`(통째 저장)를 쓰지 않는다. `monthly_closings`는 **전 지점이 공유하는 문서 하나**라,
읽어둔 값 위에 통째로 쓰면 그 사이 다른 지점이 올린 마감이 사라진다.
updater는 순수 함수로 둔다 — 트랜잭션은 재시도로 여러 번 호출될 수 있다.

## 4. 화면 설계

### 4.1 공용 컴포넌트 `MonthlyCheckAction`

`src/pages/branch/components/MonthlyCheckAction.tsx` — 비즈니스택시 탭과 연차관리 탭이 같은 걸 쓴다.

**별도 카드를 만들지 않는다.** 확인 대상 표의 **제목 밴드 우측**에 붙인다(사용자 지시 2026-08-11):

| 탭 | 붙는 밴드 |
|---|---|
| 비즈니스택시 | `등록된 인원 (지점명)` |
| 연차관리 | `직원별 연차 현황` |

확인해야 할 표와 버튼이 한 덩어리로 붙어야 "무엇을 보고 누르는 것인지"가 자명하다.
별도 카드로 띄우면 지점은 표를 안 보고 버튼만 누른다.

컴포넌트는 **조각(fragment)만** 그리고, 감싸는 `.branch-band-actions`(우측 정렬 표준 슬롯)는
호출부가 준다. '등록된 인원' 밴드엔 이미 새로고침 버튼이 그 슬롯에 있어서, 슬롯을 따로 두면
줄이 갈라진다 — 같은 슬롯을 함께 써야 한 줄로 붙는다.

```tsx
<div className="branch-band">
  <h3 className="branch-band-title">등록된 인원 ({branchName})</h3>
  <div className="branch-band-actions">
    <button …>새로고침</button>
    <MonthlyCheckAction branchName={branchName} section="businessTaxi" />
  </div>
</div>
```

**제목 옆 부연(`branch-band-meta`)은 두지 않는다**(사용자 지시). 연차관리의 기존 부연
("지점을 바꾸면 명부·연차 기록이 …")도 함께 지운다.

컴포넌트가 하는 일:
- 마운트 시 `monthly_closings` 조회 → 선택 월의 상태 알약 표시
- 월 드롭다운(`<input type="month">`, `YYYY-MM`) — 기본값은 **오늘 기준 당월**.
  고정하지 않는 이유: 다음 달 1일에 전월 누락분을 채워야 할 때가 있다.
- [마감제출] 클릭 → 확인창 → 확정 저장 / 확정 상태에서는 [마감취소](사유 없음)
- 조회 전에는 버튼을 잠근다 — 미제출로 보이는 확정건에 눌러 확정일시가 덮이는 것을 막는다
- 조회 실패 시 컨트롤 대신 **재시도 버튼 하나**만 내놓는다. 상태를 모르는데 알약을
  '미제출'로 그리면 지점이 이미 한 확인을 다시 누른다
- 저장 실패 시 서버 진실로 되돌린 뒤 `window.alert`로 알린다(밴드 안에는 배너 자리가 없다).
  낙관적 표시를 남기지 않는다 — 안 올라간 확인이 "확정"으로 보이면 게이트가 통과된 줄 알고
  지점이 마감을 못 하는 이유를 못 찾는다

### 4.2 확인 대상 표가 안 떴으면 제출을 막는다

버튼이 밴드 안에 있다는 것은 **"이 표를 눈으로 봤다"**는 뜻이다. 그런데 표가 조회에 실패했거나
아직 안 떴거나 캐시에서 꺼낸 묵은 목록이면, 지점은 아무것도 못 본 채 확정하게 된다.
그렇게 남은 '확정'은 월말마감을 열어 주므로 **확인 절차가 통째로 형식이 된다.**

그래서 호출부가 자기 표의 상태를 `blockedReason`으로 넘기고, 준비되지 않았으면 마감제출을 막는다.

| 탭 | 조건 | 버튼에 뜨는 글자 |
|---|---|---|
| 비즈니스택시 | `membersError` | 등록 인원 조회 실패 — 확인 불가 |
| 비즈니스택시 | `allMembers === null` | 등록 인원 불러오는 중 |
| 비즈니스택시 | `membersStale` | 묵은 목록 — 새로고침 후 제출 |
| 연차관리 | `loadFailed` | 연차 현황 조회 실패 — 확인 불가 |
| 연차관리 | `!isLoaded` | 연차 현황 불러오는 중 |

이유를 **버튼 글자에 그대로** 적는다. 잠긴 채 '마감제출'만 떠 있으면 지점은 왜 안 눌리는지
모르고 본사에 전화한다. `submit()` 안에서도 한 번 더 막는다 — 표가 실패로 바뀌는 순간과
클릭이 겹치면 잠기기 전 클릭이 통과한다.

**마감취소는 막지 않는다.** 확인을 거두는 방향이라 게이트를 조이기만 한다(fail-closed).

### 4.3 확정해도 탭을 잠그지 않는다

다른 마감 섹션은 확정하면 입력이 잠기지만, 이 둘은 **잠그지 않는다.**
비즈니스택시 신청·연차 등록은 상시 업무라 잠그면 다음 달 초 업무가 막힌다.
확인 시점의 기록만 남긴다.

### 4.4 색

`DESIGN.md` 지점 색 규칙을 따른다.
- 미제출 = vanilla 계열(주의·미확인)
- 확정 = honey 계열(완료)
- 오류 배너 = hex 직접 지정(`bg-[#FDE2E2] / border-[#C93A3A] / text-[#B91C1C]`).
  `rose-*` 유틸리티는 지점 스코프에서 치환돼 경고가 평범한 안내로 보인다.
- 제목은 텍스트만(아이콘 금지).

### 4.5 권한 — 마감제출 버튼은 지점 계정 전부

연차관리 탭은 지금 **작성 권한이 지점관리자·총괄뿐**이다
(`BranchConfirmPage.tsx:762` → `canWrite={userRole === "admin" || userRole === "branchAdmin"}`).

**마감제출 버튼은 이 권한에 묶지 않는다.** 묶으면 지점관리자 계정이 없는 지점은
연차 확인을 영영 못 눌러 매입매출 마감까지 데드락에 걸린다.
확인은 연차 데이터를 고치는 행위가 아니므로 일반 지점 계정도 누를 수 있다.
`MonthlyCheckAction`은 `canWrite`를 받지 않는다.

연차관리 탭은 `canWrite`에 따라 반환 경로가 둘로 갈리는데, 확인 컨트롤은 **양쪽에 공통인
`직원별 연차 현황` 카드 안**에 있어 읽기 전용 계정에도 자동으로 따라간다.

## 5. 게이트 설계

### 5.1 대상 — 말일 제출 3종 전부

`runConfirm(section)` 진입부에서 확인한다.

| 섹션 | 게이트 | 이유 |
|---|---|---|
| `purchase` (매입매출) | ✅ | 말일 제출 |
| `salesSummary` (매출집계) | ✅ | 말일 제출 |
| `partTimeSalary` (파트타이머) | ✅ | 말일 제출 |
| `salary` (정직원 급여대장) | ❌ | 25일 작성 — 말일 확인과 시점이 다르다 |
| `businessTaxi` / `annualLeave` | ❌ | 게이트의 대상이지 주체가 아니다(자기참조 방지) |

매입매출 하나에만 걸면 지점이 매출집계를 먼저 눌러 우회한다. 셋 다 건다.

**게이트가 요구하는 확인 섹션은 `GATE_REQUIRED_SECTIONS` 다 — `CHECK_SECTIONS` 전체가 아니다.**
여기엔 **확인 버튼이 실제로 배포된 섹션만** 넣는다. 요구만 해 놓고 누를 화면이 없으면
그 지점은 말일 마감 3종이 **영구히 막힌다.** 게이트가 fail-closed 라 우회 통로도 없다.

이건 가정이 아니라 실제로 날 뻔했다: 연차관리 확인 버튼은 연차 인원출처 개편(별건 작업)과
한 덩어리라 첫 커밋(`47905ad`)에 들어오지 못했는데, 게이트는 두 섹션을 다 요구했다.
그 커밋만 배포됐다면 14개 지점 전부가 월말마감을 못 한다.

현재 값: `["businessTaxi"]`.
**연차관리 확인 화면이 배포되는 커밋에서 `"annualLeave"` 를 더할 것.**

### 5.2 판정 — 서버 최신값, fail-closed

```ts
// src/pages/branch/helpers/monthlyCheckSections.ts
export async function findMissingCheckSections(
  branchName: string, month: string
): Promise<("businessTaxi" | "annualLeave")[]>   // throw = 판정 불가
```

- `getSharedDataFromServer("monthly_closings")`로 읽는다. 화면 캐시는 다른 노트북이 방금 누른
  확인을 못 본다 — 캐시로 판정하면 이미 확인한 지점이 마감을 못 한다.
- 값이 있는데 배열이 아니면(형식 손상) `throw` — 확인 여부를 단정할 수 없으면 통과시키지 않는다.
- 조회 실패도 `throw` → 마감 중단. 네트워크 오류를 "확인됨"으로 흘리지 않는다.
- 호출부(`runConfirm`)는 `catch`에서 조회 실패용 안내를 따로 띄운다(같은 팝업 형식).

판정 기준 월은 **지금 마감하려는 달**(`MonthlySettleTab`의 `selectedMonth`)이다.
확인 컨트롤에서 고른 월이 아니다.

### 5.3 안내 문구 — 하단 토스트가 아니라 팝업

**`window.alert` 팝업으로 띄운다**(사용자 지시 2026-08-11). 토스트는 화면 아래에서 잠깐 떴다
사라져서, 마감 버튼만 보고 있던 지점은 못 보고 "왜 제출이 안 되지" 하며 다시 누른다.
눌러서 닫아야 하는 안내여야 한다.

미확정 섹션 이름과 **대상 월**을 함께 적는다. 월을 빼면 안 되는 이유:
확인 컨트롤의 기본값은 당월인데, 9월 1일에 8월 마감을 제출하는 경우 지점이 보는 화면은
2026-09이고 게이트가 요구하는 것은 2026-08이라 "분명히 눌렀는데 왜 막히지"가 된다.

```
매입매출 마감을 제출할 수 없습니다.

2026-08 비즈니스택시 · 연차관리 확인이 아직 안 됐습니다.

  · 인사·기타 > 비즈니스택시
  · 인사·기타 > 연차관리

위 화면에서 월을 2026-08로 맞추고, 표 내용이 실제와 맞는지 확인한 뒤 [마감제출]을 눌러주세요.
```

하나만 미확정이면 그 하나만 적는다.

### 5.4 게이트 위치

`runConfirm` 안, **다른 검증보다 먼저** 넣는다.
매출집계 정합성 검사나 급여대장 flush는 서버 왕복·쓰기를 동반하는데, 어차피 게이트에서 막힐
제출이면 그 작업을 먼저 시킬 이유가 없다. 다만 `salesSummary`의 `loadSalesSummaryForClose`는
읽기 전용이라 순서가 안전성에 영향을 주지는 않는다 — 순서는 왕복 절약 목적이다.

## 6. 기존 마감 저장의 쓰기 방식 변경 (필수 동반 수정)

`monthly_closings`는 **전 지점·전 섹션이 함께 쓰는 문서 하나**다.
기존 `saveSectionClose`는 서버 최신값을 읽어 **통째로** 저장했다(`saveSharedData`).

그대로 두면: 지점이 매입매출 마감제출을 누른 직후(서버 읽기 ~ 쓰기 사이) 다른 기기에서 택시 확인을
올릴 경우, 통째 저장이 그 확인 레코드를 덮는다. 그러면 **그 지점은 다음 마감이 막히는데,
확인 화면에는 '확정'으로 보여 원인을 찾을 수 없다.** 확인 섹션이 마감의 선행조건이 되면서
이 경쟁의 결과가 "화면 숫자가 잠깐 어긋남"에서 "업무가 막히고 이유를 모름"으로 나빠진다.

따라서 **판정과 쓰기를 한 트랜잭션 안에서** 한다.

`saveSectionClose`는 원래 트랜잭션 밖에서 서버를 한 번 읽고(`previous`), 그 스냅샷으로
재확정 여부·사유 요구·계보·`editedAfterConfirm` 표식을 정한 뒤 통째로 저장했다.
**쓰기만 트랜잭션으로 바꾸는 것으로는 부족하다** — 판정이 여전히 커밋되지 않을 스냅샷 기준이라,
읽은 뒤 커밋 전에 다른 기기가 같은 섹션을 바꾸면 낡은 판정이 그대로 커밋된다.

가장 나쁜 경우: 이쪽이 '미제출→확정'으로 읽은 사이 다른 기기가 확정 후 수정을 시작하면,
**사유 없는 확정**이 커밋되고 쌓여 있던 수정 이력까지 지워진다. 사유 게이트가 통째로 우회된다.

```ts
// 변경 전 — 밖에서 읽고, 밖에서 판정하고, 통째로 저장
const previous = await gasClient.getSharedDataFromServer("monthly_closings");
const prevServer = latest(previous);
const serverReconfirm = …;                       // ← 스테일 가능
if (serverReconfirm && !reason.trim()) throw …;
await gasClient.saveSharedData("monthly_closings", [merged, ...previous.filter(…)]);

// 변경 후 — 판정·쓰기가 같은 스냅샷 위에서
const { value: committed } = await gasClient.mutateSharedData<any[]>("monthly_closings", (current) => {
  if (current != null && !Array.isArray(current)) throw new Error(…);   // fail-closed
  const list = Array.isArray(current) ? current : [];
  const prevServer = latest(list);
  const serverReconfirm = …;                     // ← 커밋될 값 기준
  if (serverReconfirm && !reason.trim()) throw new Error(…);
  const merged = …;
  return [merged, ...list.filter((r) => !matches(r))];
});
if (Array.isArray(committed)) setMonthlyCloseRecords(committed);
```

트랜잭션은 경합하면 커밋될 스냅샷으로 다시 실행되므로, 판정이 항상 커밋될 값과 같은 것을 본다.
updater 안의 `throw`는 트랜잭션을 취소시킨다 — fail-closed가 유지된다.

**updater의 순수성**: `current` 외에는 바깥에서 이미 확정된 값(`now` · `reason` · `status` ·
`opts` · `nextRecord`)만 읽는다. 재시도로 여러 번 호출돼도 같은 입력이면 같은 결과다.

**커밋 결과는 반환값으로 받는다.** updater 안에서 바깥 변수에 담아 두면 재시도 때 값이 어긋난다
(`firebaseMutateBranchOwnRoster`가 이미 같은 이유로 값을 반환한다). 이를 위해
`firebaseMutateSharedData` / `gasClient.mutateSharedData`의 반환형에 `value`를 추가했다 —
기존 호출부는 `changed`만 쓰므로 하위호환이다.

로컬 상태는 커밋된 목록으로 갱신한다. `previous` 기준 목록을 쓰면 다른 섹션이 방금 바뀐 경우
화면이 되레 낡아진다.
