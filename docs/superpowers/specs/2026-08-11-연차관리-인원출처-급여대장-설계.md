# 연차관리 인원 출처 전환 — 직원현황 → 정직원 급여대장

작성일: 2026-08-11

## 1. 배경과 목표

연차관리 화면(관리자페이지 · 지점 인사·기타 탭)의 인원 목록은 지금 **지점 직원현황**
(`branch_own_rosters`)에서 온다. 직원현황은 일일마감이 근무자 이름으로 **자동 등록**하는 경로가
있어 오타 이름·퇴사 후 잔류 인원이 쌓이고, 지점이 손으로 정리하지 않으면 연차관리 표에 그대로 올라온다.

반면 **정직원 급여대장**은 매달 실제로 급여가 나가는 사람만 담기므로 "지금 일하는 정직원"에 훨씬 가깝다.
사용자는 앞으로 직원현황 탭의 역할을 줄여 갈 계획이며, 그 첫 단계로 연차관리의 인원 출처를 옮긴다.

**목표**: 연차관리가 보여주는 인원을 **정직원 급여대장 기준**으로 바꾼다.

**비목표(이번에 하지 않는 것)** — 사용자 지시 2026-08-11:

- **직원현황 탭을 지우지 않는다.** 화면·데이터 모두 지금 그대로 유지한다.
- **파트타이머는 건드리지 않는다.** 연차는 정직원에게만 부여하므로 정직원 급여대장만 다룬다.
- 일일마감·파트타임일지·대시보드 등 **다른 화면의 인원 출처는 그대로 둔다.**
- 명부 마스터 자체를 급여대장으로 뒤집는 공사는 하지 않는다(§9 후속 과제).

## 2. 확정된 결정

| # | 항목 | 결정 |
|---|---|---|
| 1 | 열람 권한 | 인원·연차 표는 **급여권한 계정만**. 월말 확인 밴드는 전원 유지 |
| 2 | 인원 마스터 | 정직원 급여대장 |
| 3 | 범위 | 정직원만. 직원현황 탭은 유지 |

| 5 | 인원 편집 | 지점변경·퇴사(X)·이름·입사일 수정을 연차관리에서 **제거** |

## 3. 현재 구조 (전환 전)

```
직원현황 탭(RosterTab) ─┐
일일마감 자동등록      ─┼→ branch_own_rosters/{지점}.employees
관리자 연차관리 편집   ─┘        │
                                 ├→ 정직원 급여대장이 매달 시드로 사용 (금액만 전월 승계)
                                 └→ 연차관리가 인원 목록으로 사용  ← 여기를 바꾼다
```

- 연차 데이터 저장소 (그대로 유지):
  - `annual_leave:{지점}` — 사용기록 배열. 각 항목의 `employeeId`가 사람을 가리킨다
  - `annual_leave_grant_overrides:{지점}` — 부여일수 수동값 `{employeeId: 일수}`
  - `annual_leave_used_adjust:{지점}` — 사용일수 보정 `{employeeId: 일수}`
  - `annual_leave_grants:{지점}` — 옛 부여일수 키(읽기 전용 승계)
- 급여대장 저장소: `monthly_fulltime_salary:{지점}:{YYYY-MM}` (shared_data)
- 부여일수 계산: `src/utils/annualLeavePolicy.ts` — 입사일(`entryDate`) 기반. **변경 없음**

## 4. 데이터 설계

### 4.1 새 공용 헬퍼 — 인원 조회의 단일 출처

관리자 섹션과 지점 탭이 각자 조회 로직을 적으면 두 화면의 인원이 달라진다.
**반드시 한 파일에서만 판정한다.**

```ts
// src/pages/branch/helpers/annualLeaveRoster.ts  ← 신규, 단일 출처

/** 급여대장에서 뽑아낸 연차 대상자 1명. */
export interface AnnualLeaveMember {
  /** 연차 데이터의 열쇠. null이면 연차 기록을 남길 수 없는 행(§4.3). */
  employeeId: string | null;
  name: string;
  entryDate: string;
  /** 급여대장 행 id — 화면 key 전용. 달마다 바뀔 수 있으므로 저장 열쇠로 쓰지 말 것. */
  rowId: string;
}

export interface AnnualLeaveRosterResult {
  /** 인원을 실제로 가져온 달("2026-07"). null = 최근 3개월 모두 비어 있음. */
  sourceMonth: string | null;
  members: AnnualLeaveMember[];
  /** 조회 실패 — 화면은 저장을 잠근다(fail-closed). */
  failed: boolean;
}

export async function loadAnnualLeaveRoster(
  branchName: string,
  today?: Date
): Promise<AnnualLeaveRosterResult>;
```

### 4.2 기준 월 결정 규칙

당월(`YYYY-MM`)부터 **최대 3개월** 역순으로 급여대장을 조회하고, **이름이 있는 행이 하나라도 있는
첫 번째 달**을 채택한다.

- 이름이 빈 행(수기 추가 직후 미입력 행)은 세지 않는다 — 빈 행 하나 때문에 8월이 채택되면
  실제 인원이 있는 7월이 가려진다.
- 금액이 0인 행은 **세어야 한다.** 로스터에서 막 올라온 신규 입사자는 금액이 비어 있다.
  (`flushFullTimeSalaryForClose`의 `hasMeaningful`과 판정 기준이 다르다 — 그쪽은 마감 가능 여부,
  이쪽은 인원 존재 여부다. 헷갈리지 말 것.)
- 3개월 모두 비었으면 `sourceMonth: null` → 화면은 "급여대장이 아직 작성되지 않았습니다" 안내.
- **채택한 달을 화면에 항상 표시한다.** 이게 없으면 지점이 "새로 뽑은 사람이 왜 안 보이나"에서
  헤맨다. 지점마다 기준월이 다를 수 있다(A지점 8월 / B지점 7월).

### 4.3 사람을 알아보는 규칙 (가장 중요)

연차 기록은 `employeeId`를 열쇠로 몇 년치가 쌓인다. 그런데 급여대장 행 `id`는 **안정적이지 않다**:
로스터에서 온 행은 `ft_{직원id}`, 지점이 손으로 넣은 행은 `ft_manual_{추가한 시각}`이고,
같은 사람이 다음 달 로스터로 다시 생기면 id가 달라진다. 그대로 열쇠로 쓰면 **연차 기록이 조용히
끊긴다** — 오류가 안 나므로 아무도 모른다.

그래서 `employeeId`를 이렇게 정한다:

| 순서 | 급여대장 행 | 사용할 열쇠 | 결과 |
|---|---|---|---|
| 1 | `row.employeeId`가 있다 (로스터에서 시드된 행 — 대부분) | 그 값 | 기존 연차 기록 그대로 이어짐 |
| 2 | `employeeId` 없음 + 이름이 직원현황에 있다 | 직원현황의 `id` | 기록 이어짐 |
| 3 | 위 둘 다 아니다 | **파생 열쇠**(아래) | 새로 쌓기 시작 |

**[수정 2026-08-11 — 사용자 지적]** 처음에는 3번을 `null` 로 두고 화면에서 '직원현황 미등록'으로 막았다.
**급여대장에서 인원을 가져오기로 해 놓고 직원현황에 없다고 막는 것은 앞뒤가 맞지 않는다.**
급여대장에 있는 사람은 예외 없이 연차를 쓸 수 있어야 한다. (부수 효과로 '미등록' 배지가 이름 칸을
밀어 이름이 잘려 보이던 것도 함께 사라진다.)

**파생 열쇠**: 급여대장 행 안의 **바뀌지 않는 값**에서 만든다.

- 주민번호가 있으면 `ftx-r{해시}` — 숫자만 남겨 해시(`801010-1234567` 과 `8010101234567` 을 같게 본다)
- 없으면 `ftx-n{해시}` — 이름 해시
- **주민번호를 열쇠에 그대로 넣지 않는다.** `annual_leave:{지점}` 은 급여권한 없이도 읽히는 문서라,
  거기에 주민번호가 박히면 보호 등급이 낮은 곳으로 개인정보가 샌다. 그래서 해시(FNV-1a)를 쓴다.
- 한계: 주민번호가 없는 사람의 **이름을 바꾸면** 열쇠가 달라져 기록이 끊긴다.
  끊긴 기록은 §4.5 알림이 화면에 띄운다(조용히 사라지지 않는다).

그 밖의 규칙:

- 이름 대조는 `String(name).trim()` 완전 일치. 급여대장 `mergeRows`의 `savedByName`과 같은 규칙을 쓴다.
- 직원현황에 **같은 이름이 둘 이상**이면 2번을 건너뛰고 3번으로 간다. 엉뚱한 동명이인의 연차에
  기록이 붙느니 새로 쌓는 편이 안전하다.
- 한 지점 목록에서 열쇠가 중복되면 **첫 행만** 남기고 나머지는 버린다(콘솔 경고).
  같은 사람이 두 줄로 보이면 사용일수가 두 배로 읽힌다.

### 4.3.1 확인 월과 표 기준월을 일치시킨다

인원은 **월말 확인 컨트롤이 고른 달**의 급여대장에서 뽑는다(`loadAnnualLeaveRoster(지점, 확인월)`).
이번 달 기준으로 뽑아 놓고 다른 달을 확정하면 **보지도 않은 달**을 확인한 것이 된다(Codex 지적).

`MonthlyCheckAction` 에 `onMonthChange` 를 추가해 고른 달을 호출부로 올린다.
되돌아본 끝에 채택한 달이 확인 월과 **다르면 마감제출을 막고**, 무엇을 하면 열리는지 버튼 글자에 적는다:
`2026-08이 아닌 2026-07 인원이 표시 중 — 2026-08 정직원 급여대장을 작성해 주세요`.

#### 4.4 조회는 서버 전용 — 캐시 폴백 금지

인원 조회는 `getSharedDataFromServer` / `getBranchOwnRosterFromServer` 로 **서버 문서만** 읽는다.

`getSharedData` 는 서버 읽기가 실패하면 **로컬 캐시로 폴백**한다. 그대로 쓰면 서버에 못 닿는 상황에서
묵은 급여대장이 정상 목록처럼 뜨고 `failed` 도 서지 않아, 지점이 **낡은 표를 보고 월말 확인(마감제출)을
눌러 버린다.** 그러면 확인 절차가 통째로 형식이 되고, 그 확정이 매입매출·매출집계·파트타이머 마감을
열어 준다(Codex 지적 2026-08-11 / `MonthlyCheckAction` 의 `blockedReason` 과 같은 취지).

이름 대조용 명부도 같은 이유로 서버 전용이다. 명부 조회 실패를 삼키면 `employeeId` 없는 행이 전부
'직원현황 미등록'으로 뒤집혀, 멀쩡한 직원이 등록 대상에서 빠진 채 화면은 정상처럼 보인다.

**인원만 서버로 읽고 연차 숫자는 캐시로 읽으면 구멍이 그대로 남는다.** 확인 대상은 부여·사용·잔여
숫자이므로, `annual_leave:*` · `annual_leave_grant_overrides:*` · `annual_leave_used_adjust:*` ·
옛 키까지 **전부** 서버 전용으로 읽는다. 관리자 섹션도 같다.

비용은 늘지 않는다 — `getSharedData` 도 내부적으로 `getDocFromServer` 를 먼저 부르고 실패했을 때만
캐시로 떨어진다. 바뀐 것은 **그 폴백을 없앤 것뿐**이다.

실패는 실패라고 말하고 화면이 저장·확인을 잠그게 둔다.

### 4.5 남겨진 연차 기록 알림

지점이동 기능을 없앤 결과, 직원이 A지점 급여대장에서 빠지고 B지점 급여대장에 들어가면 연차 기록은
`annual_leave:A` 에 그대로 남고 **B 화면에서는 사용 0일**로 보인다. 기록이 지워진 것은 아니지만 화면상
초기화된 것과 같아, 그대로 두면 **이미 쓴 연차를 다시 쓴다**(Codex 지적 2026-08-11).

`findStrandedLeaveOwners(entries, members)` 가 "그 지점 기록 중 지금 인원 목록에 없는 사람"을 골라내고,
관리자·지점 양쪽 화면이 주의색 안내로 보여 준다.

- **지우지도, 자동으로 옮기지도 않는다.** 이관 판단은 사람이 한다(§9의 이관 도구 전까지의 안전장치).
- 인원을 못 불러온 지점(급여대장 없음·조회 실패)은 **제외한다** — 그 지점 기록이 전부 떠 보인다.
- 이름은 관리자에서 등록한 기록(`staffName`)에만 있다. 없으면 "이름 미상 n명"으로 묶는다.

### 4.6 조회 실패 처리 (fail-closed)

급여대장·연차 데이터 조회가 하나라도 실패한 지점은 **저장을 잠근다.** 지금 관리자 섹션의
`lockedBranches` 규약을 그대로 확장한다 — 실패를 "값 없음"으로 삼키면, 부여/사용 칸을 스치기만 해도
서버의 진짜 수동값이 지워진다(2026-08-04 Codex 지적).

권한 부족(`permission-denied`)은 **실패가 아니라 "볼 수 없음"으로 따로 구분한다.** 잠금 경고를
띄우면 원인이 권한인지 네트워크인지 알 수 없다(§6).

**잠금이 실제로 걸리는지 확인할 것 — 두 곳이 뚫려 있었다**(Codex 지적 2026-08-11):

- **지점 탭**: 실패 시 `loadedKey` 를 **거둬야 한다**. 한 번 성공한 뒤 [다시 시도]가 실패하면
  `loadedKey` 가 남아 `isLoaded` 가 참으로 유지되고, "저장이 잠겼습니다" 배너를 띄운 채 저장이 통과했다.
- **관리자 섹션**: `load()` 에 `catch` 가 없어, 지점 목록 조회가 실패하면 `setLockedBranches` 까지
  가지 못하고 **잠금 목록이 이전 값(대개 비어 있음) 그대로** 남았다. 화면에는 낡은 인원이 떠 있는데
  저장은 열려 있는 상태다. `catch` 에서 전역 `loadFailed` 를 세우고 `blockedByLoadFailure` 가
  **전 지점을 막게** 한다.

- **사용기록 수정·삭제·일부삭제**에는 가드가 아예 없었다. 트랜잭션으로 쓰니 안전하다고 넘겼는데,
  세 기능 모두 **화면에 뜬 기록을 근거로** 서버를 고친다 — 낡은 내용으로 최신 기록을 덮거나 지운다.
  창을 여는 버튼에도 같은 가드를 건다(다 채우고 저장에서 거절당하면 헛수고다).

교훈 둘:

1. 잠금은 "실패했을 때 세우는 플래그"가 아니라 **"성공했을 때만 내리는 플래그"** 로 짜야 한다.
2. **트랜잭션은 잠금을 대신하지 못한다.** 트랜잭션이 지키는 것은 "쓰는 순간의 원자성"이지
   "쓰려는 값이 최신 화면에서 나왔는가"가 아니다.

**연차 섹션의 쓰기 경로는 일곱 개다** — 부여일수 저장 / 부여일수 되돌리기 / 사용일수 저장 /
사용 등록 / 사용기록 수정 / 사용기록 삭제 / 기간 일부 삭제. 새 쓰기 경로를 만들면 여기에 추가하고
가드를 건다.

## 5. 화면 설계

### 5.1 지점 화면 — 인사·기타 > 연차관리 (`AnnualLeaveTab.tsx`)

## 6. 권한

급여대장 문서는 Firestore 규칙(`isSalaryKey` / `canReadSalary`)이 급여권한 계정만 읽게 막고 있다.
그러므로 연차관리의 인원·연차 표는 **급여권한 계정만** 볼 수 있다.

| 계정 | 인원·연차 표 | 월말 확인 밴드 | 연차 등록·수정 |
|---|---|---|---|
| 총괄(admin) | ○ | ○ | ○ |
| 지점관리자 + 해당 지점 급여권한 | ○ | ○ | ○ |
| 지점관리자 (급여권한 없음) | ✗ 안내문 | 보이되 **누를 수 없음** | ✗ |
| 일반 지점(branch) | ✗ 안내문 | 보이되 **누를 수 없음** | ✗ |
| PIN 로그인 | ✗ 안내문 | 보이되 **누를 수 없음** | ✗ |

판정은 기존 `canReadSalaryBranch(user, branchName)`를 그대로 쓴다. 새 규칙을 만들지 않는다 —
화면과 `firestore.rules`가 어긋나면 개발자도구로 뚫린다.

**[결정 번복 2026-08-11]** 처음에는 데드락을 피하려고 "월말 확인은 권한과 무관하게 누를 수 있다"로
정했다. 그런데 권한 없는 계정은 **표를 한 줄도 못 본다.** 아무것도 못 본 확정이 매입매출·매출집계·
파트타이머 마감을 열어 주므로 확인 절차가 통째로 형식이 된다(Codex 지적).
그래서 **막되, 무엇을 하면 열리는지 문구로 알려 준다.** 데드락은 두 경로로 풀린다:

1. **총괄이 그 지점 화면에서 대신 확인** — 총괄은 전 지점 급여권한을 가진다
2. **그 지점 담당자에게 급여권한 부여** — 계정 관리에서 `salaryBranches` 에 지점 추가

컨트롤 자체는 계속 렌더한다(사라지면 어디서 확인하는지 알 수 없다). 마감**취소**는 막지 않는다 —
확인을 거두는 방향이라 게이트를 조이기만 한다.

안내 문구는 `salaryAccessDenialMessage(user, branchName)`를 재사용한다.

## 7. 위험과 엣지 케이스

| 상황 | 결과 | 대비 |
|---|---|---|
| 직원현황에 있는데 급여대장에 없는 사람 | 연차관리에서 사라짐 | **의도된 동작.** 기록은 지우지 않으므로 급여대장에 다시 오르면 되돌아온다 |
| 이번 달 급여대장 미작성 | 직전 달 인원으로 표시 | 기준월을 화면에 표시 |
| 3개월간 급여대장 없음 | 인원 0명 | "급여대장이 아직 작성되지 않았습니다" 안내 + 저장 잠금 아님(진짜 없는 것) |
| 신규 입사자를 급여대장에 아직 안 넣음 | 연차관리에 안 보임 | 안내문에 "급여대장에 추가하면 표시됩니다" 명시 |
| 급여대장 행의 입사일이 비어 있음 | 부여일수 0일 | 기존 동작과 동일(수동 부여값으로 조정 가능) |
| 급여권한 없는 지점관리자 | 자기 지점 연차를 못 봄 | **운영 조치 필요** — 계정별 급여권한 부여 |
| 지점 이동이 필요한 직원 | 옮겨 간 지점에서 **사용 0일**로 보임(기록은 옛 지점에 남음) | §4.5 남겨진 기록 알림이 양쪽 화면에 뜬다. 이관은 본사가 수동 처리(§9) |
| 서버에 못 닿는 상태로 연차관리를 염 | 표가 안 뜨고 저장·마감확인이 잠김 | **의도된 동작**(§4.4). 캐시로 채워 확정시키는 것보다 안전하다 |

**성능**: 관리자 화면은 지점당 최대 3회(급여대장 역추적) + 3회(연차 키) + 1회(이름 대조용 명부).
대부분 당월에서 끝나 지점당 5회로 지금과 비슷하다. `getSharedData` 캐시가 그대로 적용된다.

## 8. 검증 계획

로컬(`npm run dev`)에서 배포 전에 확인한다:

1. 당월 급여대장이 있는 지점 → 그 달 인원, 기준월 표시가 당월
2. 당월이 비고 직전 달만 있는 지점 → 직전 달 인원, 기준월 표시가 직전 달
3. 기존 연차 기록이 있는 직원의 부여·사용·잔여가 **전환 전과 같은 숫자**인지 대조 (최소 2개 지점)
4. 관리자 화면과 지점 탭의 숫자가 같은지 대조
5. 급여권한 없는 계정으로 접속 → 표는 안내문, **월말 확인 밴드는 정상 동작**
6. `employeeId` 없는 수기 행 → `직원현황 미등록` 배지, 등록 드롭다운에서 제외
7. 연차 사용 등록 → 관리자·지점 양쪽에 즉시 반영
8. 사용기록이 있는 직원을 급여대장에서 빼 본다 → **남겨진 기록 알림**이 관리자·지점 양쪽에 뜨는지(§4.5).
   되돌려 넣으면 알림이 사라지고 사용일수가 원래대로 이어지는지
9. 네트워크를 끊고 연차관리를 연다 → 캐시로 표가 채워지지 않고 **실패 배너 + 마감제출 차단**인지(§4.4)

전환 전후 숫자 대조(3번)를 **반드시 배포 전에** 한다. 여기서 어긋나면 `employeeId` 매칭이 깨진 것이다.

**Codex 리뷰 필수** — 한 줄만 고쳐도 직후 지독한 리뷰를 돌린다(상시 지침).

## 9. 후속 과제 (이번에 하지 않음)

- 급여대장 행에 **영구 직원번호**를 심어 직원현황 이름 대조 없이도 사람을 알아보게 한다.
  이게 되면 직원현황 의존이 완전히 끊긴다.
- 급여대장이 달이 바뀔 때 **인원을 자동 승계**하도록 한다(지금은 전월 금액만 승계).
  직원현황 탭을 실제로 지우려면 이게 선행되어야 한다.
- 파트타이머 급여대장도 같은 방식으로 마스터 승격.
- 지점 이동 시 연차 기록(`annual_leave:*`) 이관 도구 — 관리자 전용.
- 급여 금액을 뺀 **명단 미러 문서** 신설. 일반 지점 계정이 쓰는 화면(일일마감·파트타임일지·대시보드)이
  직원현황 없이도 굴러가게 하는 전제 조건.
