# 지점 근로계약서 등록 → 관리자 노출 설계서

> 작성일: 2026-07-17
> 대상: `erp_ugd` 지점화면 근로계약서 탭 (`src/pages/branch/tabs/LaborContractTab.tsx`), `AdminPage.tsx`, `BranchConfirmPage.tsx`

---

## 1. 목적

지점 점장이 **전자 근로계약서 발송이 필요한 인원의 인적사항을 직접 등록**하면, 그 내역이 **관리자 페이지에 나타나** 관리자가 확인 후 전자근로계약서를 보내주는 흐름을 완성한다. 아울러 지점이 **발송 진행 상태를 확인**하고, **파트타이머 근로계약서 양식을 내려받을 수 있게** 한다.

발송 자체의 자동화(전자계약 서비스 API 연동)는 이번 범위가 **아니다**.

## 2. 현재 상태 (조사 결과)

정직원 등록 흐름은 이미 대부분 구현되어 있고, **지점 쪽 입구만 막혀 있다.**

| 영역 | 현재 상태 |
|---|---|
| 지점 등록 폼 | 이름 / `010`+뒤8자리 / 급여 입력 폼 **구현 완료** |
| 지점 화면 접근 | `if (!isAdmin) return "현재 코드 수정중이므로 작성이 불가능합니다"` — **지점 계정이 막혀 있음**. 관리자만 폼을 볼 수 있는 의도와 반대인 상태 |
| 저장 | `labor_contracts_<지점명>` + `labor_contracts:<지점명>` (레거시 키 동시 저장). 지점·관리자가 같은 키 사용 → **연결 이미 완료** |
| 관리자 화면 | `AdminPage.tsx` → `근로계약서 발송 현황` → `발송 내역` 탭. 등록일·지점명·이름·연락처·급여·요청상태·진행상태(`발송 대기/발송 완료/서명 완료/보류`)·삭제 **구현 완료** |
| 파일 저장소 | **없음.** 엑셀은 전부 브라우저에서 즉석 생성(`XLSX.writeFile`). Firebase Storage는 `storageBucket` 설정값만 있고 사용 이력 없음 |
| 사이드바 탭 순서 | 대시보드 / 일일마감정산 / 월말마감정산 / **연차관리 / 근로계약서** |

## 3. 요구사항 (확정)

1. 지점 계정에서 근로계약서 등록이 **가능해야 한다**.
2. 관리자에게 필요한 정보는 **이름 / 010-뒤8자리 연락처 / 급여 / 지점**. 지점명은 자동으로 붙으므로 입력란 없음.
3. 급여는 **등록할 때만 입력**. 등록 후 지점 화면에서 **보이지 않고 수정도 불가**. (화면 레벨 차단 — 4.3)
4. 등록 후 **이름과 연락처만** 수정 가능.
5. 삭제는 **삭제요청 방식 유지** — 지점이 요청하면 관리자가 실제로 삭제.
6. 사이드바에서 **연차관리와 근로계약서의 위치를 서로 바꾼다.**
7. 지점 화면에서 **발송 상태를 확인**할 수 있고, **관리자가 상태를 바꾸면 지점 화면에도 동일하게** 보인다.
8. 근로계약서 섹션 디자인을 **다른 탭처럼 컴팩트하게** 정리한다.
9. 지점 화면에 **파트타이머 근로계약서 양식 다운로드 버튼**. 관리자가 양식을 등록하면 지점이 받는다.

## 4. 설계

### 4.1 차단 해제

`LaborContractTab.tsx`에서 두 가지를 제거한다.

- `if (!isAdmin)` 조기 반환 블록 — 지점 계정을 막던 게이트
- 화면 상단의 `"현재 코드 수정중이므로 작성이 불가능합니다"` 배너

결과: 지점·관리자 모두 동일한 등록 화면을 본다. `isAdmin` prop은 이 탭에서 더 이상 분기에 쓰이지 않는다.

> 참고: `AnnualLeaveTab`에도 동일한 차단이 걸려 있으나 **이번 범위 밖**이므로 건드리지 않는다.

### 4.2 등록 폼 (변경 없음)

이름 / `010`-뒤8자리 / 급여 3칸 + 등록 버튼. 기존 동작 유지:

- 연락처는 숫자만 8자리로 제한, 저장 시 `010-1234-5678` 형태로 포맷
- 급여는 `250만`, `2500000`, `250` 등을 모두 2,500,000원으로 해석 (`parseSalaryInput` 유지)
- 이름·연락처 8자리·급여가 모두 채워져야 등록 가능
- 신규 건은 `status: "발송 대기"`로 목록 맨 위에 추가

### 4.3 급여 노출 차단 (화면 레벨)

**채택: 화면에서만 숨김.** 급여 데이터는 기존대로 지점 브라우저까지 내려오되, 화면에 렌더링하지 않는다.

- 등록 목록 표에 **급여 칸을 만들지 않는다**
- 수정 모드에도 급여 입력란을 노출하지 않는다
- 관리자 페이지에서는 기존대로 급여가 보인다 (변경 없음)

**서버 단 차단은 채택하지 않는다.** 현실적 위험은 "점장 노트북 화면을 다른 직원이 어깨너머로 보는 것"이며 화면 숨김으로 해소된다. 급여를 입력한 주체가 점장 본인이라 점장에게 데이터를 숨기는 실익이 적은 반면, 저장 구조 분리와 관리자 조회 경로 변경이 함께 필요해 비용이 크다.

### 4.4 수정 / 삭제

**수정** — 이름·연락처만.

- 수정 버튼 → 인라인 편집 (이름, 연락처 뒤8자리)
- 저장 시 `editRequestedAt` 기록 → 관리자 화면에 파란 `수정됨` 칩 표시 (기존 구현)
- 급여 필드는 수정 대상에서 제외 — 기존 레코드의 급여 값을 **그대로 보존**한다

**삭제** — 요청 방식 유지 (현행).

- 지점이 `삭제요청` 클릭 → `deleteRequested: true`, `deleteRequestedAt` 기록
- 관리자 화면에 빨간 `삭제요청` 칩 표시, 실제 삭제는 관리자가 수행
- 급여 오타 대응 경로: 삭제요청 → 관리자 삭제 → 지점이 새로 등록. 이 안내 문구를 화면에 유지한다

지점이 직접 삭제하지 않는 이유: 이미 발송된 건이 관리자가 모르게 사라지면 안 된다.

### 4.5 사이드바 탭 순서 교체 (요구 6)

`BranchConfirmPage.tsx`의 `mainTabs` 배열에서 `annualLeave`와 `laborContract` 항목의 순서를 맞바꾼다.

```
대시보드 / 일일마감정산 / 월말마감정산 / 근로계약서 / 연차관리
```

`mainCategory` 타입 유니온과 렌더 분기는 순서와 무관하므로 수정 불필요. 아이콘·라벨은 각 항목에 붙어 함께 이동한다.

### 4.6 발송 상태 표시 및 연동 (요구 7)

**연동은 이미 되어 있다.** 관리자의 `updateStatus`가 `labor_contracts:<지점>`과 `labor_contracts_<지점>` 두 키에 모두 저장하고, 지점이 읽는 키가 바로 그것이다. 따라서 지점 목록 표에 **상태 칸을 추가해 `contract.status`를 표시**하면 된다(읽기 전용).

- 표시값: `발송 대기` / `발송 완료` / `서명 완료` / `보류`. 값이 없으면 `발송 대기`로 간주
- 상태별 색상 칩. 지점은 상태를 **변경할 수 없다** (관리자 전용)
- 지점 화면 진입/포커스 시 새로고침되도록 `visibilitychange`·`focus` 시 재조회 (관리자 화면의 기존 패턴과 동일)

**함께 고쳐야 하는 덮어쓰기 문제 (중요)**

지점의 `saveContracts`는 화면 메모리에 있는 배열을 **통째로 덮어쓴다.** 그래서 다음 사고가 가능하다.

1. 지점이 탭을 열어둠 (메모리에 `status: "발송 대기"` 상태의 배열 보유)
2. 관리자가 상태를 `발송 완료`로 변경 (서버 갱신)
3. 지점이 이름을 수정하고 저장 → **옛 배열이 통째로 덮여 상태가 `발송 대기`로 되돌아감**

지금은 지점 화면에 상태가 안 보여 드러나지 않았을 뿐, 요구 7을 구현하면 즉시 표면화된다. 대응:

- **저장 직전 서버에서 최신 배열을 재조회**하고, 내가 바꾼 필드(이름·연락처 또는 삭제요청 플래그)만 해당 `id`의 레코드에 병합한 뒤 저장한다
- 재조회 실패 시 저장을 중단하고 사용자에게 알린다 (조용한 덮어쓰기 금지)

**로드 실패 시 저장 잠금 (중요)**

`AnnualLeaveTab`에는 있으나 `LaborContractTab`에는 없는 안전장치. 현재는 로드 실패 시 `contracts`가 빈 배열로 남고, 그 상태에서 등록하면 **기존 내역 전체가 빈 배열로 덮인다.** 지점 저장을 허용하는 순간 실제 위험이 되므로 `AnnualLeaveTab`과 동일한 패턴을 적용한다.

- `loadedBranch` / `isLoaded` 상태로 "현재 지점 데이터를 실제로 받아왔는가"를 추적
- 지점이 바뀌면 렌더 중 동기적으로 무효화 (stale 저장 창 제거)
- 미로드 상태에서는 등록·수정·삭제요청 버튼 비활성 + 실패 배너와 `다시 시도` 버튼 노출

### 4.7 디자인 컴팩트화 (요구 8)

기준은 같은 폴더의 `AnnualLeaveTab` 및 다른 지점 탭들.

- 헤더 카드: `p-6` → `p-4`, 제목 `text-lg` → 기본 크기
- 표 셀: `p-4` / `py-4 px-3` → `p-3` 수준
- 빈 목록 / 로딩 셀: `p-12` → `p-6` 수준
- 표 최소 너비 `min-w-[760px]` 재검토 — 급여 칸이 빠지고 상태 칸이 들어오므로 실제 칸 수에 맞춰 조정
- 색상은 `DESIGN.md`의 기존 토큰을 사용하고 새 색을 만들지 않는다

칸 구성 변화: `등록일 / 이름 / 연락처 / ~~급여~~ / 상태(신규) / 안내 / 요청`

### 4.8 파트타이머 근로계약서 양식 다운로드 (요구 9)

**성격**: 전 지점 공통 **빈 양식 1개**. 관리자가 등록하면 모든 지점이 같은 파일을 받는다. 지점별·직원별 개별 파일이 아니다.

**저장 방식**: **Firestore 공유데이터에 파일을 그대로 저장** (base64 문자열).

- Firebase Storage는 콘솔에서 저장소 활성화 + 보안규칙 설정이 필요하고 요금제(Blaze) 전환이 요구될 수 있어 채택하지 않음
- 외부 링크(구글 드라이브) 방식은 공유 권한 오설정 시 지점에서 열리지 않아 채택하지 않음
- **제약: Firestore 문서 1개는 약 1MB가 상한.** base64는 원본보다 약 33% 커지므로 **원본 700KB를 상한**으로 잡는다

**데이터**: 공유데이터 키 `labor_contract_template_parttime` (단일 문서)

```
{ fileName, mimeType, size, dataBase64, uploadedAt }
```

**관리자 화면** (`AdminLaborContractsSection` 헤더 영역)

- `양식 등록` 버튼 (`<input type="file">`) — 형식 제한 없음(PDF·HWP·DOCX 등)
- 700KB 초과 시 업로드하지 않고 "파일이 너무 큽니다(최대 700KB)" 안내
- 등록되어 있으면 파일명·등록일 표시 + 교체(재등록) 가능
- 교체는 덮어쓰기. 이전 파일 이력은 남기지 않는다

**지점 화면** (근로계약서 탭 상단)

- `파트타이머 근로계약서 양식 다운로드` 버튼
- 클릭 시 base64 → Blob 변환 → 원래 파일명으로 저장
- 양식이 아직 등록되지 않았으면 버튼 비활성 + "본사에서 양식 등록 전입니다" 안내

### 4.9 관리자 화면 (그 외 변경 없음)

- `발송 내역` 탭의 표·진행상태 변경·삭제는 기존 그대로
- `지점 등록 후보` 탭(직원현황 `branch_own_roster` 자동 감지)은 **별개 기능**이므로 손대지 않는다

## 5. 범위 밖 (하지 않는 것)

- 전자계약 서비스 API 연동 및 자동 발송 (`blueprint-전자근로계약서-발송.md` Step 3~6)
- 급여의 서버 단 접근 차단
- `지점 등록 후보` 탭 로직 수정
- 저장 키 구조 변경 (`labor_contracts_` / `labor_contracts:` 이중 저장 유지)
- `AnnualLeaveTab`의 동일한 `isAdmin` 차단 해제
- 양식 파일의 버전 이력 관리

## 6. 검증 방법

로컬 `npm run dev`(localhost:3000)에서 **지점 계정**과 **관리자 계정** 양쪽으로 확인한다.

1. 사이드바 순서가 `… 월말마감정산 / 근로계약서 / 연차관리`인지
2. 지점 계정 근로계약서 탭에 등록 폼이 보이고 "코드 수정중" 문구가 사라졌는지
3. 등록 → 목록에 뜨고 **급여 칸이 없는지**
4. 수정 → 이름·연락처만 편집되고 **급여 입력란이 없는지**. 저장 후 관리자 화면에서 **급여가 유실되지 않았는지**, `수정됨` 칩이 뜨는지
5. 관리자 화면 `발송 내역`에 지점명·이름·연락처·급여가 정확히 뜨는지
6. **상태 연동**: 관리자가 `발송 완료`로 변경 → 지점 화면 새로고침 시 `발송 완료`로 보이는지
7. **덮어쓰기 방지**: 지점 탭을 열어둔 채 관리자가 상태 변경 → 그 상태에서 지점이 이름 수정 → **관리자가 바꾼 상태가 유지되는지** (되돌아가면 실패)
8. 삭제요청 → 관리자 화면에 `삭제요청` 칩
9. **양식**: 관리자가 양식 등록 → 지점에서 다운로드되고 파일이 정상적으로 열리는지. 700KB 초과 파일은 등록이 거부되는지. 미등록 상태에서 지점 버튼이 비활성인지
10. 크로스디바이스: 다른 기기에서 같은 지점 진입 시 동일 내역·동일 상태가 보이는지

## 6-1. 알려진 한계 (수용된 위험)

- **동시편집 경쟁(lost update)**: 저장이 "문서 전체 교체"(`setDoc`) 방식이라, 지점이 저장 직전 최신본을 읽은 순간과 실제 쓰기 사이의 짧은 창(1초 미만)에 관리자가 같은 계약을 수정/삭제하면 그 변경이 되돌아갈 수 있다. `readContracts` 재조회로 창을 크게 줄였으나 완전히 닫지는 못했다. 이 경쟁은 **본 작업 이전부터 관리자 화면에 존재하던 구조**이며, 지점·관리자가 같은 계약 1건을 같은 순간에 조작해야만 발생한다. 월 수십 건 규모에서 실현 가능성이 낮아 **트랜잭션화 없이 현행 유지**로 결정(2026-07-17, 사용자 승인). 완전 차단이 필요해지면 `firebaseSaveSharedData`를 `runTransaction` 기반 필드 병합으로 교체.

## 6-2. 디자인 방침 (V2 탭 정렬)

지점 화면의 최신 탭인 `OrderManagementTabV2`(발주관리)·`LiquorInventoryTabV2`(주류재고)의 디자인 언어에 맞춘다. 초기 파란 버튼(`#2E6DB4`)·회색 채움 입력칸은 올드하게 읽혀 교체:

- 제목: `text-sm font-black text-gray-900 w-fit` (아이콘 없음). 노란 알약은 공용 CSS가 h3에 강제 — V2 탭과 동일하게 적용됨
- 입력칸: `h-8` 흰 배경 + `border-gray-200` 얇은 테두리 (회색 채움 폐기)
- 기본 버튼: `bg-slate-800`(hover `slate-900`)
- 카드: `<section>` + `border-gray-100 shadow-sm`, 안내문 `text-[11px] text-gray-400`
- 표: 슬레이트 톤, `text-[11px]`, 행 `py-2.5`
