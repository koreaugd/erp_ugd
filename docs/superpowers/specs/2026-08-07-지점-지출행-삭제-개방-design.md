# 지점 지출 행 삭제 개방 (카드결제 취소/반품 대응) — 설계서

- 날짜: 2026-08-07
- 요청: 지점이 일일마감에 적은 카드지출이 나중에 결제 취소/반품됐을 때, 지점 스스로 ERP에서 그 행을 없앨 방법이 없다 → 지점 화면에서 처리할 수 있게 개선.

## 1. 현재 상태 (조사 결과)

| 경로 | 지점 가능 여부 |
|---|---|
| 일일업무 > 일일마감: 과거 날짜 선택 → 수정모드 승인 → 지출 행 수정/삭제 → 재제출 | **가능** (이미 있음) |
| 월말업무 > 카드지출/현금지출 탭: 행별 [수정] 버튼 (금액·사용처·분류·내용) | **가능** (2026-07-18 배포분) |
| 월말업무 > 카드지출/현금지출 탭: 행별 [삭제] 버튼 | **불가** — `isAdmin` 게이트로 관리자 전용 |
| 지출 금액 음수 입력 (환불 행 추가) | **불가** — 금액 칸은 숫자만 필터 |

- Firestore 규칙(`daily_settles`)은 접근권한 있는 계정 모두에게 update를 허용 — 백엔드 제한은 없다.
- 모든 수정·삭제는 `edit_logs`에 before/after로 남는다. 단, 카드/현금지출은 memo 안 METADATA에 저장되므로 관리자 "정산 변경이력"의 변경 요약(`getChangesSummary`)에는 **"변경 사항 없음"**으로 뜬다(요약이 memo를 비교하지 않음).

## 2. 확정된 방향 (사용자 승인 2026-08-07)

- **A안: 삭제 버튼 개방.** 취소 표시 보존(B안)은 카드지출을 읽는 모든 화면·엑셀에 "취소 행 제외"를 심어야 해서 합계 불일치 위험 — 기각.
- **사유 입력은 지점만 필수.** 관리자는 지금처럼 확인창만.

## 3. 변경 내용

### 3-1. MonthlyCardExpensesSubTab.tsx / MonthlyCashExpensesSubTab.tsx (동일 패턴)
- [삭제] 버튼의 `isAdmin` 게이트 제거 — 지점에도 노출.
- 삭제 핸들러:
  - 지점: `window.prompt`로 삭제 사유 필수 입력 (예: "카드결제 취소", "반품"). 취소·공백이면 중단.
  - 관리자: 기존 `window.confirm` 유지 (사유 선택 아님 — 안 받음).
  - **STALE_METAINDEX 가드 추가**: 수정 핸들러와 같은 4필드(금액·상세·사용처·분류) 대조. 현재 삭제는 이 가드가 없어, 로드 후 다른 사람이 앞 행을 지우면 엉뚱한 행을 지울 수 있는 잠재 결함이 있다(삭제를 지점에 열면 동시 사용이 늘어 위험이 커짐 — 이번에 함께 막는다).
  - try/catch: STALE이면 "목록이 바뀌어 취소" 안내 + 재조회, 그 외 실패는 알림.
- 사유는 `updateDailyMetadata`의 options로 전달.

### 3-2. 사유 전달 경로
- `dailyOps.ts` `updateDailyMetadata(recordId, updater, actor, options?: { reason?: string })`
- `gasClient.ts` `updateDaily(..., reason?)`
- `firebaseDirect.ts` `firebaseUpdateDaily(..., reason?)` → `edit_logs` 문서에 `reason` 필드 저장 (없으면 빈 문자열).
- 기존 호출부는 옵션 미전달 — 동작 불변.

### 3-3. AdminPage.tsx — 정산 변경이력 표시 개선
- `getChangesSummary`: memo METADATA의 `cardExpenses`/`cashExpenses`를 파싱해 건수·합계 변화를 요약 ("카드지출: 3건 90,000원 ➔ 2건 60,000원"). 파싱 실패 시 기존 문구 유지.
- `reason`이 있으면 변경 내용 앞에 "사유: …"를 표시.

### 3-4. Codex 리뷰 반영 (2026-08-08)
- **P0 — 동시수정 유실**: `updateDailyMetadata`가 "읽고 나서 통째 덮어쓰기"라 두 기기가 같은 날 기록을
  동시에 고치면 나중 저장이 먼저 저장을 되살렸다(지출 A·B 동시 삭제 → 한쪽 유실).
  → `firebaseUpdateDailyAtomic`(Firestore `runTransaction`) 신설, `gasClient.updateDailyAtomic` 경유로
  `updateDailyMetadata` 전체를 트랜잭션화. 이 헬퍼를 쓰는 5개 탭(월 카드/현금지출·현금관리·초과근무·파트타이머)
  모두 원자적이 된다. 각 탭의 updater는 전부 순수 함수임을 확인(경합 시 재실행되므로 필수 전제).
  일일마감 전체 폼 저장(`updateDaily`)은 의도적 전체 교체라 종전 유지.
- **P1 — editLogFailed 삼킴**: 삭제·수정 성공 후 이력 기록만 실패하면 조용히 묻힘
  → 4곳(카드/현금 × 삭제/수정) 모두 알림 추가.
- **P2 — 변경이력 노이즈**: 내용 비교를 JSON.stringify(객체)로 하면 key 순서·"30000" vs 30000 차이로
  거짓 "내역 수정됨" → 고정 순서 튜플(금액 Number 정규화)로 비교.

### 3-5. Codex 2라운드 반영 (2026-08-08)
- 2R 결과: P0·P2·P3 없음. 트랜잭션 closure·STALE 전파·mutator 재실행·레거시 경로 영향 모두 Clean 판정.
- **P1 — 초과근무 일지 낙관적 UI 미복원**: 수정/삭제가 낙관적으로 화면을 먼저 고치는데, 저장 실패 후
  복구 재조회까지 실패하면 저장 안 된 값이 화면에 남았다(트랜잭션은 오프라인에서 즉시 실패하므로 노출 증가).
  → `loadData`가 성공 여부를 반환하게 하고, 파트타이머 일지와 같은 스냅샷 복원을 수정/삭제 양쪽에 추가.

### 3-6. Codex 3~5라운드 + 정지게이트 반영 (2026-08-08)
- **3R P1 — 저장 중 화면 전환 경쟁**: 저장 실패 복원 스냅샷이 그 사이 바뀐 월/목록 위에 덮일 수 있음
  → 저장 중(saving) 월 선택기·새로고침·수기 등록 잠금(disabled).
- **4R P1 — 수기 등록이 잠금 밖**: 수기 등록 진행 중 수정/삭제 시작 가능
  → 수기 등록도 setSaving 임계구역에 편입 + 수정/삭제 진입 가드("다른 저장이 진행 중입니다").
- **5R: CLEAN.**
- **정지게이트 — 수기 기록 cross-device 유실**: `manual_overtime`/`manual_parttime` 목록을
  "읽고-통째저장"해서 두 기기가 동시에 등록/수정/삭제하면 한쪽이 유실
  → 기존 트랜잭션 헬퍼 `gasClient.mutateSharedData`로 5곳 전부 교체(초과근무 등록/수정/삭제 + 파트타이머 등록/삭제).
  수기 등록 항목(id=Date.now())은 mutate 밖에서 생성해 트랜잭션 재시도에도 id가 고정되게 함.

### 3-7. Codex 6~7라운드 (2026-08-08)
- **6R P0 — 관리자 수기삭제 잔존**: AdminPage `deleteManualRecord`가 여전히 읽고-통째저장
  → mutateSharedData로 교체. src 전체 grep으로 manual_* 키의 읽고-통째저장 쓰기 잔존 0건 확인.
- **7R: CLEAN** (P0/P1/P2 없음, 전체 diff 재스캔 포함). npm run lint·build 통과.
