# 계정관리·법인택시·근로계약서 개선 설계 (2026-07-29)

사용자 요청 5건에 대한 설계. 모두 클라이언트(웹앱) 수정만으로 구현하며 **GAS 재배포는 불필요**하다
(관리자 지점 변경에 쓰는 `updateKakaoTaxiMember`는 이미 운영 GAS에 배포돼 있음).

## 1. 계정관리 — 행 내 즉시 승인 + 상세 자동 스크롤

대상: `src/pages/admin/AccountManagementSection.tsx`

- **행 내 승인 버튼**: `reviewedByAdmin === false`인 행의 이름 셀에 `[승인]` 버튼을 추가한다.
  - 클릭 시 `markReviewed(uid)` 호출(기존 함수 재사용). `stopPropagation`으로 행 클릭(상세 열기)과 분리.
  - 처리 중 중복 클릭 방지(해당 uid 진행 중 표시), 성공 시 "신규" 배지가 사라진다.
- **상세 자동 스크롤**: 상세 패널 위치는 지금처럼 표 아래 유지(사용자 선택). 상세 패널에 `ref`를 달고,
  `editingUid` 변경 시 `useEffect`에서 `scrollIntoView({ behavior: "smooth", block: "start" })` 실행.
  다른 행 클릭 시에도 다시 상세 위치로 내려간다.

## 2. 법인택시 — 삭제요청 폐지, 변경신청(지점변경) 도입

### 2-1. 요청 타입 확장
대상: `src/pages/admin/helpers/kakaoTaxiRequests.ts`

- `KakaoTaxiRequestType`에 `"branchChange"` 추가. **`"delete"`는 타입에서 제거하지 않는다**
  (이미 접수된 레거시 삭제요청 레코드가 Firestore에 남아 있으므로 읽기·표시용으로 유지).
- `KakaoTaxiRequest`에 필드 추가: `targetBranch?: string`(옮겨간 지점, 모르면 빈값),
  `effectiveDate?: string`(이동일, YYYY-MM-DD).
- 라벨: `branchChange` = "변경신청(지점변경)". 지점 화면에서 `delete` 신규 생성 경로는 전부 제거.

### 2-2. 지점 화면
대상: `src/pages/branch/tabs/BusinessTaxiTab.tsx`

- 직원 행의 [수정 요청]/[삭제 요청] 버튼 2개 → **드롭다운 1개**로 교체.
  옵션: `선택`(기본값, 아무 동작 없음) / `수정요청` / `변경신청`. 삭제요청 옵션 없음.
- `수정요청`: 기존과 동일(사유 필수 입력 → 제출).
- `변경신청`: 입력 3개 — 옮겨간 지점(ERP 지점 목록 select, "모름" 허용=빈값), 이동일(date, 기본값 오늘),
  사유(필수). 제출 시 `type: "branchChange"`로 저장. 중복 차단 로직(pending/processing 존재 시 차단)은 기존 재사용.
- 제출 후 드롭다운은 `선택`으로 리셋.

### 2-3. 관리자 신청관리
대상: `src/pages/admin/KakaoTaxiSection.tsx`

- `branchChange` 요청 행: **승인 UI = 새 지점 드롭다운(요청의 targetBranch가 있으면 미리 선택) + 적용일
  (요청의 effectiveDate 기본, 수정 가능) + [지점변경 승인] 버튼**.
  - 승인 실행: ① `updateKakaoTaxiMember`로 `department`만 새 지점으로 변경(이름·전화·그룹은 기존 값 유지,
    4필드 전송 규칙 준수) ② 지점 변경 이력 기록(§3) ③ 요청 상태 `approved` 처리.
  - 그룹(group_ids)은 건드리지 않는다 — 카카오 API가 그룹 제거를 거부하므로(기존 제약) 부서만 이동.
- **레거시 `delete` 요청 행**: 기존 [삭제하기] 옆에 **[지점변경으로 처리]** 버튼을 추가 — 위와 같은 승인 UI로
  전환해 직원을 지우지 않고 소속만 옮길 수 있게 한다. [삭제하기]는 유지하되 기존 경고문 그대로
  (진짜 퇴사·오등록 정리는 관리자 직원관리 탭과 함께 여전히 가능).

## 3. 지점 변경 이력 — "변경일부터만" 새 지점으로 집계

### 3-1. 문제
이용내역은 ERP에 저장되지 않고 카카오 API가 **조회 시점의 직원 부서(=현재 지점)** 를 실어 보낸다.
그래서 부서를 바꾸면 과거 내역까지 소급 재집계되고, 직원을 삭제하면 과거 내역의 지점이 null이 된다.

### 3-2. 저장소
- Firestore `shared_data` 문서 **`kakao_taxi_branch_history`** (전역 1문서, `{ value: Entry[] }`).
- `Entry = { id, accountKey, memberId, memberName, fromBranch, toBranch, effectiveDate(YYYY-MM-DD),
  recordedAt(ISO), note? }`
- 기록 시점: ① 관리자 직원관리 수정에서 `department`가 실제로 바뀔 때(수정 폼에 **적용일** date 입력 추가,
  기본값 오늘 — 과거 날짜 입력 시 소급 보정 가능) ② §2-3 변경신청 승인 시.
- 쓰기는 Firestore 트랜잭션 append(기존 `kakao_taxi_requests` append 패턴 재사용). 크로스디바이스 일관성 확보.

### 3-3. 집계 반영
대상: `src/pages/admin/helpers/kakaoTaxi.ts` (`resolveBranchName`), `KakaoTaxiSection.tsx`

- 이용내역 화면 로드 시 이력 문서를 함께 읽어 `accountKey|memberId` → 이력(적용일 오름차순 정렬) 맵 구성.
- 주문 1건의 지점 판정(이력이 있는 직원만 적용, 없으면 기존 로직 그대로):
  - 주문일 = `departure_time`(없으면 `call_time`)의 날짜.
  - 주문일 ≥ 어떤 이력의 적용일 → 그 이력들 중 가장 늦은 것의 `toBranch`.
  - 주문일 < 첫 이력의 적용일 → 첫 이력의 `fromBranch`.
- 효과: 변경일 이후 이용분만 새 지점으로 집계. 삭제돼 `member_department`가 null이 된 직원도
  이력이 있으면 과거 집계가 복원된다(기존 하드코딩 보정표 `KAKAO_RETIRED_MEMBER_BRANCH`는 그대로 두되
  이력이 우선).
- 지점별/직원별 합계·이상 점검 등 `resolveBranchName`을 쓰는 모든 집계에 자동 반영.

## 4. 근로계약서 — 계약유형 3종 필수 선택

대상: `src/api/gasClient.ts`(LaborContract 타입), `src/pages/branch/tabs/LaborContractTab.tsx`,
`src/pages/AdminPage.tsx`(AdminLaborContractsSection)

- `LaborContract`에 `periodType?: "1주" | "2주" | "정규"` 추가.
- 지점 등록 폼: **계약유형 드롭다운(필수)** — `선택`(기본값) / `1주 단위` / `2주 단위` / `정규(수습 후 계속)`.
  미선택 시 등록 버튼에서 검증 실패 안내.
- 지점 표·관리자 표에 "계약유형" 컬럼 추가. 기존 등록건(필드 없음)은 `-` 표시.
- 양식 파일은 현재처럼 단일 공통 양식 유지(유형별 양식 분리는 이번 범위 아님).

## 5. 계정 비밀번호·이름·전화번호 변경

- **비밀번호**: 관리자가 직접 설정은 불가(서버 없는 Firebase 구조). 계정관리 상세에
  **[비밀번호 재설정 메일 보내기]** 버튼 추가 — `sendPasswordResetEmail`로 해당 계정 이메일에 재설정 링크 발송.
  구글 로그인 계정에는 비밀번호가 없으므로 안내 문구 표시.
- **이름·전화번호**: 계정관리 상세의 읽기 전용 텍스트를 **입력칸으로 전환**, 저장 시
  `users/{uid}`의 `name`/`phone` 갱신(기존 `updateUserProfile` 확장). Auth `displayName`은 관리자 권한으로
  변경 불가하므로 Firestore 값만 갱신(화면 표시는 Firestore 기준이라 문제 없음).
- 규칙 확인: `firestore.rules`가 개인 관리자에게 타인 문서 update를 이미 허용 — 규칙 변경 불필요.

## 구현 후 Codex 리뷰 반영 (5라운드, 2026-07-29)

- 1R: ①계정관리 전체 저장→**변경 필드만 저장**(editBaseline+buildDirtyPatch, markReviewed 동일) ②지점변경 승인의 이력 실패 처리 ③빈 fromBranch→'미지정' 명시(BranchAtDate) ④이력 로드 실패 시 엑셀 차단 ⑤근로계약서 등록 **트랜잭션 append**(+레거시 키 선 시드). 스톱게이트: saveEdit 계정 간 부서변경 가드.
- 2R: **이력 선기록(history-first) 구조로 재설계** — 선점→이력 append(실패 시 카카오 미실행·선점 해제=깨끗한 재시도)→카카오 PUT(확정 실패 시 보정 이력 append로 상쇄)→승인 기록. prevBranch 재시도안 폐기.
- 3R: 지점변경 승인도 선점 직후 **직원 재조회(fail-closed)** 후 가드 재검증, PUT·이력을 최신본 기준으로.
- 4R: 재조회에 forceRefresh=true(캐시 우회) — saveEdit 기존 검사도 동일 적용.
- 5R 잔여(수용한 한계): 재조회→카카오 PUT 사이 수 초의 시간차 경쟁은 카카오 API에 조건부 갱신이 없어
  클라이언트만으로 원천 차단 불가. 두 관리자가 같은 직원을 동시에 수정하는 경우에만 발생하며,
  기존 운영 saveEdit 검사와 같은 구조의 알려진 한계로 문서화한다.
